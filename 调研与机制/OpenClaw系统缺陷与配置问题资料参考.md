# OpenClaw 系统缺陷与配置问题资料参考# 一、可能导致 Kimi 无法 spawn 的根本原因## 1.1 allowAgents 配置位置错误（Issue #47862）**官方文档确认**：`allowAgents` 必须在 `agents.list[].subagents` 中，而不是 `agents.defaults` 中。```json5// ❌ 错误位置{  agents: {    defaults: {      subagents: {        allowAgents: [ceo, atlas-deep]      }    }  }}// ✅ 正确位置{  agents: {    list: [      {        id: router,        subagents: {          allowAgents: [ceo, atlas-deep, data-analyst]        }      }    ]  }}```**如果 allowAgents 配错位置**，`sessions_spawn` 会返回：```json5{status: forbidden, error: agentId is not allowed for sessions_spawn (allowed: none)}```## 1.2 operator.admin scope 被 Gateway 剥离（Issue #666）**症状**：```sessions_spawn errorCode=INVALID_REQUEST errorMessage=missing scope: operator.admin```**原因**：Gateway 可能剥离了 `operator.admin` scope，即使后端显式请求了。**这直接导致 sessions_spawn 失败**，即使配置正确也无法 spawn 子代理。**修复**：升级到 OpenClaw v2026.3.11+（包含 pairing fix + announce delivery refactor）。## 1.3 Python 独立脚本无法调用 sessions_spawn（架构限制）**这是 ds_kimi 自己承认的问题**：OpenClaw 的工具（`sessions_spawn`、`kimi_search`、`browser` 等）**只在 Agent 对话上下文中可用**。独立 Python 进程无法访问 OpenClaw 运行时环境。**这意味着**：- 后台 Python 脚本永远无法 spawn Kimi- 只有 Agent 在对话中直接调用 `sessions_spawn` 才能工作- 之前设计的「Python 脚本跑测试」架构从根本上不可行## 1.4 权限问题（EACCES）如果 `openclaw.json` 被 root 编辑后权限变成 `root:root 600`，OpenClaw（以 UID 1000 运行）无法读取配置，会默认回退到 `allowed: none`。**解决方案**：```bashchown 1000:1000 openclaw.json```# 二、模型配置缺陷## 2.1 contextWindow 配置键不被识别（Issue #24068）**症状**：```Error: Config validation failed: Unrecognized key: contextWindow```**正确配置方式**：OpenClaw 不接受 `contextWindow` 这个键。需要通过其他方式设置上下文限制。**实际上 ds_kimi 提到的 `compaction.maxTokens = 24000` 也是一个不合法的键**，他在汇报中也承认了这一点并删除了。## 2.2 上下文窗口检测错误OpenClaw 可能错误检测模型的上下文窗口。例如：- Ollama API 报告 32768 tokens- OpenClaw 只检测到 4096 tokens- 然后阻止模型运行：```⚠️ Agent failed before reply: Model context window too small (4096 tokens). Minimum is 16000.```**这可能导致 Kimi 模型被错误阻止**。## 2.3 模型配置路径复杂OpenClaw 的模型配置路径不直观：```json5{  agents: {    defaults: {      models: {        kimi: {          // 配置在这里        }      }    }  }}```如果配置路径错误，模型可能使用默认参数运行，导致意外行为。# 三、记录系统缺陷## 3.1 日志包含敏感信息**默认配置下，日志包含**：- API keys（明文）- 请求体（完整内容）- 响应内容**这是严重的安全问题**。应该启用：```json5{  logging: {    level: warn,    format: json,    redactKeys: true,    redactPII: true  }}```## 3.2 日志无限增长**默认配置没有日志轮转**。日志文件会无限增长直到占满磁盘。应该配置：```json5{  logging: {    outputs: [      {        type: file,        path: /var/log/openclaw/gateway.log,        rotation: {          maxSize: 100MB,          maxFiles: 10,          compress: true        }      }    ]  }}```## 3.3 会话历史无限增长OpenClaw 默认不清理会话历史。长期运行后：- 主会话上下文无限增长- 每次请求携带越来越多历史- 最终导致上下文窗口溢出**应该配置**：```json5{  session: {    maintenance: {      mode: enforce,      pruneAfter: 24,      maxEntries: 100,      maxDiskBytes: 104857600    }  }}```# 四、Gateway 配置安全缺陷## 4.1 绑定到 0.0.0.0（高危）**默认配置**：```yamlserver:  host: 0.0.0.0  port: 3000```**风险**：Gateway 暴露在所有网络接口上，包括公网。**修复**：```yamlserver:  host: 127.0.0.1  port: 3000```## 4.2 无认证**默认无 gateway auth**。任何人可以访问 agent。**修复**：```bashOPENCLAW_GATEWAY_AUTH=true```## 4.3 未设置速率限制**默认无速率限制**。单个客户端可以耗尽所有 API token。**修复**：```json5{  rateLimit: {    enabled: true,    windowMs: 60000,    maxRequests: 60,    keyBy: ip  }}```# 五、实验流程设计缺陷（基于资料总结）## 5.1 架构设计错误：后台脚本 vs Agent 直接执行| 方案 | 可行性 | 问题 ||------|--------|------|| Python 脚本调用 API | ✅ 可行 | 只能调用 HTTP API，无法 spawn 子代理 || Python 脚本间接 spawn | ❌ 不可行 | Agent 不会自动检查文件系统任务 || Agent 直接执行 | ✅ 可行 | 需要人工触发或在对话中执行 |**结论**：ds_kimi 设计的「Python 脚本跑完整链路」方案从根本上不可行。## 5.2 子代理完成信号丢失（Issue #50747）**已知 bug**：子代理完成后，父会话收不到完成信号。这会导致：- 父会话永远卡在 processing- 消息队列阻塞- 新消息无法处理**这不是配置问题，是 OpenClaw 的 bug**。## 5.3 评估模块缺失之前没有 Step 2/3/4 的评估模块，导致：- 无法检测 Kimi 是否真正执行- 无法检测结果是 mock 还是真实- 把 Step 1 pass 误判为链路完成# 六、给 ds_kimi 的检查建议基于以上资料，建议 ds_kimi 重点检查：## 6.1 配置检查清单- [ ] `allowAgents` 是否在正确的位置（`agents.list[].subagents`）- [ ] `operator.admin` scope 是否被授予- [ ] `openclaw.json` 权限是否为 `1000:1000`- [ ] Gateway 是否绑定到 `127.0.0.1`- [ ] Gateway auth 是否启用- [ ] 速率限制是否配置- [ ] 日志是否启用了 redactKeys 和 redactPII- [ ] 会话清理是否配置（pruneAfter, maxEntries）## 6.2 模型配置检查- [ ] Kimi 模型的配置路径是否正确- [ ] 上下文窗口是否被正确检测- [ ] 是否有 `contextWindow` 等非法配置键## 6.3 记录系统检查- [ ] 日志文件大小，是否配置了轮转- [ ] 日志中是否包含敏感信息- [ ] 会话文件数量，是否膨胀- [ ] MEMORY.md 大小，是否超过 15KB## 6.4 流程设计检查- [ ] 是否还有独立 Python 脚本尝试 spawn 子代理- [ ] 子代理超时是否设置合理- [ ] 是否有状态文件检查机制（替代 sessions_yield 等待）
