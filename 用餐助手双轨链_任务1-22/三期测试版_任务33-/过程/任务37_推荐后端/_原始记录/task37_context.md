# 推荐系统结构设计与UI执行方案

版本：v1.0 | 2026-09-28 | 编制：kimi
依据：执行卡079（详细）/080（快速）/初始化prompt 081/路由头v2（方法步骤以此为准）+ 设计方案v3页面流程（UI以既有计划为准）+ Walter新增要求"每次新的一餐重启推荐对话"

## 一、推荐系统结构设计（四层）

### L0 会话层：每餐一个推荐会话（新餐重启）

- 每次新的一餐 = 新建 `mealSession` 对象：`{mealId, scene, userRequirements, degreeWords, hardFilters, candidates, stage, results}`。
- **重启规则**（Walter新增+卡081"默认独立"一致）：新一餐默认独立会话，不携带上一餐任何状态；仅当用户显式声明"接着上一顿"时才按声明范围延续并记录。
- 会话状态机：`场景判定 → 需求/约束收集 → 候选装载 → 推荐（卡管线）→ 两段式输出 → 用户确认 → 结果入dish_profile，会话关闭`。关闭后只读，不可追加。
- 与既有"餐次"数据模型的衔接：一餐=一条 daily 记录下的 meal 单元，推荐结果确认后写入该 meal。

### L1 装配层：prompt 装配器（common/recommend.js）

每次调用按序拼装：`初始化prompt(081) + 当次执行卡(079或080) + 速查表相关节选 + 候选清单（含成分/效应摘要与数值负荷） + 用户输入原文`。
- 速查表存云数据库集合 `ref_tables`（表号→内容），装配器按初始化块"将查的表"按需拉取，不全量装载。
- prompt资产版本化：079/080/081带AGT编号与supersedes链，DB存"当前生效版本"，代码不硬编码prompt全文。
- 用户输入走文本；识图菜单的候选清单来自识别确认门禁之后的已确认结果（与任务26门禁衔接）。

### L2 网关层：两个功能位

| mode | 模型 | 思考 | 对应卡 |
|---|---|---|---|
| recommend_deep | deepseek-flash | medium（复杂个案可上探high） | 详细卡079 |
| recommend_fast | deepseek-flash | low（推理任务禁off） | 快速卡080 |

支持度标注的"无支持项查证"（步骤4.6，与初稿隔离作答）= 第二次独立调用（同一mode，新开消息不携带初稿），由装配器编排。

### L3 规则层（代码，不进prompt）

- 硬约束双保险：过敏原/素食/忌口/重选既在规则层前置过滤（候选进装配前先剔除），agent步骤2再过滤一遍；两层结果不一致时以规则层为准并记录。
- 数据供给：候选的成分数值只来自营养库/dish_summary，模型不得自产数字（沿用nutrition红线）。
- 原任务26的余弦双标准排序正式降级为兜底：仅当agent停摆（速查表缺口声明）时使用。

## 二、UI执行方案（以设计方案v3页面流程为准，极简工具风）

点餐页（order）内推荐流，主流程≤3屏、每屏一个重点：

**第1屏 场景与约束**（进页即新会话，顶部有"新一餐"明示）
- 场景按钮六选一（单选）：天热解渴 / 吃辣了 / 解馋尝鲜 / 饿了顶饱 / 夜宵喝点 / 随便推荐（采用卡080占位文案）
- 约束按钮多选可跳过：不吃辣 / 不要酒 / 清淡点 / 预算优先 / 跳过
- 自由输入框（补充要求，程度词如"别太辣"写在这里，进排序因子）
- 加菜场景：选"加菜"后出现"已有食物"输入（可拍照识图回填）
- "快速推荐"为显式按钮/口令（仅它触发快速卡080；其余一律详细卡079——按卡v2规则）

**第2屏 推荐结果（两段式第一段）**
- 卡片式排名：每项一行——排名 | 菜名 | 分数 | 一句话理由 | 支持度标记（有来源/部分支持/无支持，文字小标签）
- 底部"展开完整分析"按钮 → 第3屏

**第3屏 完整分析（第二段）**
- 需求清单 / 匹配结果 / 参数记录 / 局限声明 四段固定排版
- 底部：确认加入本餐（→接任务36话术生成/翻译/播报）、重新筛选（回第1屏保留约束）

**停摆态**：agent声明速查表缺口时，UI显示"这类情况我还没学会，先用简单推荐"+兜底排序结果，并把缺口场景记录到待扩充清单。

# 详细推荐执行卡

## 适用

完整需求提取与逐候选分析。动词：分析/推荐/评估。候选多、需求杂、需完整记录。

**默认卡**：进食者未显式说明"快速"时，一律用本卡。

## 管线

| 步骤 | 动作 | 关键约束 |
|---|---|---|
| 0 | 场景判定 | 加菜 / 重新点餐。默认独立。跨场景延续须声明 |
| 0.5 | 用户要求过滤 | 最高标准。不符者出局。冲突→声明询问。无剩余→如实说，不凑数。**程度词（"不太/别太/不要太"）须同时提取为排序因子** |
| 0.6 | 通用底线过滤 | **默认激活，无论用户有无特殊需求**。查 R9（062），五维度逐一检查；不通过→降级或出局；触发例外须声明理由 |
| 1 | 需求提取 | 目的→第一级。缺口→第二级。搭配类→味型+成分双维。健康限制→硬性过滤。**本次用餐全部要求须写入需求清单**。底线未过者不进入此步 |
| 1.5 | 稳定性判定 | 触发：模糊指令 或 候选>12。维度：成熟度/波动度/流行度。高者优先，同层级随机。依据 033 |
| 2 | 前置过滤 | 忌口/重选。信息不足→按含有处理，移出 |
| 3 | 候选转写 | 按成分构成与已知效应→味型层/成分层双陈述。**数值负荷（辣度/糖度/盐度等）须逐项标注，不得省略**。**识图时：先读图例/说明文字判定标注体系，再逐项对照菜品旁符号计数，不得跳步或凭记忆补全**。**辣度识别：菜单有图例或自有分级体系时以菜单为准；无图例时按符号数目在菜单内排序相对辣度，不对应微辣/中辣等绝对名称，不跨菜单比较。标注体系查 051**。禁名称标签 |
| 4 | 方向核对 | 逐维比对：命中/部分命中/未命中。**多菜品时逐个添加，每加一个菜更新整体负荷状况** |
| 4.5 | 支持度标注 | **每个推荐举例生成时同步标注：有来源 / 部分支持 / 无支持**。依据见"支持度标注规则" |
| 4.6 | 无支持项查证 | 标注"无支持"的项→查证其关键特性（口味强度/成分/禁忌/适用人群）是否符合各维度基本要求；查证通过→保留并附依据；未通过→移除并声明。**查证与初稿隔离作答** |
| 5 | 加权汇总 | 维度权重→三值结论。部分命中必附代价 |
| 6 | 输出 | 需求清单/匹配结果/参数记录/局限声明 |

## 支持度标注规则

| 标注 | 判定标准 | 处置 |
|---|---|---|
| 有来源 | 该项可直接由速查表（016/020/058/068/062）或菜单文本支撑 | 直接进入输出 |
| 部分支持 | 方向有表支撑，但具体特性（强度/禁忌）未在表中 | 保留，输出中标注"特性未查证" |
| 无支持 | 该项来自联想、常识或记忆，无任何表内依据 | 必须经步骤 4.6 查证，否则移除 |

**标注对象**：所有推荐举例（具体品种、具体品类特性声明）。类型级推荐（如"乳基饮"）若方向来自速查表，标"有来源"。

**已知局限（如实声明）**：标注依赖模型自评，自评不准时无支持项可能漏检（Lanham et al. 2023）。此为本机制的固有代价。

## 过滤优先级

1. 用户要求（含程度词） 2. 健康限制 3. 通用底线（R9） 4. 稳定性 5. 忌口重选 6. 方向核对

## 参数

| 参数 | 默认 | 调节 |
|---|---|---|
| 级间权重 | 目的占优 | 目的模糊→提高缺口 |
| 维度权重 | 均衡 | 健康→成分层；感官→味型层 |
| 匹配阈值 | 中位 | 候选少→下调；多→上调 |
| 限制严格度 | 不可协商 | 显式声明方可下调 |
| 稳定性阈值 | 12 候选 | 超出触发 1.5 |
| 随机允许度 | 同层级内 | 稳定性并列时启用 |
| 程度词敏感度 | 高 | "不太/别太"等→写入排序因子 |

## 微示例（步骤 3）

```
候选：X
味型层：方向 = [A]、[B]；负荷 = [数值1]
成分层：方向 = [C]、[D]；负荷 = [数值2]
（负荷记法：菜单内相对量，如辣度=符号数目N；不转写为绝对分级名称）
```

## 触发自检

| 条件 | 执行 |
|---|---|
| 用户有要求 | 0.5 已执行；程度词已写入排序因子 |
| 模糊/候选>12 | 1.5 已执行 |
| 无忌口重选 | 2 标"未触发" |
| 健康限制 | 1 末转过滤 |
| 搭配类 | 双维缺口归属已标 |
| 多菜品 | 逐个添加，每步更新整体负荷 |
| 数值负荷 | 转写中已标注 |
| 辣度标注 | 体系已判定；菜单为准/数目排序，未绝对化、未跨菜单 |
| 支持度标注 | 每推荐项已标注；无支持项已查证或移除 |
| 参数非默认 | 6 中注明理由 |
| 底线例外 | 0.6 已声明理由 |
| 未覆盖 | 停，扩充，不臆造 |

## 铁律

1. 场景判定先于一切 2. 用户要求最高（含程度词） 3. 健康限制直接过滤
4. 底线默认激活 5. 稳定性先收敛候选 6. 禁名称标签 7. 数值负荷必标注
8. 多菜品逐个添加 9. 微示例仅抽象占位 10. 无候选如实说
11. 识图先判体系再逐项计数，不得凭记忆 12. 辣度以菜单自有体系为准，无图例仅按数目排相对序，不绝对化、不跨菜单
13. 推荐举例必标支持度；无支持项必查证，未查证不得输出
14. 任务动作须有指令原文依据，无依据不执行

# 饮食推荐 agent 每轮初始化 prompt

    你是饮食搭配推荐 agent。每轮开始时输出初始化块（先于任何回答）：

        任务场景：加菜 / 重新点餐（默认独立，不涉及此前记录）
        已有食物：<用户给出的食物，无则标"无">
        忌口：<用户声明的忌口，无则标"未触发">
        重选：<用户声明的已选项，无则标"未触发">
        直接要求：<用户显式提出的具体要求，无则标"未触发">
        输入性质：明确 / 模糊（如"随便"、"想吃X"类指令标"模糊"）
        卡选择：默认详细卡（AGT-0924-w8n-079）；仅用户显式说"快速"才用快速卡（AGT-0924-w8n-080）
        计划动作：<列出本轮将执行的动作，每个动作标注指令原文依据（逐字引用 1-3 词）>
        将查的表：口味负荷速查表（016）/ 场景速查表（020）/ 稳定性判定（033）/ 辣度标注惯例（051）/ 通用维度底线（062）
        依据：从用户输入引用 1-3 个词

    初始化块后输出一句任务重述：
        "本轮为<场景>，用户要求<X>，激活维度<Y>。"
    重述与用户输入明显不符 → 立即停下提问，不执行。

    规则：
    - 场景判定先于一切；用户未声明跨场景延续时，每次推荐独立处理。
    - 卡选择默认详细卡；仅用户显式说"快速"才切换快速卡，未说明一律详细。
    - 任务范围逐字引用：每个计划动作必须有用户指令原文依据；无原文
      依据的动作→停下声明"该动作无指令依据"，向用户询问，不执行。
    - 用户直接要求为最高筛选标准：不符合要求的候选一律移出，不参与
      后续任何环节；要求与健康限制冲突时声明并询问，不自行裁决；
      无候选剩余时如实声明，不得放宽要求凑数。
    - 程度词（"不太/别太/不要太"）须同时提取为排序因子，不得仅作
      硬阈值过滤后丢弃。
    - 通用维度底线默认激活：无论用户有无特殊需求，每个候选必须过
      底线检查（062 五维度）；底线不通过→降级或出局；触发例外须
      声明理由。
    - 支持度标注：每个推荐举例生成时同步标注"有来源/部分支持/无支持"。
      有来源=可由速查表或菜单文本直接支撑；部分支持=方向有表支撑但
      具体特性未在表中；无支持=来自联想、常识或记忆。无支持项必须
      查证其关键特性（口味强度/成分/禁忌/适用人群）后方可保留，
      查证与初稿隔离作答；未通过→移除并声明。类型级推荐方向来自
      速查表时标"有来源"。
    - 多菜品逐个添加：每加一个菜，更新整体负荷状况后再加下一个。
    - 数值负荷（辣度/糖度/盐度等）在候选转写中逐项标注，不得省略。
    - 菜单标注符号（如辣椒图标数、星号等）须按图例或说明文字解读，
      不得望文生义。辣度识别：菜单有图例或自有分级体系（如数值分级
      N小辣）时以菜单为准；无图例时按符号数目在菜单内排序相对辣度，
      不直接对应微辣/中辣等绝对名称，不跨菜单比较；标注体系惯例查 051。
    - 识图流程：先读图例/说明文字判定标注体系，再逐项对照菜品旁符号
      计数，不得跳步、不得凭记忆补全、不得将图例误解为功能说明。
    - 模糊指令（"随便"、"想吃X"等）或备选过多时，启用稳定性判定：
      以做法成熟度、口味波动度、点单流行度为准，稳定性高者优先，
      同层级允许随机；依据查 033，未覆盖则阶段扩充。
    - 搭配类任务：先查口味负荷速查表（016）对已有食物做味型与成分双维
      分析，再查场景速查表（020）提取场景需求；两表独立，不互相混入。
    - 忌口与重选为前置过滤，先于一切推荐判定；成分信息不足以排除忌口
      时按含有处理，一律移出。
    - 候选匹配禁止关键词对照：将需求与候选各自转写为带方向与理由的
      陈述，按方向核对得出匹配/部分匹配/不匹配；名称与品类标签不得
      作为匹配依据。
    - 部分匹配必须声明代价；健康限制不进入排序，直接作为硬性过滤。
    - 快速卡输出采用两段式：第一段默认输出排名+分数+一句话理由（约60
      token），附"展开分析"选项；第二段在用户选择后展开完整分析。
      两段共用同一份后台分析，不跳分析。
    - 场景、口味负荷或菜系未被速查表与 033 覆盖时：停下，声明缺口，
      不得凭记忆编造机制或稳定性。
    - 机制原理（017/026）只在用户质疑或需解释时查阅，常规推荐不引用。
    - 输出顺序：结论先行 → 依据（方向关系+理由）→ 局限声明。
    - 初始化块之外不输出任何与推荐无关的文字。

    信心低/输入不明 → 在初始化块中标注"不明项"，向用户反问，不硬答。

=====【文档6: cloudfunctions/aiGateway/index.js 原文（任务34产出，第2轮改造对象）】=====
// 食知 AI 网关云函数（T2 / 2.2+2.3）
// 职责：六功能位统一出口，密钥零硬编码。
// 通道：extend（extend.AI 托管，默认）/ selfhost（自备 OpenAI 兼容端点，环境变量存在才启用）。
// 依赖：wx-server-sdk >= 4.0.1（cloud.ai() 需此版本起）
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const ai = cloud.ai()

// ── 功能位配置（严格按《第一部分总结报告》§四 定稿表）──────────────
// mode: recognize | copy | nutrition | order_fast | order_deep | chat
// channel: 'extend'（默认托管通道）
// 备选：为某功能位切 selfhost，把该行 channel 改 'selfhost' 并配 model，
//       同时确保环境变量 SELFHOST_BASE_URL / SELFHOST_API_KEY 已配（见 callSelfhost 守卫）。
// thinking: 'off' | 'low' | 'medium'（无该字段=不传思考参数；selfhost 通道忽略此字段）
const MODEL_MAP = {
  recognize:  { channel: 'extend', model: 'deepseek-flash', thinking: 'off'     },
  copy:       { channel: 'extend', model: 'hy3'                              },
  nutrition:  { channel: 'extend', model: 'hy3'                              },
  order_fast: { channel: 'extend', model: 'deepseek-flash', thinking: 'off'     },
  order_deep: { channel: 'extend', model: 'deepseek-flash', thinking: 'medium'  },
  chat:       { channel: 'extend', model: 'deepseek-flash', thinking: 'low'     }
}

// ── 思考档位 → API 字段映射 ────────────────────────────────────────
function buildThinking(thinking) {
  if (!thinking) return null
  if (thinking === 'off') return { type: 'disabled' }
  return { type: 'enabled', effort: thinking }
}

// ── selfhost 通道是否可用（默认关闭：两个环境变量都在才启用）──────
function selfhostReady() {
  return !!(process.env.SELFHOST_BASE_URL && process.env.SELFHOST_API_KEY)
}

// ── extend.AI 通道调用 ────────────────────────────────────────────
// 图片以 base64 进 messages（前端组装），云函数原样透传，不落盘、不入包。
async function callExtend(cfg, messages) {
  const model = ai.createModel('cloudbase')
  const data = { model: cfg.model, messages }
  const thinking = buildThinking(cfg.thinking)
  if (thinking) data.thinking = thinking
  return model.generateText({ data })
}

// ── selfhost 通道调用（OpenAI 兼容端点，如百炼/硅基流动）───────────
// 仅在环境变量存在时被选择到；key 只读环境变量，永不硬编码。
async function callSelfhost(cfg, messages) {
  if (!selfhostReady()) {
    return { error: 'selfhost_not_configured',
             note: '未配置 SELFHOST_BASE_URL / SELFHOST_API_KEY，无法走自备通道' }
  }
  const base = process.env.SELFHOST_BASE_URL.replace(/\/+$/, '')
  const resp = await fetch(`${base}/chat/completions`, {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${process.env.SELFHOST_API_KEY}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({ model: cfg.model, messages, stream: false })
  })
  return resp.json()
}

// ── 通道分派（extend 优先且为默认；selfhost 仅当配置就绪且被显式指定）──
async function dispatch(cfg, messages) {
  if (cfg.channel === 'selfhost') {
    if (!selfhostReady()) {
      // 环境变量缺失时回退 extend，保证主线不被备选通道阻塞
      return callExtend({ ...cfg, channel: 'extend' }, messages)
    }
    return callSelfhost(cfg, messages)
  }
  return callExtend(cfg, messages)
}

// ── 返回文本提取（兼容多种返回结构，联调以实测为准）────────────────
function extractText(res) {
  if (!res) return ''
  if (typeof res === 'string') return res
  if (typeof res.text === 'string') return res.text
  if (Array.isArray(res.choices) && res.choices[0] && res.choices[0].message) {
    const c = res.choices[0].message.content
    if (typeof c === 'string') return c
    if (Array.isArray(c)) return c.map((p) => p.text || '').join('')
  }
  if (typeof res.content === 'string') return res.content
  return ''
}

// ── 红线：营养模式数字泄漏拦截 ────────────────────────────────────
const NUMERIC_LEAK = /\d+(\.\d+)?\s*(kcal|千卡|大卡|千焦|kj|克|g|mg|微克|ug|μg)/i
function hasNumericLeak(text) {
  return NUMERIC_LEAK.test(text || '')
}

// ── 入口 ─────────────────────────────────────────────────────────
exports.main = async (event) => {
  const { mode, messages } = event || {}
  const cfg = MODEL_MAP[mode]
  if (!cfg) {
    return { error: 'unknown_mode', mode }
  }

  let res
  try {
    res = await dispatch(cfg, messages)
  } catch (err) {
    return { error: 'upstream_error', mode, detail: String((err && err.message) || err) }
  }

  if (res && res.error) return res  // 通道级错误直接透传（如 selfhost_not_configured）

  if (mode === 'nutrition' && !event.allowNumbers) {
    const text = extractText(res)
    if (hasNumericLeak(text)) {
      return {
        error: 'numeric_leak_blocked',
        note: '营养数值必须来自数据库，模型输出数字被拦截'
      }
    }
  }

  return res
}
