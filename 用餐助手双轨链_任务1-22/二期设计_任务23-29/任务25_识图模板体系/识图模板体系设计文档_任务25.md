## 一、设计总原则：分层组装 prompt

把一次调用拆成"固定层 + 可变层"，模板负责固定层与任务骨架，两类文字只填充可变层：

```
L1 系统角色     固定：食知助手身份/合规/不臆造数值（全局共用）
L2 任务模板     固定：目标 + 步骤 + 输出格式 + 硬约束（随模板切换）
L3 上下文事实   ← 提示文字注入（地域/场景/人数/份量/受众）
L4 图片         图像输入
L5 用户问题     ← 问题注入（定制查询/追加意图）
L6 输出约束     固定：置信度标注、确认流程、数据来源标注
```

## 二、两类文字的分工与拼接

| 维度 | 提示文字 | 问题 |
|---|---|---|
| 本质 | **事实/上下文注入**（先验） | **查询/意图指令** |
| 作用对象 | 影响"看什么、按什么前提看" | 影响"输出什么内容" |
| 优先级 | 高（**可含硬约束**：过敏原、素食、份量事实） | 中（可覆盖模板默认意图） |
| 位置 | **图片之前**（带着预期去识别） | **图片之后**（避免干扰识别） |
| 缺失时 | 不注入，仅凭图片判断 | 走模板默认意图 |

**冲突裁决（优先级从高到低）：**
1. **硬约束优先**：提示文字/用户档案中的过敏原、素食、人数份量，任何情况不得推翻。
2. **任务意图**：用户问题 > 模板默认意图（识图模板下问"能配什么饮品"→ 转搭配推荐）。
3. **输出格式**：由 L2 模板骨架决定；用户问题只能在模板允许范围内调整，不得破坏数值来源、置信度等强约束。

## 三、三个模板的 prompt 骨架

### 模板 A · 识图（识别菜品）
```
[角色] 你是食物识别助手。
[任务] 识别图片中的菜品，输出名称与份量估计。
[背景信息(如有)] {提示文字}        # "在四川吃的""大概两人份"
[图片]
[用户问题(如有)] {问题}            # "这是哪道川菜"
[步骤] 1.结合背景与图片逐道识别；2.输出 菜名/置信度/份量估计/判断依据
[约束] 低置信必须标注，不得编造菜名；识别结果交用户确认后方可使用
[输出] 结构化列表(菜名, 置信度, 份量, 依据)
[默认] 无问题→只做识别；无提示文字→纯图识别
```

### 模板 B · 设计文案（识别后生成分享文案）
```
[角色] 你是社交分享文案助手。
[依赖] 先取模板A识别结果；风格标签:文艺/搞笑/专业
[背景信息(如有)] {提示文字}        # "发朋友圈""给朋友看"
[用户问题(如有)] {问题}            # "写文艺一点"
[步骤] 1.按风格标签生成；2.附话题标签；支持"再生成一版"
[约束] 不夸大功效、不虚构食材；风格以标签为准，问题微调语气
[输出] 文案正文 + 话题标签
[默认] 无问题→默认/上次风格；无风格标签→先请用户选
```

### 模板 C · 营养/成分分析（识别后出营养表）
```
[角色] 你是营养分析助手。
[依赖] 先取模板A识别结果(菜品+份量)；用户身体数据与每日目标(如有)
[背景信息(如有)] {提示文字}        # "大概两人份"→份量折算
[用户问题(如有)] {问题}            # "这餐蛋白质够吗"
[步骤] 1.调营养数据库按份量计算当餐摄入；2.与每日目标对比；3.模型仅将数值翻译成建议
[约束] 所有数值必须来自数据库，禁止模型生成或估算；份量不明须标假设并请用户确认
[输出] 营养表(热量/蛋白质/脂肪/碳水/钠…) + 建议
[默认] 无问题→标准营养表；无身体数据→只出表不做个性化对比
```

## 四、用户无文字输入时的默认行为

| 输入情况 | 识图 | 文案 | 营养分析 |
|---|---|---|---|
| 问题为空 | 执行识别默认意图 | 按默认/上次风格生成 | 输出标准营养表 |
| 提示文字为空 | 仅凭图片识别，低置信标注 | 识别结果+默认风格 | 份量按标准份/图片估计并标假设 |
| 两者都空 | 走模板默认流程，结果仍需确认 | 同上 | 同上并提示确认份量 |

**统一兜底（L1/L6常驻）**：先识别→用户确认→再下游；数值必标来源，不确定必标置信度/假设；稳定偏好（如"我吃素"）可提示存为长期偏好，与个性化储存联动。

## 五、模板与自由提问并行

自由提问不套模板骨架，但复用同一分层（L3背景、L5主指令，L2换开放式，L6不变）。切换：命中模板→走骨架；直接提问→自由提问；模板内明显偏题→以问题意图为准，可结构化则结构化，否则转自由提问 lane。

## 六、模板 vs 自由对话：速度与表现（机制分析）

1. **省轮次=省图像编码**：模板把意图声明前置（选模板=声明意图，风格走默认，身体数据本地读），省掉意图澄清轮1-2个+参数补全轮。更关键的是多模态模型每轮都要重新token化图片（一张图数百至上千token），自由对话跨轮传图每轮重付prefill；模板把识别→文案→营养收进单次调用或一次确认闭环，**图像只编码一次**——这是延迟下降主来源，非单纯RTT。
2. **prompt长度"短且恒定"**：L1/L2/L6固定前缀可命中KV/prompt缓存，prefill只算可变尾巴几十token；同时省掉自然语言意图解析的额外推理。一次性任务模板可能比5字提问略长，但换掉意图解析+追问轮，总成本仍降。净值取决于复用频率。
3. **结构化输出消灭抽取轮+修复轮**：自由文本前端只能正则/NLP抽取，措辞变就崩，崩了要修复轮或抽取轮。结构化直接JSON.parse；置信度数值字段让前端`<阈值`自动路由三分档UI；字段闭合可先渲染；schema约束解码天然合法。链条：结构化→直接解析→消灭抽取/修复轮→端到端少一次往返。**最确定的性能收益**。
4. **模板限制发挥：强制schema诱发越界幻觉**。模板A契约写死"输出菜品列表"，用户拍的不是食物时，空列表=违约，模型被压着编菜名（OOD典型失效）。**必须内置逃生机制**：schema最前面加路由门字段 `is_food/scene_type`，规则"若非食物输出is_food=false并说明，不进菜品列表"，让schema允许负路径；低置信转手动为第二逃生口。第二类：固定形态装不下新意图→L5问题通道允许范围内覆盖，超出溢出到自由提问lane。第三类：文案趋同→风格标签受控变化+再生成靠采样温度恢复多样性。

**收敛**：模板用"前置意图+固定前缀可缓存+结构化免解析"换速度，代价是把OOD处理责任从模型转嫁到schema设计——`is_food`路由门字段不是可选项，是模板成立的前提。

## 七、模型选型：双模型分工（按模态切，非按结构化切）

**结论：双模型分工更优——但切分轴不是"结构化vs自由对话"，而是"模态×难度来源"。**

1. **纠正切分轴**：结构化≠可降配。识图难度在**感知**（图→菜品身份），输出JSON只是换格式，感知难度一分未减——"结构化就用小VL模型"在识图上不成立。文案/营养建议难度在**生成**且被骨架/风格/DB数值三重约束，可降配。**结构化降低的是生成/指令遵循难度，不降低感知难度。**
2. **核心机制**：识图结构化输出（菜名/份量/置信度）本身是纯文本，下游文案、营养建议不再需要图片——"必须多模态"只剩识图+含图自由对话，切分线正好落在模态交界。图片只在感知层编码一次，下游不再付图像prefill。**结构化的回报率：让双模型交接无需重传图。**
3. **定档表**：

| 任务 | 难度来源 | 模态 | 档位 |
|---|---|---|---|
| 识图A / 含图自由对话 | 感知 | 多模态 | **强VL（不降配）** |
| 纯文本自由对话 | 通用推理 | 文本 | 强文本 |
| 文案B | 生成(受约束) | 文本 | 中/轻量可试 |
| 营养建议C | 翻译(数值固定) | 文本 | 轻量即可 |
| 搭配推荐 | 规则为主 | — | 规则引擎 |

4. **调度与成本**：路由零成本（选模板=已知路由）；交接成本被结构化抵消；固定前缀双模型各自缓存；双冷启动是唯一实打实新增成本（预热/常驻缓解）；**文案"再生成"高频循环是自反馈陷阱**——小模型质量差→用户反复再生成→调用量上涨吃掉省的成本，降配前必须先验质量。
5. **选型**：感知/含图对话=强多模态单一模型。中文菜系+菜单OCR敏感→Qwen3-VL/GLM-5V/Kimi K3优先；极致速度+结构化稳定→Gemini 3.x Flash。生成/翻译=轻量文本模型，可与感知同族复用工具链。**退回单模型判据：降配省下的"单次成本×下游调用量"是否大于"运维+双冷启动+质量回退"；接近时选单模型。**

### 第2轮原文（速度影响机制分析）

> 纯分析任务,在能力内,直接作答。以下每条都给到"为什么"的机制,不空谈。
>
> ## 1. 省掉哪些轮次(机制:消除意图澄清 + 避免图像重复编码)
>
> 自由对话的轮次来源有两处**结构性浪费**：
> - **意图澄清轮**:用户传图 + "帮我看看" → 模型不知道要识别还是要文案还是要营养 → 追问"你想做什么" → 用户答 → 才进入正题。这一来一回至少 1–2 轮。
> - **参数补全轮**:文案要问风格,营养要问身体数据/份量。自由对话里这些只能当场问。
>
> 模板把这两类信息**前置声明**:选模板 = 声明意图;风格走"默认/上次使用";身体数据从【上下文记录】第5节的本地存储直接读。**省掉 1–3 轮**。
>
> 关键机制在于:**比轮次数字更贵的是图像的重复编码**。多模态模型每一轮都要把图片重新 token 化(prefill),一张图动辄数百至上千 token。自由对话往往把图留在历史里跨多轮传递 → 每轮重付一次图像 prefill。模板把"识别→文案→营养"尽量收进**单次调用**或"先出识别结果交确认"的一次闭环,图像只编码一次。所以省轮次≈省图像编码次数,这是延迟下降的主要来源,而非单纯的 RTT。
>
> ## 2. prompt 长度变化(机制:固定前缀可缓存 + 消除自然语言意图解析)
>
> 模板的结构是 `L1+L2+L6 固定 + L3/L5 可变`,这带来两个反向机制：
> - **降**:固定层是常量前缀 → 可命中 **prompt/KV 缓存**,prefill 只算可变尾巴那几十个 token;同时自由对话里"帮我看看这是什么菜然后写个朋友圈文案"这类自然语言,模型要先**解析意图**(额外推理 token),模板直接省掉这步。
> - **升**:对超简单一次性任务,模板骨架**可能比用户一句 5 字提问更长**;结构化输出的 key/标签也增加输出 token。
>
> 净值取决于复用频率:同一模板反复用 → 固定前缀被缓存摊薄,净变短;一次性即用即走 → 可能略长,但换掉了意图解析和追问轮,总成本仍降。
>
> **结论**:prompt 长度不是单纯变短,而是**从"长且随轮次增长"变成"短且恒定"**。常量可缓存、尾巴很小,这才是速度稳定的机制来源。
>
> ## 3. 结构化输出对前端解析(机制:消除"抽取轮"与"修复轮")
>
> 自由文本 → 前端要拿菜名/置信度/份量,只能靠正则或 NLP 抽取 → 措辞一变(换行、同义替换)就崩 → 崩了就得**再发一次请求让模型按格式重出**(修复轮),或**单独调一次做 JSON 抽取**(抽取轮)。这两轮既费时又费钱。
>
> 结构化(字段/JSON)直接 `JSON.parse`,带来三层好处：
> - **分档 UI 可编程**:置信度是数值字段 → 前端直接 `<阈值` 比较,自动路由到"高置信直显 / 中置信请纠正 / 低置信转手动"三条界面(对应【上下文记录】第1节),无需模型再判断。
> - **可校验、可部分渲染**:字段闭合即可先渲染菜名,不必等全文;`is_food`、份量等字段可直接喂给下游规则引擎。
> - **参数化解码**:若运行时支持 schema 约束解码,输出天然合法,连"请你按格式输出"的修复轮都省了。
>
> 机制链条:**结构化 → 可直接解析 → 消灭抽取轮+修复轮 → 端到端少一次往返**。这是模板相对自由对话最确定的性能收益。
>
> ## 4. 模板会不会限制发挥(机制:强制 schema 诱发越界幻觉)
>
> **会,且边界情况明确。** 机制是"**强制输出契约 + 越界输入**"的冲突：
>
> 模板 A 的 L2 写死"识别菜品",L6 要求必须给出菜品列表。模型的解码被这个先验**拉向"这里有食物、去命名它"**。当用户拍的不是食物时：
> - 自由对话里,"这不是食物/我看不出"是自然的**退路**;
> - 模板里这条路被 schema 堵死——因为契约要求"必须输出列表",空列表等于违约,模型被压着**编一道菜**(越界幻觉)。这是受限解码下 OOD 输入的典型失效。
>
> **必须内置的逃生机制**(否则模板的稳定性优势会在这里翻车)：
> - **在 schema 最前面加路由门字段**,如 `is_food / scene_type`,并配规则:"若图片非食物,输出 `is_food=false` 并说明,**不进入菜品列表**"。把路由决策放在任务字段**之前**,让 schema 允许负路径存在。
> - 承接【上下文记录】第1节的**低置信转手动输入**,作为第二道逃生口。
>
> **第二类限制**:模板固定输出形态 → 装不下新意图。机制上的缓解是——上一轮设计的 `L5 问题` 通道本身允许意图覆盖(模板允许范围内),超出范围则**溢出到并行的自由提问 lane**。所以表达力损失被限制在结构化路径内,不会全局封死。
>
> **第三类**:文案模板的固定骨架可能让文案趋同。缓解靠风格标签给受控变化 + "再生成一版"靠采样温度恢复多样性。
>
> **一句话收敛**:模板用"前置意图 + 固定前缀可缓存 + 结构化免解析"换速度,代价是**把 OOD 处理的责任从模型转嫁到 schema 设计**——所以 `is_food` 这类路由门字段不是可选项,是模板能成立的前提;而自由提问 lane 作为溢出口,负责兜住模板装不下的表达需求。

### 第3轮原文（模型选型）

> 纯选型分析,在能力内,直接作答。每条给机制。
>
> **结论先行:双模型分工更优——但切分轴不是题目预设的"结构化 vs 自由对话",而是"模态 × 难度来源"。**
>
> ## 1. 先纠正切分轴:结构化 ≠ 可降配
>
> 决定模型大小的不是输出格式,而是**任务难度卡在哪一段**：
> - **识图(模板A)**:难度在**感知**(图→菜品身份),那是多模态编码器的活。把它输出成 JSON 只是换了输出格式,**上游感知难度一分未减**。所以"因为结构化就用小 VL 模型"这条推理在识图上不成立——结构化还在,识别准确率却掉了。这是本问题最容易踩的坑。
> - **文案 / 营养建议**:难度在**生成**,且被模板骨架、风格标签、DB 数值三重约束,输入又是已知的结构化文本。难度大降 → 确实可降配。
>
> 一句话机制:**结构化降低的是"生成/指令遵循"难度,不降低"感知"难度。** 能不能用小模型,取决于任务卡在哪一段,而不是输出长什么样。
>
> ## 2. 关键机制:结构化输出把"多模态边界"和"任务边界"对齐了
>
> 这是整个方案能立住的核心。识图输出的结构化结果(菜名/份量/置信度)本身就是**纯文本**。它一旦产出：
> - 下游文案(【上下文记录】第2节:输入=菜品信息+风格标签)、营养建议(第3节:数值来自DB,模型只翻译)**都不再需要图片**;
> - 于是"必须多模态"的任务只剩识图和含图自由对话,其余全是纯文本。
>
> **结果:双模型的切分线正好落在模态交界上,而不是人为切在"结构化/自由"之间。** 由此得到一个直接省成本的机制——图片只在感知层编码一次,下游文本任务不再重复付昂贵的图像 prefill。**这正是"结构化输出"回报率的来源:它不只是让前端好解析,更让双模型交接无需重传图。**
>
> ## 3. 按难度来源 × 模态分层定档
>
> | 任务 | 难度来源 | 模态 | 模型档位 |
> |---|---|---|---|
> | 识图 A | 感知 | 多模态 | **强 VL(不降配)** |
> | 自由对话(含图) | 感知+通用 | 多模态 | 强 VL |
> | 自由对话(纯文本) | 通用推理 | 文本 | 强文本 |
> | 文案 B | 生成(受约束) | 文本 | 中/轻量可试 |
> | 营养建议 C | 翻译(数值固定) | 文本 | 轻量即可 |
> | 搭配推荐 | 规则为主 | — | 规则引擎,弱模型/不用 |
>
> ## 4. 调度与成本:机制清单
>
> - **路由零成本**:用户**选中模板 = 已知路由**,无需模型判断走哪条;仅自由对话需要路由,且可由"有没有命中模板"直接决定。省掉一次意图判断推理。
> - **交接成本被结构化抵消**:上表成立的前提是 A 输出结构化。若 A 吐自由文本,下游 B/C 就得重传图或另做抽取——**所以结构化的价值必须兑现为"让文本任务免图",否则双模型的省成本逻辑不成立**。
> - **KV/prompt 缓存**:固定前缀(角色+模板骨架)可缓存;双模型各自缓存,单次成本可控。
> - **冷启动:双模型唯一实打实的新增成本。** 用预热/常驻缓解。
> - **文案"再生成一版"是高频循环**:每次点都发一次请求,循环频次可能反超识图。机制上它适合放轻量文本模型;但有个**自反馈陷阱**——若小模型文案质量差,用户会反复"再生成",调用量反而上涨,省下的单次成本被吃掉。**所以文案降配前必须先验质量,否则越省越贵。**
>
> ## 5. 结论与具体选型
>
> **推荐:双模型分工(按模态切),同时保留退化为单模型的开关。**
> - **感知 / 含图对话**:强多模态,单一模型。中文菜系 + 菜单 OCR(【上下文记录】第1节)对中文能力敏感 → **Qwen3-VL / GLM-5V / Kimi K3** 优先;极致速度 + 结构化稳定性优先 → **Gemini 3.x Flash**。
> - **生成 / 翻译(纯文本)**:轻量文本模型,可与感知模型**同族**以复用工具链、共用 KV 缓存格式。
> - **营养数值**:不进模型,DB 直供,模型只做"数值→建议"的翻译(第3节),这点与选型无关,是硬约束。
>
> **何时退回单模型通吃:**
> - 下游调用量小,或轻量文本模型文案质量不足以压低"再生成"循环时,单强多模态(Gemini 3.x Flash 或 Qwen3-VL)更划算——**运维简单、一致性高、无双冷启动**。
> - 判据一句话:**降配省下的"单次成本 × 下游调用量",是否大于新增的"运维 + 双冷启动 + 质量回退"成本。** 两边接近时,选单模型。
>
> **收敛**:双模型是对的,但必须按"模态边界=任务边界"切,不能按"结构化 vs 自由"切——后者会把感知任务误降配;而这一步之所以成立,恰恰依赖识图输出结构化数据,让下游文本任务彻底摆脱图片。
