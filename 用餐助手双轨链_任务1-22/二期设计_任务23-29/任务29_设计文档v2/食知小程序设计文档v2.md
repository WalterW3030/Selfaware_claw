## 1. 定位与功能总览

### 1.1 全局设计基线与约束(去重后唯一出处)

食知小程序为**饮食识别 + 点餐 + 营养健康管理**一体的工具。全部五份设计共同遵循以下"轨A"决策,后文一律引用不再复述:

1. **本地优先**:数据先落小程序 Storage,用户授权后同步云端,可导出/删除。
2. **用户确认后使用**:识别/外部数据结果一律交用户确认方进入正式记录(确认门禁)。
3. **营养数值来自数据库,不由模型生成**:数值由权威食物库 + 份量比例公式/规则引擎产出,模型只负责"把数值翻译成建议"。
4. **规则引擎为主**:过滤、打分权重、缺口计算、运动消耗换算均为规则引擎,模型不拍脑袋出数字。
5. **个性化信息储存**:身体数据、过敏原、饮食目标、口味偏好标签沿用轨A既有"个性化信息储存"模块(任务5/15),作为各功能的约束源与画像源。

### 1.2 功能模块总览

| 模块 | 对应产出 | 一句话职责 | 数据角色 |
|---|---|---|---|
| **数据层** | 任务24 | 五表分层:档案=可复用知识、记录=唯一事实+快照、汇总=健康只读入口、审计=不可变留痕、用户=约束源 | **地基,冲突裁决基准** |
| **识图模板体系** | 任务25 | 两类文字分工 + 三分层骨架(识图/文案/营养分析)+ 模板与自由提问并行 + 模型选型 | 数据入口与 prompt 组装 |
| **点餐助手** | 任务26 | 菜单识别(结构化抽取)→ 推荐排序(口味/营养两分数加权)→ 搭配推荐(已点约束+预设+路由) | 消费数据层并写入记录 |
| **健康管理** | 任务27 | 个人健康数据体系 + 日/周/月三周期检测 + 趋势/缺口分析 + 建议生成 | 周期聚合与建议输出 |
| **外部接入** | 任务28 | 外部数据源可行性查证 + 能进什么/怎么进 + 优先级 + 与数据层对接 | 补充数据来源 |

### 1.3 模块间数据流总览

```
【外部接入】步数/体重等sample(带source) ┐
                                        ├→【数据层】diet_record / sample 存储
【识图模板】识别→确认→入库 ───────────┘            ↓ 事件驱动增量
【点餐助手】菜单识别→点单→搭配 ──写──→          daily_nutrition_summary(只读入口)
                                                     ↓ 按周期聚合
【健康管理】日/周/月周期分析 ←── 读汇总/事实 ──→ 建议生成(规则引擎出结论,模型翻译)
                                                     ↓ 月周期重校准 target_k
                                              反向改写点餐助手营养分输入(闭环)
```

## 2. 数据层(任务24,冲突裁决基准)

### 2.1 总体架构:五表分层

| 表 | 层级 | 主键 | 核心字段 | 语义 |
|---|---|---|---|---|
| `dish_profile` | 知识库(可复用) | `dish_id` | dish_name, aliases[], base_portion_g, calories/protein/fat/carbs/fiber/sodium, allergen_tags[], is_vegetarian, confidence, source, user_corrected, use_count, last_used_at, created_at, updated_at | 去重后的**菜品营养基准**(菜名归一,份量做系数) |
| `diet_record` | 事实层(逐餐) | `record_id` | user_id, dish_id→dish_profile, eaten_at, meal_type, actual_portion, snapshot_nutrition, nutrition_source_ref, source(识别/手动), status(有效/被取代), created_at | **每次进食事实**,唯一事实源,带营养快照 |
| `daily_nutrition_summary` | 汇总层(健康入口) | (user_id, date) | total_*, by_meal, manual_entries[], target_*快照, completeness, updated_at, version | 当日累计,健康侧**只读**接口 |
| `nutrition_audit_log` | 留痕层 | `log_id` | user_id, record_id, action(add/modify/delete/undo), before, after, reason, operator, created_at | **不可变修正日志**,不改写事实 |
| (复用)`user_profile` | 用户 | user_id | 身体数据、过敏原、饮食目标、口味偏好标签 | 沿用"个性化信息储存" |

**表间关系**(理由均随附):
- `dish_profile` **1:N** `diet_record`——一条档案被多次进食引用;档案唯一,历史各自独立。
- `diet_record` **N:1** `daily_nutrition_summary`——多餐聚合进当日汇总。
- `diet_record` **1:N** `nutrition_audit_log`——一条记录多次修改留多条日志。
- `user_profile` **1:N** 上述各表——过敏原/素食是搭配推荐的硬约束来源。
- **快照关系**:`diet_record.snapshot_nutrition` 冻结"当次计算值",与 `dish_profile` 基准解耦;**档案日后修正不追溯改写历史**(关键约束)。

### 2.2 餐品记录功能

**数据结构:两表拆分**
拆成去重后的「餐品营养档案」(`dish_profile`,可复用知识)与「饮食记录表」(`diet_record`,每次进食事实),一对多。
- 关键约束1:`diet_record` 通过 `dish_id` 引用档案,复用营养知识,避免重复分析。
- 关键约束2:**必须存快照**,理由——档案日后被修正,历史记录不应被"追溯改写",快照保证历史查询稳定。
- 关键约束3:本地优先,先落 Storage,授权后同步云端,可导出/删除。
- 关键约束4:营养数值一律来自数据库 + 份量比例公式,轻量语言模型只翻译成建议。

**触发入库时机:确认后正式入库门禁**
1. **识别→确认→入库(主路径)**:置信度分档处理(高直接展示、中请用户纠正、低转手动);**用户确认瞬间**双写 `diet_record` + 必要时新建/更新 `dish_profile`。
2. **高置信可"预暂存"**:先写档案为候选态,用户确认后转正式,避免污染知识库。
3. **手动输入直接入库**:确认即入库。
4. **"再生成"不触发入库**:文案重生成属展示层,与记录无关。
- 原则:**未经用户确认不入正式库**。

**调用场景**
1. 重复点餐快速带出:匹配档案按 dish_name/aliases,直接读营养跳过重识别,仅确认份量后按比例算。
2. 历史查询:按时间/meal_type/菜名检索 `diet_record`,用 `snapshot_nutrition` 不改动。
3. 搭配推荐复用:直接读档案 `allergen_tags`/`is_vegetarian` 硬约束过滤,无需重算。
4. 输入联想:按 `use_count` 排序,高频优先补全。
5. 周期性归纳:多次用餐评价归纳生成口味偏好标签,反哺推荐。

**去重策略:基础菜品 + 份量系数两层模型**
1. 菜名归一化:清洗别名、OCR纠错、同义词归并("番茄炒蛋/西红柿炒鸡蛋"合并为一个档案)。
2. 份量不拆档案,拆系数:同菜不同份量不新建档案,用 `base_portion_g` 与比例公式动态换算。
3. 何时新建档案:归一后菜名不同→新建;份量差异导致营养**本质不同**(如大小份来自数据库不同条目而非单纯比例)→可建带 portion 维度的独立档案。
4. 冲突合并:按比例可换算→合并,更新 use_count/last_used_at;营养数值冲突→以 `user_corrected=true` 版本为准。
5. 份量差异归属:记在 `diet_record.actual_portion`,不改档案,保证档案唯一、历史独立。

### 2.3 营养-健康互通

**数据管道:逐餐落库 + 事件驱动每日汇总(双层)**
- 层1 逐餐事实(源):`diet_record` 每确认一餐即写入,带 `snapshot_nutrition`,**唯一事实源**。
- 层2 每日汇总(健康入口):`daily_nutrition_summary`(复合主键 user_id+date)。

数据流向(事件驱动,非定时全量):
```
识别/确认 → diet_record 写入 →(同一事务/本地事件)→ 增量更新 daily_nutrition_summary
          →(变更事件)→ 健康模块按 version 增量同步(只读)
```
关键设计点:
- 写入走同一写路径,餐品入库顺带增量更新当日汇总,避免两处不一致。
- 增量而非全量重算:加一餐 = 加该餐营养值。
- 删除/修改 = 反算(先减旧值再加新值)。
- 汇总对健康侧是**只读接口**:健康模块不直接改 `diet_record`,保持单一写入者。
- 手动补录同权:标 `source=manual`,同等计入,可单独统计占比。

**手动添加/修改:防数量级手滑**
1. 单位与量级分离输入:数值 + 单位下拉(g/ml/份/个/碗);份量优先选常用档位,减少自由输入。
2. 量级护栏(硬校验):按营养项设合理区间(单餐热量50–3000 kcal、单餐钠1–5000 mg、单菜品蛋白质0–200 g);超区间**不拒绝而拦截提示**("您填的3000g米饭,是不是300g?"),给"确认原值/改为建议值"两选;明显数量级错误(10倍/100倍)且与历史不符→默认高亮建议值。
3. 跨字段一致性:三大营养素换算热量 vs 填入热量偏差超±20%提示;当日已录总量 vs 每日目标超倍数提示。
4. 交互防误触:修改先展示 diff 再确认;高风险修改(已同步云端)二次确认;支持短时撤销。
5. 不做静默纠正:系统只提示建议,最终值以用户确认为准。

**修改历史:留痕但不改写事实**
不可变事实 + 修正记录双写,不原地覆盖。
- `diet_record` 不物理覆盖:保留原记录,新增修正记录(或标原记录 `status=superseded`);汇总按最新有效版本计算,历史可取任一版本。
- 新增 `nutrition_audit_log`(字段见2.1)。
- 汇总层:`daily_nutrition_summary` 用 version 递增,健康侧可按版本对账;跨日修改触发对应日期汇总重算并入审计日志。
- 三条原则:**可追溯**(每次变化有 before/after)、**不追溯改写**(档案修正只影响未来)、**用户可查可删**(本地优先,删除即删审计记录)。

### 2.4 读写路径

```
① 识别  用户上传照片 → 视觉模型出菜名+置信度(高/中/低分档)
            ↓
② 分析  命中 dish_profile? ──是──→ 读基准营养,按 actual_portion 比例算
            │                          │
            └──否──→ 查营养数据库 → 建候选档案 ←┘
            ↓
③ 记录  用户确认 → 同一写路径双写:·新建/更新 dish_profile ·写 diet_record(事实+快照)
            ↓(本地事件,同事务)
④ 健康  增量更新 daily_nutrition_summary(加该餐值)
            ↓(变更事件,按 version)
       健康数据模块只读拉取(对比 target_* 出建议)
```
写路径三原则:**单一写入者**(只有"记录"环节写事实表,健康模块绝不直接改)、**同路径更新汇总**(写餐即增量更汇总)、**读路径分层**(展示/健康读汇总,历史查询读事实+快照,搭配推荐读档案标签)。

### 2.5 一致性风险清单(10条,一句一个)

1. **档案修正 vs 历史快照**:改 `dish_profile` 只影响未来,历史 `snapshot_nutrition` 不动。
2. **多端并发改同一餐**:后写覆盖先写,靠 updated_at/版本号判胜负,败方入审计日志。
3. **改餐未更汇总**:改了 `diet_record` 漏触发汇总重算则脱节,必须走同一写路径。
4. **跨日补录**:补昨天/改前天触发对应日期汇总重算,只重算今日则历史日错。
5. **手动与识别来源冲突**:同餐两记汇总双计,靠确认门禁 + 手动条目单列去重。
6. **档案去重误合并**:别名归一误合并牵连所有引用,合并需可回滚。
7. **删档 vs 引用记录**:删 `dish_profile` 时仍有引用,应软删或降级为"仅存快照",防外键悬空。
8. **云端同步冲突**:离线本地改与云端改对撞,以用户确认/最新时间戳为准并保留双方入审计。
9. **汇总 version 漂移**:健康侧按 version 增量拉取,漏版本则增量算错,需支持整日重拉兜底。
10. **审计与事实不一致**:事实改了审计没写(或反之)破坏可追溯性,修改必须"改事实+写日志"原子化。

**解法收敛**:确认门禁 + 版本/时间戳裁决 + 审计留痕 + 可回滚。

## 3. 识图模板体系(任务25)

### 3.1 设计总原则:分层组装 prompt

把一次调用拆成"固定层 + 可变层",模板负责固定层与任务骨架,两类文字只填充可变层:
```
L1 系统角色     固定:食知助手身份/合规/不臆造数值(全局共用)
L2 任务模板     固定:目标 + 步骤 + 输出格式 + 硬约束(随模板切换)
L3 上下文事实   ← 提示文字注入(地域/场景/人数/份量/受众)
L4 图片         图像输入
L5 用户问题     ← 问题注入(定制查询/追加意图)
L6 输出约束     固定:置信度标注、确认流程、数据来源标注
```

### 3.2 两类文字的分工与拼接

| 维度 | 提示文字 | 问题 |
|---|---|---|
| 本质 | **事实/上下文注入**(先验) | **查询/意图指令** |
| 作用对象 | 影响"看什么、按什么前提看" | 影响"输出什么内容" |
| 优先级 | 高(**可含硬约束**:过敏原、素食、份量事实) | 中(可覆盖模板默认意图) |
| 位置 | **图片之前**(带着预期识别) | **图片之后**(避免干扰识别) |
| 缺失时 | 不注入,仅凭图片判断 | 走模板默认意图 |

**冲突裁决(优先级从高到低):**
1. **硬约束优先**:提示文字/用户档案中的过敏原、素食、人数份量,任何情况不得推翻。
2. **任务意图**:用户问题 > 模板默认意图。
3. **输出格式**:由 L2 模板骨架决定,用户问题只能在模板允许范围内调整,不得破坏数值来源、置信度等强约束。

### 3.3 三个模板的 prompt 骨架

**模板 A · 识图(识别菜品)**
```
[角色] 你是食物识别助手。
[任务] 识别图片中的菜品,输出名称与份量估计。
[背景信息(如有)] {提示文字}        # "在四川吃的""大概两人份"
[图片]
[用户问题(如有)] {问题}            # "这是哪道川菜"
[步骤] 1.结合背景与图片逐道识别;2.输出 菜名/置信度/份量估计/判断依据
[约束] 低置信必须标注,不得编造菜名;识别结果交用户确认后方可使用
[输出] 结构化列表(菜名, 置信度, 份量, 依据)
[默认] 无问题→只做识别;无提示文字→纯图识别
```

**模板 B · 设计文案(识别后生成分享文案)**
```
[角色] 你是社交分享文案助手。
[依赖] 先取模板A识别结果;风格标签:文艺/搞笑/专业
[背景信息(如有)] {提示文字}        # "发朋友圈""给朋友看"
[用户问题(如有)] {问题}            # "写文艺一点"
[步骤] 1.按风格标签生成;2.附话题标签;支持"再生成一版"
[约束] 不夸大功效、不虚构食材;风格以标签为准,问题微调语气
[输出] 文案正文 + 话题标签
[默认] 无问题→默认/上次风格;无风格标签→先请用户选
```

**模板 C · 营养/成分分析(识别后出营养表)**
```
[角色] 你是营养分析助手。
[依赖] 先取模板A识别结果(菜品+份量);用户身体数据与每日目标(如有)
[背景信息(如有)] {提示文字}        # "大概两人份"→份量折算
[用户问题(如有)] {问题}            # "这餐蛋白质够吗"
[步骤] 1.调营养数据库按份量计算当餐摄入;2.与每日目标对比;3.模型仅将数值翻译成建议
[约束] 所有数值必须来自数据库,禁止模型生成或估算;份量不明须标假设并请用户确认
[输出] 营养表(热量/蛋白质/脂肪/碳水/钠…) + 建议
[默认] 无问题→标准营养表;无身体数据→只出表不做个性化对比
```

### 3.4 用户无文字输入时的默认行为

| 输入情况 | 识图 | 文案 | 营养分析 |
|---|---|---|---|
| 问题为空 | 执行识别默认意图 | 按默认/上次风格生成 | 输出标准营养表 |
| 提示文字为空 | 仅凭图片识别,低置信标注 | 识别结果+默认风格 | 份量按标准份/图片估计并标假设 |
| 两者都空 | 走模板默认流程,结果仍需确认 | 同上 | 同上并提示确认份量 |

**统一兜底(L1/L6常驻)**:先识别→用户确认→再下游;数值必标来源,不确定必标置信度/假设;稳定偏好("我吃素")可提示存为长期偏好,与个性化储存联动。

### 3.5 模板与自由提问并行
自由提问不套模板骨架,但复用同一分层(L3背景、L5主指令,L2换开放式,L6不变)。切换:命中模板→走骨架;直接提问→自由提问;模板内明显偏题→以问题意图为准,可结构化则结构化,否则转自由提问 lane。

### 3.6 速度影响(4条机制)

1. **省轮次=省图像编码**:模板把意图声明前置(选模板=声明意图,风格走默认,身体数据本地读),省意图澄清轮1–2个+参数补全轮。更关键——多模态模型每轮重新token化图片(数百至上千token),自由对话跨轮传图每轮重付prefill;模板把识别→文案→营养收进单次调用或一次确认闭环,**图像只编码一次**。这是延迟下降主来源,非单纯RTT。
2. **prompt"短且恒定"**:L1/L2/L6固定前缀可命中KV/prompt缓存,prefill只算可变尾巴几十token;并省掉自然语言意图解析的额外推理。一次性任务模板可能比5字提问略长,但换掉意图解析+追问轮,总成本仍降。净值取决于复用频率。
3. **结构化输出消灭抽取轮+修复轮**:自由文本前端只能正则/NLP抽取,措辞变就崩,崩了要修复轮或抽取轮。结构化直接JSON.parse;置信度数值字段让前端`<阈值`自动路由三分档UI;字段闭合可先渲染;schema约束解码天然合法。链条:结构化→直接解析→消灭抽取/修复轮→端到端少一次往返。**最确定的性能收益**。
4. **模板限制发挥:强制schema诱发越界幻觉**:模板A契约写死"输出菜品列表",用户拍的不是食物时空列表=违约,模型被压着编菜名(OOD典型失效)。**必须内置逃生机制**:schema最前面加路由门字段 `is_food/scene_type`,规则"若非食物输出is_food=false并说明,不进菜品列表",让schema允许负路径;低置信转手动为第二逃生口。第二类:固定形态装不下新意图→L5问题通道允许范围内覆盖,超出溢出到自由提问lane。第三类:文案趋同→风格标签受控变化+再生成靠采样温度恢复多样性。
- **收敛**:模板用"前置意图+固定前缀可缓存+结构化免解析"换速度,代价是把OOD处理责任从模型转嫁到schema设计——`is_food`路由门字段不是可选项,是模板成立的前提。

### 3.7 模型选型:双模型分工(按模态切,非按结构化切)

**结论:双模型分工更优——但切分轴不是"结构化vs自由对话",而是"模态×难度来源"。**
1. **纠正切分轴**:结构化≠可降配。识图难度在**感知**(图→菜品身份),输出JSON只是换格式,感知难度一分未减——"结构化就用小VL模型"在识图上不成立。文案/营养建议难度在**生成**且被骨架/风格/DB数值三重约束,可降配。**结构化降低的是生成/指令遵循难度,不降低感知难度。**
2. **核心机制**:识图结构化输出本身是纯文本,下游文案、营养建议不再需要图片——"必须多模态"只剩识图+含图自由对话,切分线正好落在模态交界。图片只在感知层编码一次,下游不再付图像prefill。**结构化的回报率:让双模型交接无需重传图。**
3. **定档表**:

| 任务 | 难度来源 | 模态 | 档位 |
|---|---|---|---|
| 识图A / 含图自由对话 | 感知 | 多模态 | **强VL(不降配)** |
| 纯文本自由对话 | 通用推理 | 文本 | 强文本 |
| 文案B | 生成(受约束) | 文本 | 中/轻量可试 |
| 营养建议C | 翻译(数值固定) | 文本 | 轻量即可 |
| 搭配推荐 | 规则为主 | — | 规则引擎 |

4. **调度与成本**:路由零成本(选模板=已知路由);交接成本被结构化抵消;固定前缀双模型各自缓存;双冷启动是唯一实打实新增成本(预热/常驻缓解);**文案"再生成"高频循环是自反馈陷阱**——小模型质量差→用户反复再生成→调用量上涨吃掉省的成本,降配前必须先验质量。
5. **选型**:感知/含图对话=强多模态单一模型。中文菜系+菜单OCR敏感→Qwen3-VL/GLM-5V/Kimi K3优先;极致速度+结构化稳定→Gemini 3.x Flash。生成/翻译=轻量文本模型,可同族复用工具链。**退回单模型判据:降配省下的"单次成本×下游调用量"是否大于"运维+双冷启动+质量回退";接近时选单模型。**

## 4. 点餐助手(任务26)

### 4.1 菜单识别(结构化抽取)

菜单识别是**结构化抽取**,不是单菜品分类,结构在"单菜品"上加一层列表和分区:

```json
{
  "menu_id": "m_20260916_001",
  "source_image": "oss://.../menu_raw.jpg",
  "menu_layout": "printed",            // printed | handwritten | mixed
  "overall_confidence": 0.86,
  "sections": [{ "section_name": "热菜", "section_confidence": 0.91 }],
  "items": [
    {
      "item_id": "i_001", "name": "宫保鸡丁", "name_confidence": 0.96,
      "price": 38.0, "price_confidence": 0.93, "price_type": "fixed",
      "category": "热菜", "category_confidence": 0.80,
      "raw_text": "宫保鸡丁 …… 38", "bbox": [120, 340, 480, 392], "flags": []
    }
  ],
  "warnings": ["detected_handwriting"]
}
```

关键设计点:
| 字段 | 说明(理由) |
|---|---|
| `name_confidence`/`price_confidence` **分开** | 菜名和价格识别难度不同。价格纯数字+位置固定,OCR更准;菜名受字体、生僻字、手写影响大。合并会掩盖问题 |
| `price_type` | 菜单常见"时价""按份/按斤",不能强行填数字,否则污染营养/预算计算 |
| `category` | 两条来源:①菜单分区标题(优先级高,标 from_section)②模型推断(置信度天然偏低) |
| `bbox` | 小程序交互必备:纠错时高亮原图区域,降低核对成本 |
| `raw_text` | 保留OCR原始串,便于对照"模型看到了什么" |

> 类别建议**不单独依赖模型**:优先用菜单分区标题映射(凉菜/热菜/主食/饮品),比模型分类更稳;类别给营养分析和搭配推荐用,**误分类比误价格更易被下游放大**。

**置信度处理**(沿用任务24三分档,并给具体阈值):
| 档位 | 置信度 | 处理 |
|---|---|---|
| 高 | ≥ 0.90 | 直接展示为已识别,默认勾选 |
| 中 | 0.60 – 0.90 | 展示+高亮角标"请确认",默认勾选但强制过目 |
| 低 | < 0.60 | 展示为空白占位输入框,不预填 |

- **手写菜单**(`menu_layout=handwritten`):全局对 `name_confidence` 降档(×0.7);默认不勾选低置信项;`price_confidence` 门槛更严(高置信提到0.95,防连笔误读7↔1);输出 `warnings` 前端提示重点核对价格。
- **花哨字体/艺术字**:主要影响名称OCR,价格区受影响小→只降 `name_confidence`;对易混字符做候选集输出("鳳/风""鳝/善")。
- **价格硬校验**:量纲校验(>999元、<0.5元标 `low_price`);缺失即拦截(`price_type=missing` 未补全不进入下一步营养/搭配计算)。

**用户纠错交互**:顶部回显原图,下方逐条卡片列表,点击高亮对应 `bbox`;按 section 分组。分档视觉(高=常规卡片可批量确认 / 中=黄色高亮+候选菜名+价格快速修正 / 低=灰色占位输入 / 价格缺失=红色必填)。三类纠错动作:**改**(点任意字段编辑,类别给下拉)、**删**(误识别项一键删)、**增**(漏识别是菜单高发问题,常驻"+手动添加菜品"入口)。纠错结果回传作标注数据;"全部确认"需先校验,存在红标时禁用或强提示。衔接:确认后列表才进入 §3.3 营养分析(模板C)与 §4.3 搭配推荐;**类别错误会污染搭配推荐**(荤误判素会绕过素食硬约束),中置信类别建议随确认流一并核对。

### 4.2 推荐与排序(两分数加权)

**先说明**:过敏原、素食是硬约束,走硬过滤,**不进入打分加权**(否则权重会被"绕过健康红线"污染)。

**总体排序管线**:

```
候选菜品(已确认识别列表)
   ↓ ①硬约束过滤:过敏原排除 + 素食过滤
   ↓ ②计算两分数:S_taste、S_nutrition
   ↓ ③归一化到同一量纲 [0,1]
   ↓ ④加权融合:Score = w_t·S_taste + w_n·S_nutrition
   ↓ ⑤排序 + 去重/多样性破平
推荐列表
```

关键原则:**两分数必须先归一化再加权**,否则量纲不同加权失去意义。

**1. 口味偏好分 S_taste**

数据来源(按信号强度):显式用餐评价(星级/标签)> 显式偏好/收藏/忌口 > 历史点单频次+新近度(时间衰减,近期>久远)> 历史识别确认/纠错记录 > 浏览停留(辅助)。

推断方式:菜品属性与用户偏好落成**同维度向量**(口味维度示例:辣度/甜度/酸度/咸鲜/油腻度/荤素/菜系/冷热/汤干),用户偏好取值=带时间衰减的加权平均(`pref[dim]=Σ(signal_weight·decay(Δt)·value)/Σ(signal_weight·decay(Δt))`,半衰期60天;评价>点单>浏览);产出**稳定的口味偏好标签**(周期性归纳生成,非每次实时算)。

单菜口味分:`S_taste_raw(d) = cos(pref_vec, dish_vec) + λ·freq_bonus(d)`——余弦相似度+常点菜频次加成(避免"喜欢川菜但没吃过这道"被埋没)。

**2. 营养缺口分 S_nutrition**(规则引擎+数据库,数值非模型生成)

```
每日目标 target_k:身体数据(身高/体重/年龄/性别/活动量/目标) → 规则引擎按公式算 TDEE 与各营养素目标(数值来自数据库)
今日已摄入 consumed_k:今日饮食记录按份量比例累加(即 §2 的 daily_nutrition_summary)
缺口 gap_k = target_k − consumed_k
```

营养素分两类:正向补足型(蛋白质/膳食纤维/热量-减脂目标下)gap>0=还差;限制封顶型(钠/添加糖/饱和脂肪)接近/超限再加=负分。

```
Fulfill(d) = Σ_{k∈正向} α_k·min(1, nut_dk / max(gap_k, ε))     // 超过缺口不额外加分,防推荐超量
Penalty(d) = Σ_{k∈限制} β_k·clamp((consumed_k+nut_dk−limit_k)/limit_k, 0, 1)
S_nutrition(d) = clamp(Fulfill(d)·(1−Penalty(d)), 0, 1)
```
α_k、β_k 由规则引擎按用户目标设定(减脂→热量/钠权重高;增肌→蛋白权重高)。

**3. 归一化策略(分治,各自保真)**
- `S_taste`:在**当前候选菜单内 min-max** 到 [0,1](喜欢程度本是菜单内相对比较)。
- `S_nutrition`:天然落在 [0,1](比例值),**保持绝对映射不拉伸**——"今天蛋白缺口很大"的真实含义不丢失。
- 融合 `Score = w_t·S_taste_norm + w_n·S_nutrition`(w_t+w_n=1);破平:同菜系/同主料连续出现降权(多样性),仍平手则营养缺口大者优先(契合健康管理定位)。

**4. 权重滑块(5档粗调,两端留余量)**

| 档位 | 文案 | w_t | w_n |
|---|---|---|---|
| 1 | 更看重口味 | 0.80 | 0.20 |
| 2 | 偏口味 | 0.65 | 0.35 |
| 3 | 均衡 | 0.50 | 0.50 |
| 4 | 偏营养 | 0.35 | 0.65 |
| 5 | 更看重营养 | 0.20 | 0.80 |

设计要点:**两端不用 0/1**——即使"更看重营养"仍留 0.20 口味,避免推荐不可执行;滑块即时重排(只改权重重新加权,不重算两分数)。

**5. 冷启动与边界**:无历史偏好→S_taste 置 0.5 中性或退化为大众热门;无身体数据→用 DRI 默认目标并提示补全;今日无记录→gap≈target(整日全额);某营养素已超标→gap 记负,限制型叠加惩罚自动避开重钠重糖菜;缺口全补满→Fulfill 趋 0,排序退化为纯口味推荐(合理)。

### 4.3 搭配推荐(已点约束 / 预设选项 / 路由)

核心对齐参考文件第4节:"过敏原排除与素食过滤为**硬约束**,口味互补、营养均衡、浓淡平衡为**软约束**"。

**1. 已点餐品解构为三类约束**

已点集合是推荐问题的**上下文**(不是候选),先解构:

| 约束 | 类型 | 进入方式 |
|---|---|---|
| 过敏原集合(已点过敏原∪用户档案过敏原) | 硬 | 候选集剔除,任何路由都不放行 |
| 素食标记(已点含荤→不强制;已点全素/用户素食→纯素) | 硬 | 候选过滤 |
| 营养均衡(本餐剩余缺口) | 软 | 已点营养合计 vs 今日目标 |
| 口味互补 | 软 | 基于已点口味向量求差异化方向 |
| 浓淡/冷热/品类平衡 | 软 | 已点偏浓→推清淡;已有凉菜→优先热菜 |

本餐剩余缺口:`gap_this_order_k = target_k − 今日已摄入(不含本单) − nut_C_k`;已点把限制型顶到临界→推荐端叠加惩罚主动避开重盐重油菜。

口味互补与 4.2 排序**方向相反**:选单菜要相似(cos 越高越好),搭配要互补(`complement_score = 1 − cos(taste_d, taste_C)`),并叠加规则校正(已有重辣→辣度惩罚;已有多道酸甜→甜酸惩罚)。

```
S_pair(d) = clamp(w_fill·Fulfill_remaining − w_pen·Penalty_remaining + w_comp·complement_score + w_bal·balance_score, 0, 1)
```
权重 w_* 由预设意图决定(如"推荐饮品"时 w_bal 侧重品类);数值全部来自规则引擎+数据库。

**2. 预设选项清单(5项)+ 统一 prompt 骨架**

| 预设标签 | 意图 | 硬过滤 | 软约束侧重 | 输出形态 |
|---|---|---|---|---|
| 再加一个菜 | 补一道正餐 | 过敏原、素食 | 营养均衡+口味互补+浓淡平衡 | 3~5道菜+理由 |
| 推荐饮品 | 配饮 | 过敏原、素食 | 品类(排除已有饮品)、口味互补、避冲突(重油配解腻) | 2~3款 |
| 来个汤 | 配汤 | 过敏原、素食 | 品类(已有汤则提示)、浓淡平衡 | 2~3款 |
| 清淡点 | 减油腻 | 过敏原、素食 | 油/盐惩罚拉高权重 | 3道清淡菜 |
| 加个主食 | 补碳水 | 过敏原、素食 | 热量缺口 | 主食选项 |

统一骨架 prompt:角色声明→**硬约束段(绝不违反)**→已点餐品(菜名/类别/份量/主要营养)→本餐剩余营养缺口(标注"数值来自数据库,不得自行编造")→口味浓淡现状→本次意图→要求(只在候选清单内选/给2~4项并说"为什么搭配"/无法满足硬约束时明确说明而非硬凑/输出JSON)→候选清单。

要点:**候选清单由规则引擎预过滤后给出**(硬约束在进 prompt 前已剔除),模型只负责"选谁+讲理由",**不负责判过敏原、不生成营养数值**。

**3. 预设与自由提问并行路由(共用执行层)**

```
用户输入 → 意图判定(轻量分类)
  ├ 命中预设关键词 → 预设管线(固定硬过滤+骨架prompt)
  └ 自由提问 → 解析意图→抽取约束→同一过滤器+自定义prompt
  └ 两者皆像 → 预设定品类+自由提问定侧重
  └ 无法识别 → 澄清式反问+预设选项按钮
```

**关键:两条路由共用同一「硬过滤→候选→生成」执行层**——硬约束过滤、营养缺口计算、候选生成完全一致,自由提问不会绕过过敏原/素食红线。

自由提问约束抽取示例:"有没有不那么辣的肉菜,预算50以内"→品类:肉菜(候选过滤)/辣度:低(惩罚权重↑)/预算:≤50(价格硬过滤)/过敏原素食仍从档案+已点继承(**不可被提问覆盖**)。安全兜底:用户说"给我来个带虾的"而虾在过敏原内→返回"该菜含您的过敏原,已为您排除"+替代建议。

**4. 前后衔接**:入口依赖 4.1 确认的菜单列表+已点购物车;营养/口味数据复用 §2/§5;已点菜品计入"今日已摄入";推荐结果可回填购物车,形成"识别→点单→搭配"闭环。

## 5. 健康管理(任务27)

### 5.1 个人健康数据体系(借鉴 HealthKit 四类对象,与 §2 五表互补)

| 数据类 | 字段 | 更新方式 | 频率 |
|---|---|---|---|
| 档案 characteristic | 性别、出生日期、身高 | 用户录入 | 极低频 |
| 身体测量 | 体重、体脂率、BMI、腰围 | 体脂秤同步/手动 | 日~周 |
| 饮食记录 | 餐次/食物/分量→营养素(**即 §2 的 diet_record/daily_nutrition_summary,唯一事实源**) | 点餐助手自动写入/拍照识别/手动 | 每餐 |
| 运动消耗 | 运动类型、时长、消耗热量 | 设备同步/手动 | 每次运动后 |
| 体征(可选) | 步数、睡眠时长、静息心率 | 设备同步 | 日 |
| 实验室数据 | 空腹血糖、A1c、血脂(LDL/HDL/TG) | 用户录入体检报告 | 月~季 |
| 目标 goals | 体重目标、每日热量目标、宏量目标(比例+克双单位)、特殊诉求 | 初始算法生成+月周期重校准 | 月级 |

**每条 sample 必带 `source` 字段**(设备同步/手动/拍照识别/点餐写入)——数据可信度争议时可追溯。营养数值一律由食物库供给(§1 全局原则),模型不估算。

### 5.2 检测周期:日/周/月三层架构(非三选一)

- **日=决策层**("今天该怎么吃"):记录即反馈+晚间汇总;热量缺口/盈余、三大营养素达成率、单餐结构均衡检查;**剩余预算 = target_k − consumed_k 直接作为 4.2/4.3 排序输入**;呈现=当日反馈卡(数值+环形进度条),不长文。
- **周=行为层**("我的习惯怎么样"):7日均值 vs 目标(平滑单日噪声);**达标天数**("蛋白质7天达标5天"比"周均值82%"更可行动);波动方差/周末效应(识别"周末崩盘");缺口排行前3;外食占比/跳过早餐次数/零食热量占比;食物贡献度下钻(学 MyFitnessPal food analysis);呈现=高亮摘要+明细图表+**1~3条下周可执行建议**。
- **月=战略层**("方向和目标要不要改"):月度均值 vs DRI;体重/体脂趋势;**综合健康分**(学 Apple Health Age:心脏/代谢/营养多指标加权,纳入 A1c/LDL);目标进度校准(一直大缺口→目标太高→重校准);方案重调建议(coaching 式:给动作不给指责)。

**三层闭环**:
```
日(每餐决策) ──累积──→ 周(习惯诊断) ──累积──→ 月(战略重校准)
   ↑target_k 每日来自目标库     ↑建议按周微调习惯        ↓重调目标
   └──────── 月回调改写 target_k、宏量比例 ────────→ §4 营养分自动跟随
```

### 5.3 周期分析

**趋势分析**:7日/30日移动平均平滑;**双条件判定(借 Apple Trends):`|当前窗口均值−基准均值|/基准 ≥ 阈值(如5%)` 且 `持续 ≥ N天(如14天)`** 才认定趋势;单点偏离只进当日反馈不升级为趋势告警;数据点可下钻到具体记录。

**缺口分析**:达标率 `r_k = 实际摄入_k / DRI_k` 三级分级——单日 r<0.8→当日反馈卡提示(联动 §4 点餐补缺口);周均值<0.8 且连续2周→周报重点+食物替换建议;月均值<0.7→月报结构性调整/建议就医检查(如长期铁缺口)。过剩对称分级(钠/糖/饱和脂肪 r>1.2)。输出永远是**具体到食物的动作**("钙缺口300mg/天≈每天一杯酸奶")——数字来自统计,食物等价换算走规则库模板。

**建议生成(两级架构,与 §1 全局原则一致)**:规则引擎先行(周期统计→阈值/规则库→结构化结论:缺口项/幅度/建议动作/关联食物候选)→ 模型只翻译成人话,**禁止产出任何数字**。分级:当日微调("晚餐加一份豆制品")/周计划(习惯替换)/月方案(热量目标±10%、宏量比例调整)。闭环回流:每条建议带"已调整/忽略"按钮,连续3次同类忽略→降权不再推送(防唠叨)。医学诉求模板标注"非医疗建议,以医嘱为准"。

### 5.4 与数据层(§2)及点餐助手(§4)的接口

| 接口 | 数据 | 说明 |
|---|---|---|
| §4 点餐 → 健康管理 | 订单/识别结果自动写入饮食记录(consumed_k) | 点餐即记录,零额外操作 |
| 健康管理 → §4 点餐 | target_k 每日目标、剩余预算 | 月周期重校准后直接改写排序营养分输入 |
| 健康档案 → 目标库 | 身体数据→能量缺口算法生成初始目标 | 冷启动用人群统计先验;学 Keep 能量缺口原理 |
| 食物库 | 权威数据源(中国食物成分表/商业授权),只读 | 禁众包修改;营养数值禁模型生成 |

### 6.2 食知联动方案(数据项 / 进法 / 优先级)

**能进的数据**:步数(微信运动)、体重/体脂(蓝牙秤直连+手动录入)、运动消耗(步数经 METs 规则库换算,规则引擎出数字禁模型估算)。

**优先级**:
- **P0**(纯小程序可交付):`wx.getWeRunData` 步数接入;体重/体脂手动录入+蓝牙体脂秤直连(微信BLE);步数→运动消耗 METs 规则库
- **P1**(商务/资质驱动):华为 Health Kit REST(企业资质+数据权限审核,预留约1个月)
- **P2**(战略项按需立项):iOS 原生伴随App+HealthKit;Health Connect(仅当出安卓原生App)
- **P3**(并行评估):薄荷食物数据开放平台采购(食物库供给线,与数据接入线正交)

**落地对接**:每条外部样本带 `source` 字段(`werun`/`ble-scale:{model}`/`manual`/`huawei-healthkit`)入 §5.1 数据体系;外部数据与手录数据同等参与 §5.3 双条件趋势判定;冲突时设备自动源优先于手录、手录可覆盖;用户拒绝 scope.werun → 提示手动录入并给 openSetting 入口(不阻塞主流程);步数属敏感个人信息,隐私指引须明示收集范围/用途/存储期限。
