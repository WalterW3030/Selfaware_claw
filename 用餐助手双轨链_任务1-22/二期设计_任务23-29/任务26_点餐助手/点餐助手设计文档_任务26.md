## 第1轮：菜单识别（输出结构 / 置信度 / 纠错交互）

### 一、菜单识别输出结构（JSON）

菜单识别本质是**结构化抽取**，不是单菜品分类，结构在"单菜品"基础上加一层列表和分区：

```json
{
  "menu_id": "m_20260916_001",
  "source_image": "oss://.../menu_raw.jpg",
  "menu_layout": "printed",            // printed | handwritten | mixed
  "overall_confidence": 0.86,
  "sections": [
    { "section_name": "热菜", "section_confidence": 0.91 }
  ],
  "items": [
    {
      "item_id": "i_001",
      "name": "宫保鸡丁",
      "name_confidence": 0.96,
      "price": 38.0,
      "price_confidence": 0.93,
      "price_type": "fixed",           // fixed | market(时价) | missing
      "category": "热菜",
      "category_confidence": 0.80,
      "raw_text": "宫保鸡丁 …… 38",
      "bbox": [120, 340, 480, 392],    // 用于拍照回显定位
      "flags": []                       // low_name / low_price / dup
    }
  ],
  "warnings": ["detected_handwriting"]
}
```

**关键设计点：**

| 字段 | 说明 |
|---|---|
| `name_confidence` / `price_confidence` **分开** | 菜名和价格的识别难度完全不同。价格是纯数字+位置固定，OCR通常更准；菜名受字体、生僻字、手写影响大。合并成一个置信度会掩盖问题 |
| `price_type` | 菜单常见"时价""按份/按斤"，不能强行填数字，否则污染后续营养/预算计算 |
| `category` | 允许来源有两条：①菜单分区标题（优先级高，来源可标注 `from_section`）②模型推断（置信度天然偏低） |
| `bbox` | 小程序交互必备：用户纠错时能高亮原图对应区域，降低核对成本 |
| `raw_text` | 保留 OCR 原始串，便于用户和调试对照"模型看到了什么" |

> 类别建议**不单独依赖模型**：优先用菜单分区标题映射（凉菜/热菜/主食/饮品），这比模型分类更稳；类别主要是给【营养分析】和【搭配推荐】用的，误分类比误价格更容易被下游放大。

### 二、置信度处理（含字体花哨 / 手写菜单）

沿用参考文件的分档思路，但对**菜名和价格分别分档**，因为二者下游影响不同：

**1. 分档规则**

| 档位 | 置信度 | 处理 |
|---|---|---|
| 高 | ≥ 0.90 | 直接展示为已识别，默认勾选 |
| 中 | 0.60 – 0.90 | 展示+高亮角标"请确认"，默认勾选但强制过目 |
| 低 | < 0.60 | 展示为空白占位输入框，不预填，需用户输入 |

**2. 字体花哨 / 手写菜单的特殊处理**

**手写菜单（检测到 `menu_layout = handwritten`）：**
- 全局对 `name_confidence` 做**降档处理**（如整体 ×0.7），避免印刷体训练出的高置信假象
- 默认不勾选任何低置信项，引导用户逐条核对
- 手写价格极易连笔误读（7↔1、6↔0），`price_confidence` 阈值应比印刷菜单更严（例如高置信门槛提到 0.95）
- 输出 `warnings: ["detected_handwriting"]`，前端顶部提示"手写菜单识别可能不准，请重点核对价格"

**花哨字体 / 艺术字（印刷但装饰重）：**
- 主要影响名称 OCR，价格区（通常在右侧固定列、字体更朴素）受影响较小 → 可只降 `name_confidence`
- 对易混字符做**候选集输出**（如"鳳/风""鳝/善"），中置信项在纠错时给候选项而非让用户全键盘重输

**3. 价格硬校验**

价格是硬字段，做两道规则校验（价格影响营养与预算）：
- **量纲校验**：单价超出合理区间（如 > 999 元、< 0.5 元）直接标 `low_price`
- **缺失即拦截**：`price_type = missing` 的菜项，进入"待补全"状态，**未补全不进入下一步**营养/搭配计算

### 三、用户纠错交互

延续参考文件第1节"识别结果交用户确认后使用"的原则，针对**多菜品**做列表化交互：

**1. 结果页形态**
- 顶部回显原图，下方**逐条卡片列表**，点击卡片高亮原图对应 `bbox`
- 按 `section`（热菜/主食…）分组展示，贴合真实菜单心智

**2. 分档视觉**

| 状态 | 视觉 | 交互 |
|---|---|---|
| 高置信 | 常规卡片 | 可直接批量确认 |
| 中置信 | 黄色高亮 + "请确认"角标 | 点击展开：**候选菜名（含易混字候选）+ 价格快速修正** |
| 低置信 | 灰色占位输入框 | 需手动输入，键盘直接唤出 |
| 价格缺失/时价 | 红色必填标记 | 下拉选"时价/按斤"，或填数字 |

**3. 必要的三类纠错动作**

1. **改**：点任意字段即可编辑（菜名/价格/类别），类别给下拉避免键盘
2. **删**：误识别项（如把"本店特色"当菜名）一键删除
3. **增**：**漏识别**是菜单场景高发问题（被图片截断、跨列排版），必须有常驻"+ 手动添加菜品"入口

**4. 效率设计**
- "全部确认"按钮，但要**先校验**：存在红标（价格缺失）时禁用或强提示
- 纠错结果**回传**：用户对低置信项的最终修正，作为该菜单的标注数据，用于后续 OCR/模型迭代

**5. 与后续流程衔接**
- 确认后的菜品列表才进入【营养分析】（按份量比例算摄入）和【搭配推荐】（过敏原/素食为硬约束，依赖准确的菜名与类别）
- **类别错误会污染搭配推荐**（如把荤菜误判为素菜，绕过素食过滤硬约束），因此类别在中置信时也应提示确认，而非静默使用

## 第2轮：推荐与排序（两分数加权）

**先说明**：过敏原、素食是硬约束，走【第4节】的过滤，**不进入打分加权**（来源：上下文记录第4节），否则权重会被"绕过健康红线"污染。

### 一、总体排序管线

```
候选菜品(已确认识别列表)
   ↓ ①硬约束过滤：过敏原排除 + 素食过滤
   ↓ ②计算两分数：S_taste、S_nutrition
   ↓ ③归一化到同一量纲 [0,1]
   ↓ ④加权融合：Score = w_t·S_taste + w_n·S_nutrition
   ↓ ⑤排序 + 去重/多样性破平
推荐列表
```

关键原则：**两分数必须先归一化再加权**，否则"口味相似度"和"营养价值"量纲不同，加权失去意义。

### 二、口味偏好分 S_taste

**1. 从哪些数据推断（按信号强度排序）**

| 优先级 | 数据源 | 说明 |
|---|---|---|
| 强 | **显式用餐评价**（星级/标签） | "用餐评价经周期性归纳生成口味偏好标签"，是最直接信号 |
| 强 | **显式偏好/收藏/忌口** | 用户主动表达，权重最高 |
| 中 | **历史点单频次 + 新近度** | 饮食记录，用时间衰减，近期>久远 |
| 中 | **历史识别确认/纠错记录** | 确认过的菜=实际吃过，可反推常点菜 |
| 弱 | 浏览/停留行为（若有埋点） | 只作辅助，不单独成结论 |

**2. 推断方式：聚合成"口味维度向量"**

把菜品属性拆成可比较的维度，用户偏好也落成同维度向量：

**口味维度（示例）：** 辣度、甜度、酸度、咸鲜、油腻度、荤素、菜系、冷热、汤/干

用户偏好某维度的取值（带时间衰减的加权平均）：

```
pref[dim] = Σ (signal_weight · decay(Δt) · value) / Σ (signal_weight · decay(Δt))
```

- `signal_weight`：评价 > 点单 > 浏览
- `decay(Δt)`：如半衰期 60 天，近期行为权重更高
- 产出的是**稳定的口味偏好标签**（周期性归纳生成，非每次实时算）

**3. 单个菜品口味分**

菜品从食物库取属性向量 `dish_vec`，与用户偏好向量算相似度：

```
S_taste_raw(d) = cos(pref_vec, dish_vec)          // 0~1
              + λ · freq_bonus(d)                 // 常点菜加成(可选)
```

`freq_bonus` 用饮食记录里该菜/该菜系的历史频次，避免"喜欢川菜但没吃过这道"被埋没。

### 三、营养缺口分 S_nutrition

**1. 健康数据怎么取（规则引擎+数据库）**

```
每日目标 target_k：由 身体数据(身高/体重/年龄/性别/活动量/目标:减脂·维持·增肌)
                    → 规则引擎按公式算出 TDEE 与各营养素目标(数值来自数据库)
今日已摄入 consumed_k：由今日饮食记录，按份量比例累加
缺口 gap_k = target_k − consumed_k
```

**营养素分两类处理（设计要点）：**

| 类型 | 例子 | 缺口语义 |
|---|---|---|
| **正向（补足型）** | 蛋白质、膳食纤维、热量（减脂目标下） | gap>0 = 还差，补上有益 |
| **限制（封顶型）** | 钠、添加糖、饱和脂肪 | 已摄入接近/超限，再加就是负分 |

**2. 单个菜品的营养分**

**补足型贡献（0~1）：**
```
Fulfill(d) = Σ_{k∈正向} α_k · min(1, nut_dk / max(gap_k, ε))
```
`nut_dk` 是该菜某营养素含量（按份量从数据库取），`gap_k` 是今日缺口。填得越准越接近 1，但**超过缺口不额外加分**（避免推荐超量）。

**限制型惩罚（0~1）：**
```
Penalty(d) = Σ_{k∈限制} β_k · clamp( (consumed_k + nut_dk − limit_k) / limit_k , 0, 1)
```

**合成：**
```
S_nutrition(d) = clamp( Fulfill(d) · (1 − Penalty(d)), 0, 1)
```
- α_k、β_k 为用户目标相关的权重（减脂→热量/钠权重高；增肌→蛋白权重高），由规则引擎设定，非模型生成。

### 四、归一化 + 加权

**为什么必须归一化：** `S_taste` 是余弦相似度（相对），`S_nutrition` 是缺口满足度（有物理量纲）。直接加权会让量纲大的一方主导。

**归一化策略：**
- `S_taste`：在**当前候选菜单内做 min-max**，映射到 [0,1]。因为"喜欢程度"本就是菜单内的相对比较。
- `S_nutrition`：已天然落在 [0,1]（满足度+惩罚都是比例），**保持绝对映射**，不做菜单内拉伸——这样"今天蛋白缺口很大"的真实含义不丢失。

> 归一化后，排序是"在这份菜单里，相对口味偏好和相对营养缺口下的最优"，而非绝对最优。这符合点单场景。

**融合：**
```
Score(d) = w_t · S_taste_norm(d) + w_n · S_nutrition(d)
其中 w_t + w_n = 1
```

**破平/去重：**
- 同菜系/同主料连续出现的，按名次降权（多样性）
- 仍平手时：营养缺口大者优先（契合"健康管理"定位）

### 五、权重滑块映射（粗调）

滑块做成**5 档**（粗调，不需要连续）。把"更看重口味 ←→ 更看重营养"映射为：

| 档位 | 文案 | w_t | w_n |
|---|---|---|---|
| 1 | 更看重口味 | 0.80 | 0.20 |
| 2 | 偏口味 | 0.65 | 0.35 |
| 3 | 均衡 | 0.50 | 0.50 |
| 4 | 偏营养 | 0.35 | 0.65 |
| 5 | 更看重营养 | 0.20 | 0.80 |

**设计要点：**
- **两端留余量（不用 0/1）**：即使"更看重营养"，仍保留 0.20 给口味，避免推出用户完全不想吃的菜（否则推荐不可执行）；反之亦然。
- **软约束不被滑块覆盖**：过敏原/素食是①步硬过滤，任何档位都不放行。
- **滑块即时重排**：只改 `w_t/w_n` 重新加权即可，无需重算两分数（即改即出，体验顺滑）。

### 六、冷启动与边界

| 场景 | 处理 |
|---|---|
| **无历史偏好**（新用户） | `S_taste` 置 0.5 中性，或退化为大众热门/菜系通用度；提示用户点几道后生成偏好 |
| **无身体数据** | 用膳食参考摄入量（DRI）默认目标，提示补全身体数据以精确化 |
| **今日无饮食记录** | `gap_k ≈ target_k`（整日全额），正常推荐 |
| **某营养素已超标** | 该维度 `gap_k` 记为负，不参与补足、且对限制型叠加惩罚 → 自动避开重钠/重糖菜 |
| **缺口全补满** | `Fulfill` 趋 0，此时排序由口味主导（退化为纯口味推荐，合理） |

## 第3轮：搭配推荐（已点约束 / 预设选项 / 路由）

核心对齐【保留功能参考·第4节 搭配推荐】："过敏原排除与素食过滤为**硬约束**，口味互补、营养均衡、浓淡平衡为**软约束**"，并复用前几轮的营养缺口与口味偏好。

### 一、已点餐品如何转成推荐约束

已点菜品是推荐问题的**上下文**（不是候选），要先把它"解构"成三类约束，再送进推荐器。

**1. 从已点集合提取约束**

```
已点集合 C = {c1, c2, ...}
        ↓ 解构
硬约束(不可违反)    软约束(尽量满足)
├ 过敏原集合 Σ_allergen = 已点菜的过敏原 ∪ 用户档案过敏原
├ 素食标记 veg_flag = 已点中是否含荤(含荤则全荤约束,含素则纯素约束)
└ 用户档案忌讳

营养侧: 已点营养合计 nut_C = Σ nut_ci(按份量,来自数据库)
口味侧: 已点口味向量 taste_C = 已点菜属性聚合
浓淡侧: 已点浓淡程度(清淡↔重口)
温度/品类侧: 已点是否已有汤/饮品/凉菜/主食
```

**2. 三类约束进推荐的规则**

| 约束 | 类型 | 进入方式 |
|---|---|---|
| **过敏原排除** | 硬 | 候选集中剔除含 `Σ_allergen` 的菜，任何预设/自由提问都不放行 |
| **素食过滤** | 硬 | 用户素食 或 已点全素 → 只留素菜；已点含荤且用户非素食 → 不强制 |
| **营养均衡** | 软 | 用"已点营养合计 vs 今日目标"算**剩余缺口** |
| **口味互补** | 软 | 基于 `taste_C` 求"差异化方向" |
| **浓淡平衡** | 软 | 已点偏浓→推清淡；偏淡→推重口 |

**3. 营养均衡：复用第3节缺口，但基准换成"已点"**

第3节缺口是 `target − 今日已摄入`；搭配场景要再扣掉**已点这单**，得**本餐剩余缺口**：

```
gap_this_order_k = target_k − 今日已摄入(不含本单) − nut_C_k
```
- 已点把某补足型（蛋白/纤维）填满了 → 该维度不再作为推荐目标
- 已点把限制型（钠/糖）顶到临界 → 推荐端**叠加惩罚**，主动避开重盐重油菜

**4. 口味互补：从"相似"翻转为"差异化"**

注意与第2轮排序**方向相反**：
- 第2轮（选单菜）：`S_taste` 是**相似度**，越像偏好越好
- 本轮（搭配）：是**互补**，要避免"全辣""全甜"叠加

```
complement_score(d) = 1 − cos(taste_d, taste_C)      // 差异越大越互补
再叠加规则校正:
  - 已有重辣 → 辣度维度做惩罚(避免火上浇油)
  - 已有多道酸甜 → 甜/酸维度惩罚
  - 已有凉菜 → 优先热菜(冷热平衡)
```

**软约束合成**（数值来自规则引擎+数据库，非模型生成）：

```
S_pair(d) = clamp(
    w_fill · Fulfill_remaining(d)          // 补剩余缺口
  − w_pen  · Penalty_remaining(d)          // 超限惩罚
  + w_comp · complement_score(d)           // 口味互补
  + w_bal  · balance_score(d),             // 浓淡/冷热/品类平衡
  0, 1)
```
权重 `w_*` 由预设意图决定（如"推荐饮品"时 `w_bal` 侧重品类）。

### 二、预设选项清单 + prompt 骨架

预设的好处是**约束明确、可控**，直接映射到硬编码的过滤 + 骨架化 prompt。

| 预设标签 | 意图 | 硬过滤 | 软约束侧重 | 输出形态 |
|---|---|---|---|---|
| **再加一个菜** | 补一道正餐 | 过敏原、素食 | 营养均衡 + 口味互补 + 浓淡平衡 | 3~5 道菜+理由 |
| **推荐饮品** | 配饮 | 过敏原、素食 | 品类（排除已有饮品）、口味互补、**避开与菜冲突**（如重油配解腻） | 2~3 款饮品 |
| **来个汤** | 配汤 | 过敏原、素食 | 品类（已有汤则提示）、浓淡平衡 | 2~3 款汤 |
| **清淡点** | 减油腻 | 过敏原、素食 | 油/盐惩罚拉高权重 | 3 道清淡菜 |
| **加个主食** | 补碳水 | 过敏原、素食 | 热量缺口 | 主食选项 |

**Prompt 骨架（统一模板）**

```
【角色】你是点餐搭配助手,基于"已点餐品"给出搭配建议。

【硬约束·绝不违反】
- 过敏原:候选不得含 {Σ_allergen}。若候选信息不足,标注"过敏原未知,请核实"。
- 素食:{veg_flag ? "只推荐素食" : "无素食限制"}。

【已点餐品】
{逐条列出 菜名 / 类别 / 份量 / 主要营养}

【本餐剩余营养缺口】(数值来自数据库,你不得自行编造)
- 待补足:{正向营养素及剩余量}
- 已接近上限:{限制型营养素及余量}

【口味与浓淡现状】
- 已点口味倾向:{taste_C 摘要}
- 浓淡:{清淡/适中/重口}

【本次意图】{预设标签,例:"推荐饮品"}

【要求】
1. 只在下方候选清单中选择,不得虚构菜品。
2. 给出 2~4 项,每项说明"为什么搭配"(对应哪个软约束)。
3. 若无法在满足硬约束下给出,明确说明而非硬凑。
4. 输出 JSON:{intent, items:[{name, reason, tags}], note}

【候选清单】
{candidates}
```

要点：**候选清单由规则引擎预过滤后给出**（硬约束在进 prompt 前就剔除了），模型只负责"选谁+讲理由"，**不负责判过敏原、不生成营养数值**。

### 三、自由提问与预设并行路由

**1. 路由架构**

```
用户输入
   ↓ 意图判定(轻量分类)
┌──────────────┬──────────────────┐
│ 命中预设关键词 │ 自由提问          │
│ ("来个汤"…)   │ ("有没有不那么辣   │
│               │  的肉菜")         │
└──────┬───────┴────────┬────────┘
       ↓                 ↓
 预设管线             自由提问管线
 (固定硬过滤+        (解析意图→抽取约束→
  骨架prompt)         同一过滤器+自定义prompt)
       └────────┬────────┘
                ↓
        统一的「硬过滤 → 候选 → 生成」执行层
```

**关键：两条路由共用同一执行层**——硬约束过滤、营养缺口计算、候选生成完全一致，只是"意图与软约束侧重"不同。这样自由提问不会绕过过敏原/素食红线。

**2. 路由判定与兜底**

| 情况 | 处理 |
|---|---|
| 明确命中预设（"来个汤""推荐饮品"） | 走预设管线 |
| 含偏好/条件（"不要太辣""便宜点的肉"） | 走自由提问：先抽约束 → 映射到软约束权重 |
| 同时像预设又带条件（"来个解腻的汤"） | 预设定品类（汤）+ 自由提问定侧重（解腻） |
| 无法识别 | 兜底：澄清式反问 + 给预设选项按钮 |

**3. 自由提问的约束抽取（映射到执行层）**

```
"有没有不那么辣的肉菜,预算 50 以内"
   ↓ 抽取
品类:肉菜(荤)         → 候选过滤
辣度:低               → 口味互补/惩罚权重↑
预算:≤50              → 价格硬过滤
过敏原/素食            → 仍从用户档案+已点继承(不可被提问覆盖)
```

**安全兜底原则（贯穿两条路由）：**
- 用户自由提问**不能覆盖硬约束**：即使说"给我来个带虾的"，若虾在其过敏原内，返回 `"该菜含您的过敏原,已为您排除"` + 替代建议。
- 数值仍来自数据库：自由提问里模型不得凭空给热量/钠值。

### 四、与前后流程衔接

- **入口**：依赖第一步识别+确认的菜单列表，以及"已点"购物车集合
- **营养/口味数据**：复用第3节（营养）与第5节（偏好），已点菜品作为"今日已摄入"的一部分
- **输出**：推荐结果可回填到购物车，形成"识别→点单→搭配"闭环
