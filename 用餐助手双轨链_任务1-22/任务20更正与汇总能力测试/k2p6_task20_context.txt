## 一、总体定位

**一句话定位**：一款"边吃边懂"的用餐知识助手——把每一次吃饭变成获取饮食知识、记录饮食习惯的入口。

**核心价值主张**：解决用户"吃的时候有疑问、吃完想记录、但信息分散"的痛点，通过 **拍照/文字/图文混合** 的多模态输入，实时提供用餐相关知识，并把零散的饮食行为沉淀为个人数据。

**差异化关键（三个抓手）**：
1. **场景聚焦"用餐时"**——不是通用营养查询工具，而是精准卡在"吃饭这一刻"的即时需求。
2. **多模态输入**——拍照识食物（看菜名/看配料表/看菜单）、打字问（"这个能一起吃吗"）、图文结合（拍照+补一句"我在减肥"）。
3. **数据闭环**——身体数据 + 饮食记录互相反哺，让建议越来越个性化（这是长久留存的护城河）。

---

## 二、目标用户

建议按"需求强度"分层，避免一开始就想覆盖所有人：

| 层级 | 用户画像 | 核心诉求 |
|------|---------|---------|
| **核心用户** | 体重/健康管理者（减脂、控糖、健身人群） | 吃之前想知道热量、能不能吃、怎么吃更健康 |
| **核心用户** | 有饮食限制者（过敏、糖尿病、三高、孕期） | 快速判断"这口能不能进嘴"，规避风险 |
| **次核心** | 家庭主厨/家长 | 配餐、食材搭配、营养均衡 |
| **次核心** | 外食党/外卖族 | 看菜单、看配料、点餐决策辅助 |
| **泛用户** | 美食爱好者、养生人群 | 食物科普、饮食文化、养生知识 |

**建议起步聚焦**：核心用户中的"减脂/控糖 + 过敏人群"，因为他们的需求最高频、最刚需，最容易形成付费或高留存。

---

## 三、使用场景

围绕"用餐全流程"拆解，覆盖事前—事中—事后：

**① 点餐前 / 备餐前（决策场景）**
- 拍菜单 → 识别菜品、给热量和营养提示
- 拍食材/包装 → 看配料表、识别添加剂、过敏原
- 拍冰箱剩菜 → "这些能一起做吗""怎么搭配"

**② 用餐中（即时问答场景）**
- 拍盘中菜 → "这是什么""大概多少卡"
- 文字提问 → "螃蟹和柿子能一起吃吗""痛风能吃这个吗"
- 图文结合 → 拍照+"我在哺乳期"

**③ 用餐后（记录场景）**
- 一键把刚才拍的食物存进饮食记录
- 自动累计当日热量/营养/糖分
- 结合身体数据给反馈（"今天钠摄入偏高"）

**④ 长期（数据沉淀场景）**
- 身体数据（体重、血糖、身高、目标）→ 个性化推荐
- 饮食记录趋势 → 周报/月报，看到习惯变化

## 四、给你的三个提醒

1. **"食物相克"类知识要谨慎**——大量流传的相克说法是伪科学，产品若不加辨别直接输出，会损害专业可信度。建议知识库做科学审核。
2. **拍照识别的准确率是生死线**——拍照是核心入口，识别错的代价很高（尤其对过敏/控糖人群），要明确告知置信度和免责声明。
3. **合规红线**——涉及健康建议，要规避"诊断/治疗"措辞，身体数据涉及隐私，需符合隐私合规要求。

## 一、统一输入模型的思路

不管用户发什么，**先归一到统一数据结构**，再进入处理管线。这样避免为三种情况各写一套逻辑。

```
InputObject {
  text:      string | null   // 用户文字
  image:     image[]  | null // 用户照片（支持多张）
  context: {                 // 系统附带的上下文
    userProfile,             // 身体数据、过敏史、目标
    history,                 // 近期饮食记录
    timestamp, location      // 用餐时间/地点（可选）
  }
}
```

三种输入只是这个对象的三种填充方式：
- 只发照片 → `text = null, image = [...]`
- 只发文字 → `text = "...", image = null`
- 图文一起 → `text = "...", image = [...]`

**核心原则：入口统一，分流处理。**

---

## 二、三种输入分别怎么接、怎么处理

### 情况 A：只发照片

**接收**：前端调起相机/相册 → 压缩、纠偏、旋转校正 → 上传。

**处理管线（三步）**：
1. **图像识别**：调用视觉模型识别图中主体
   - 是菜品/食物 → 输出候选食物名 + 置信度
   - 是包装/配料表 → OCR 提取文字
   - 是菜单 → OCR + 版面理解，切成菜品列表
2. **意图推断**：无文字时，靠图像类型推断用户想要什么
   - 盘中菜 → 默认意图 ="这是什么 / 多少热量"
   - 配料表 → 默认意图 ="有没有我不能吃的"
   - 菜单 → 默认意图 ="帮我选 / 这菜健康吗"
3. **生成回答**：结合用户画像输出（下节细讲）

**风险点**：置信度低时必须反问确认，不能瞎猜。
> 例："我识别到可能是'红烧肉'，对吗？如果不对请告诉我菜名～"

---

### 情况 B：只发文字

**接收**：文本框输入 → 检测语言、长度 → 上传。

**处理管线（三步）**：
1. **意图分类**：先用轻量分类器判断属于哪类
   - 知识问答型（"螃蟹和柿子能一起吃吗"）
   - 记录型（"中午吃了碗牛肉面"）
   - 求助决策型（"减肥晚饭吃啥"）
2. **实体抽取**：抽出食物名、身体状态、约束条件
3. **路由到对应能力**：知识库检索 / 记录入库 / 推荐引擎

**关键点**：纯文字没有视觉线索，意图全靠语义，分类准确度是重点。

---

### 情况 C：照片 + 文字

**接收**：图文同时上传，注意两者**时序和关联**（用户可能先拍照后补字，或反之）。

**处理管线（核心是"融合"）**：
1. **分别处理**：图像识别出食物实体，文字解析出意图和约束
2. **语义对齐（最关键的一步）**：把文字当作对图片的"注解/指令"
   - 文字是**补充约束**："我在哺乳期" → 给图片食物的建议要叠加哺乳期规则
   - 文字是**修正**："这不是红烧肉，是糖醋排骨" → 用文字覆盖识别结果
   - 文字是**具体问题**："这个我能吃几口" → 回答要针对这个问题
3. **融合生成**：回答 = f(图片实体, 文字意图, 用户画像)

**示例**：
> 用户发【一盘海鲜照片】+ 文字"痛风能吃吗"
> → 识别：海鲜（高嘌呤）
> → 文字意图：痛风禁忌查询
> → 输出：结合痛风知识库给出警示 + 替代建议

---

## 三、统一处理管线（三种输入共用主干）

```
[输入接收层]
   ↓ 归一化为 InputObject
[预处理]
   图片→压缩/OCR/识别    文字→意图分类/实体抽取
   ↓
[融合层]  ← 只有情况C真正触发，A/B是单模态直通
   对齐图文语义，消解冲突
   ↓
[决策路由]
   知识问答 → 知识库检索
   饮食记录 → 数据库写入
   决策推荐 → 推荐引擎
   ↓
[个性化层]
   叠加用户画像（过敏/目标/历史）
   ↓
[生成层]
   输出答案 + 记录动作 + 置信度声明
```

## 四、三类输入的差异对照表

| 维度 | 只发照片 | 只发文字 | 图文结合 |
|------|---------|---------|---------|
| **主要难点** | 识别准确率 | 意图分类 | 图文语义对齐 |
| **意图来源** | 靠图像类型推断 | 靠语义分析 | 文字直接给 + 图像补充实体 |
| **默认行为** | 识别+科普+记录 | 按分类路由 | 以文字问题为主，图像为实体 |
| **出错风险** | 识别错→答非所问 | 分类错→走错流程 | 图文冲突→答偏 |
| **必要交互** | 低置信度时反问确认 | 意图模糊时澄清 | 冲突时以用户文字为准 |

## 五、三个工程建议

1. **先做情况 A 和 B，C 后做**——A/B 是单模态直通，C 的融合对齐最复杂，可作二期。
2. **所有识别结果都要带置信度**，低置信度统一走"反问确认"，这是体验安全网。
3. **保留原始输入 + 处理中间结果**，便于后续 debug、纠错和模型迭代。

## 一、先分清两类数据的本质差异

设计前必须先看清这两类数据性质完全不同，这决定了它们的存储和管理方式：

| 维度 | 身体数据 | 饮食记录 |
|------|---------|---------|
| **变化频率** | 低（几天/几周变一次） | 高（每天多次） |
| **数据性质** | 状态快照（时间序列） | 事件流水 |
| **主观性** | 客观测量值 | 主观输入，有误差 |
| **关联对象** | 人 | 具体食物+时间 |
| **敏感度** | 极高（健康隐私） | 高（行为隐私） |

**核心结论**：不能混在一张表里，必须分开建模。

---

## 二、数据模型设计

### 1. 身体数据（状态快照表）

特点：每次记录是"某时刻的状态"，形成时间序列。

```
BodyMetric {
  id
  user_id
  date             // 记录日期
  height           // 身高（相对稳定）
  weight           // 体重
  body_fat_rate    // 体脂率（可选）
  blood_sugar      // 血糖（可选，糖尿病用户）
  blood_pressure   // 血压（可选）
  waist            // 腰围（可选）
  target           // 当前目标：减脂/增肌/控糖/维持
  note             // 备注
  source           // 手动录入 / 体脂秤同步 / 医疗设备
  created_at
}
```

**关键设计点**：
- **身高单独处理**：身高基本不变，不必每次记录，可放在用户档案里，体重等高频指标才进时间序列表。
- **可选字段设计**：不同用户关心的指标不同（减脂的看体重体脂，控糖的看血糖），字段要可扩展。
- **source 字段很重要**：区分手动录入和设备同步，便于数据质量判断。

---

### 2. 饮食记录（事件流水表）

特点：每吃一次就是一条事件，需要记录"吃了什么、什么时候、多少"。

```
DietRecord {              // 主表：一次用餐事件
  id
  user_id
  meal_type          // 早餐/午餐/晚餐/加餐
  time               // 用餐时间
  location           // 在家/外食/外卖（可选）
  input_type         // photo / text / photo+text ← 和你的输入设计呼应
  raw_text           // 用户原始文字
  raw_image_url      // 原始照片存对象存储，表里只存URL
  note               // 用户备注
  created_at
}

DietItem {               // 从表：这一餐包含的每样食物
  id
  record_id          // 外键关联主表
  food_name          // 食物名
  quantity           // 份量
  unit               // 单位（克/份/碗）
  calories           // 热量
  protein/carb/fat   // 营养成分
  sodium/sugar       // 钠/糖
  confidence         // 识别置信度 ← 呼应拍照识别
  is_confirmed       // 用户是否确认了识别结果
}
```

**为什么主从分表**：一顿饭可能有多样食物（一餐=多个DietItem），分开才能做营养累加和单品查询。

---

## 三、两类数据如何"关联管理"

这是你产品的核心价值——**两类数据互相反哺**：

```
身体数据 ──提供个性化基准──→ 饮食建议
   ↑                              │
   │                              ↓
   └────饮食记录累积趋势────── 影响身体变化
```

**具体机制**：
1. **身体数据 → 饮食建议**：算出用户每日热量/营养目标，饮食记录实时对照。
   > 例：基础代谢算出日需1800kcal → 今日已摄入1200 → 剩余600
2. **饮食记录 → 趋势反馈**：按日/周/月聚合，生成报告。
   > 例："本周平均钠摄入偏高""连续5天蛋白质不足"
3. **联动触发**：身体指标变化时提示关联。
   > 例："体重连续两周未变，是否调整饮食结构？"

## 四、存储策略

### 存储分层

| 数据类型 | 存储位置 | 理由 |
|---------|---------|------|
| 结构化数据（数值、字段） | 关系型数据库 | 便于查询、聚合、统计 |
| 原始照片 | 对象存储（OSS/S3） | 图片大，不进库，表里存URL |
| 聚合统计结果 | 缓存/物化视图 | 周报月报不用实时算 |
| 敏感健康数据 | 加密存储 | 合规要求 |

### 关键策略

1. **读写分离**：饮食记录写多读少，身体数据读多写少，可分别优化。
2. **冷热分离**：近期记录高频访问放热存储，历史记录归档。
3. **照片生命周期**：原始照片可设保留期（如90天），既省成本也降隐私风险；用户可手动保留重要照片。
4. **聚合表预计算**：日汇总/周汇总提前算好，避免每次打开都全表扫描。

---

## 五、数据管理（增删改查 + 治理）

### 1. 写入管理
- **手动录入**：表单 + 快捷录入（常用食物一键记录）
- **拍照自动带入**：呼应你的输入设计，照片识别结果直接预填 DietItem，用户确认/修正
- **设备同步**：体脂秤、血糖仪等，source 字段标记来源
- **去重与纠错**：同一餐重复提交要合并；识别错误的 item 允许用户修改（is_confirmed 标记）

### 2. 查询管理
- **时间维度**：日/周/月/自定义区间
- **指标维度**：单指标趋势（体重曲线）、多指标对比
- **食物维度**：常吃食物排行、某食物摄入频次

### 3. 隐私与合规（重点）
- **加密**：传输加密（HTTPS）+ 存储加密（敏感字段）
- **权限隔离**：用户只能访问自己的数据
- **用户控制权**：可导出、可删除全部数据（合规硬要求）
- **授权范围**：若未来接入医疗/健康服务，需明确授权边界
- **免责声明**：数据仅供自我管理参考，不作医疗诊断

### 4. 数据质量
- 异常值检测（如体重录成300kg 提示确认）
- 单位统一（全部转标准单位存储）
- 缺失值标记（不强制填写，但记录哪些没填）

## 七、三个落地建议

1. **MVP 先存最小集**：身体数据先做身高、体重、目标；饮食记录先做食物名、份量、热量。别一上来铺满字段。
2. **主从分表从第一天就做对**：饮食主表+明细从表的结构后期很难改，一开始就设计好。
3. **隐私合规前置**：健康数据敏感，加密、导出、删除能力要在 MVP 就具备，不要等上线后补。

## 一、可行性判断：可行，但不是"拍一下就对"那么简单

**结论：技术上可行，且已有成熟路线，但要认清三个难点，否则做出来体验会很差。**

| 难点 | 具体问题 | 难度 |
|------|---------|------|
| **细粒度分类** | 区分"红烧肉 vs 糖醋排骨 vs 东坡肉"这类相似菜 | 高 |
| **混合菜品** | 中餐一盘里常有多种食材（青椒炒肉、麻辣香锅） | 高 |
| **份量估计** | 识别出"米饭"容易，但"多少克"极难 | 极高 |
| **非标菜品** | 家常菜、地方菜、店名菜，训练集里根本没有 | 中高 |

**所以正确的产品心态是**：不是"识别即正确"，而是"识别出候选 + 用户确认/修正"。这一点和你之前设计的 `confidence`、`is_confirmed` 字段正好呼应。

## 二、技术路线对比

有三条主流路线，各有取舍：

### 路线A：专用食物分类模型（传统CV）
- **做法**：用 Food-101 这类数据集训练的 CNN/ResNet 分类模型
- **优点**：快、便宜、可离线、可控
- **缺点**：只能识别训练集里的固定类别（101类），遇到中餐家常菜就抓瞎，无法输出营养/份量
- **适合**：只做"通用食物大类"识别

### 路线B：多模态大模型（VLM）直接识别 ⭐推荐
- **做法**：把图片丢给视觉多模态大模型，让它输出食物名+描述
- **优点**：能识别开放类别（不用预先定义菜单）、能理解场景、能直接输出结构化结论
- **缺点**：有幻觉风险、调用有成本、延迟比小模型高
- **适合**：你的场景（开放、多模态、要结合文字）

### 路线C：混合方案（级联）
- **做法**：小模型先快速筛 → 大模型兜底/精修 → 营养库匹配
- **优点**：成本和准确率平衡
- **缺点**：架构复杂
- **适合**：用户量起来后的优化阶段

**建议：MVP 走路线B（VLM），跑通体验后再演进到路线C。**

### 整体架构

```
[小程序端]
  拍照/选图
    ↓ 压缩、旋转校正、转Base64或上传URL
[上传层]
  图片上传至对象存储，拿到URL
    ↓
[识别服务]
  组装Prompt + 图片 → 调用VLM
    ↓ 输出结构化JSON
[结构化解析]
  解析出：食物名、置信度、可能份量
    ↓

  叠加用户画像、过敏原、目标
    ↓
[返回端]
  展示识别结果 + 让用户确认/修正
    ↓ 用户确认
[入库]
  写入 DietItem（带 is_confirmed、confidence）
```

### 核心：Prompt 设计要求结构化输出

不要让模型自由发挥，要约束它输出JSON：

```
你是食物识别助手。请识别图片中的食物，严格输出JSON：
{
  "foods": [
    {
      "name": "食物名称",
      "confidence": 0.0-1.0,
      "estimated_quantity": "估算份量(如1碗/200g)",
      "ingredients": ["可能含的食材"],
      "is_mixed_dish": true/false
    }
  ],
  "scene": "用餐场景描述",
  "need_confirm": true/false
}
```

**关键约束**：
- 要求输出 `confidence`，低置信度自动触发前端反问
- 要求识别 `ingredients`，应对混合菜品
- 明确告知模型"不确定就说不确定"，抑制幻觉

### 分步流程

1. **拍照** → 前端压缩到合理尺寸（如1024px），省流量和token
2. **上传** → 存对象存储，返回URL（不要直接把大图塞进API）
3. **识别** → 调VLM，带上面Prompt
4. **解析** → 拿到结构化结果，校验字段
5. **营养补全** → 食物名去查营养库（如USDA、中国食物成分表）补营养值
6. **个性化** → 查用户过敏史/目标，加警示（如"含花生，你过敏"）
7. **返端确认** → 展示结果，用户可改食物名、调份量
8. **入库** → 确认后写入饮食记录

### 与前面设计的衔接
- 识别结果 → 自动预填 `DietItem`
- `confidence` → 直接用；低于阈值（如0.7）标黄让用户确认
- `is_confirmed` → 用户点确认后置true
- 用户修正的名字 → **收集起来做badcase，未来微调模型**

## 一、可行性判断：可行，但必须换一个思维——**营养数据不能靠模型"生成"**

**结论：完全可行，但你之前几个功能的技术直觉在这里要反过来。**

关键分水岭：

> **食物识别**可以靠多模态大模型（开放类别，容错高）；
> **营养数值**绝对不能靠大模型生成——它会一本正经地胡说八道。

原因：大模型对"红烧肉每100g含多少卡"这类问题**没有可靠记忆**，它会根据语言模式"编"一个看似合理的数字。而营养数据是要进用户健康档案的，一个编造的热量值后果比识别错菜名严重得多。

**所以正确架构是**：

```
大模型负责"识别是什么" → 营养数据库负责"含多少营养" → 计算逻辑负责"这顿多少"
```

模型做**前端识别与匹配**，数据库做**数值背书**，代码做**份量计算**。三者分工，缺一不可。

---

## 二、先拆解"营养成分分析"到底要算啥

别把它当成一个黑盒，拆成四个子问题：

| 子问题 | 具体要产出 |
|--------|-----------|
| **① 是什么** | 每样食物的标准名称 |
| **② 多少** | 每样食物的份量（克） |
| **③ 含多少** | 每样食物对应营养素密度（每100g值） |
| **④ 共多少** | 汇总这一餐的总量 |

**记住这个公式**：

```
某营养素摄入量 = Σ（食物营养密度 × 实际份量 ÷ 100g）
```

这是整个功能的数学内核。所有架构都是为服务这个公式。

**营养素指标建议**：基础六大项（热量、蛋白质、碳水、脂肪、钠、糖）+ 可扩展（膳食纤维、胆固醇、饱和脂肪、钙铁锌、维生素）。起步只做六大项。

## 三、技术路线对比

### 核心问题：营养数值从哪来？

这是本功能与传统"AI说个数"的根本区别，有三条路线：

| 路线 | 做法 | 优点 | 缺点 | 建议 |
|------|------|------|------|------|
| **A. 全靠大模型生成** | 让LLM直接说"红烧肉500大卡" | 实现最简单 | **数值不可靠、会幻觉、无法溯源** | ❌ 不推荐 |
| **B. 营养数据库 + 匹配** ⭐ | 识别食物名→查标准营养库 | 数值权威、可溯源、可计算 | 依赖库覆盖度、要处理份量 | ✅ 推荐 |
| **C. 混合（识别用模型，数值用库）** ⭐⭐ | LLM识别+匹配库，库未命中才让模型估算 | 覆盖广 + 数值可靠 + 应急兜底 | 架构稍复杂 | ✅✅ **最佳** |

**建议：走路线C。** 这正是你前面几个功能一以贯之的思路——模型负责"理解"，结构化数据负责"事实"。

### 营养数据库选型

| 数据库 | 特点 | 适合 |
|--------|------|------|
| **中国食物成分表** | 中式食物权威、中文菜名全 | 国内产品**首选** |
| **USDA FoodData Central** | 全球最全、开放免费 | 补充西式食物 |
| **自建菜品库** | 针对你家常菜、店名菜补充 | 长尾兜底 |
| **商业营养API** | 接入省事、有中文菜 | 想快速上线的选择 |

**建议：以中国食物成分为主库 + USDA补充 + 自建高频家常菜库作长尾兜底。**

## 四、模型选择

分两块，分工明确：

### 1. 识别/匹配环节 → 用LLM或VLM
- **纯文字输入**：LLM做食物实体抽取 + 归一化（"一碗大米饭"→"米饭"）
- **图片输入**：VLM识别（复用你前面拍照识别的能力）
- **国产**：通义千问VL/文本、豆包、Kimi、GLM —— **合规友好，中式菜名强**，首选
- **作用边界**：**只让它输出"食物标准名+估算份量+置信度"，绝不让它输出营养数值**

### 2. 数值环节 → 不用模型，用数据库查询
- 拿识别出的标准食物名 → 查营养库 → 返回每100g营养密度
- 这一步是**确定性查询**，不是AI推理，结果可复现、可审计

> **这是本方案和"让GPT算营养"最大的区别：数值环节去AI化。**

### 3. 兜底环节 → 库未命中时才让LLM估
- 食物在库中查不到时，才让LLM给一个"估算值"，并**明确标记"估算，仅供参考"**
- 这是应急通道，不是主路径

**注意**：模型具体版本、定价会持续更新，落地前以厂商最新文档为准——这部分我无法提供实时信息。

## 五、完整实现方案

### 整体架构

```
[输入]
  文字/照片（复用已有输入设计）
    ↓
[① 识别层]  ← LLM/VLM
  抽出食物标准名 + 估算份量 + 置信度
    ↓
[② 匹配层]  ← 关键环节
  食物名去营养库检索（模糊匹配+别名映射）
    ├─ 命中 → 取每100g营养密度
    └─ 未命中 → 走兜底（LLM估算 or 上位概念替代）
    ↓
[③ 计算层]  ← 纯代码，确定性
  Σ(营养密度 × 份量/100)
  算出这餐总热量/蛋白/碳水/脂肪/钠/糖
    ↓
[④ 个性化层]
  对比用户每日目标 → 是否超标/不足
  叠加过敏原、健康禁忌提示
    ↓
[⑤ 输出层]
  展示拆解 + 汇总 + 评价 + 数据来源标注
```

### 分步流程

1. **拿食材清单**：从识别结果得到"米饭200g、红烧肉150g"这样的列表
2. **逐个匹配**：每个食物名去营养库查
   - 处理别名（"西红柿"=“番茄”）
   - 处理模糊名（"红烧肉"→按标准配方估算）
3. **计算总量**：套公式 Σ(密度×份量/100)
4. **对照目标**：和用户日目标比，算占比和剩余
   > "这餐680kcal，占日目标38%；钠偏高，已接近上限"
5. **输出**：拆解表 + 汇总卡 + 一句话评价

### 示例输出

```
这餐分析：
  米饭 200g    →  232 kcal
  红烧肉 150g  →  480 kcal
  ───────────────────────
  合计         →  712 kcal
  蛋白质 22g | 碳水 68g | 脂肪 38g | 钠 980mg

  评价：热量适中，但脂肪和钠偏高，晚餐建议清淡些。
  ⚠️ 红烧肉为估算值，仅供参考
```

### 与已有功能的衔接
- 复用**拍照识别**产出食物名
- 复用**饮食记录**结构（DietItem）直接挂营养字段
- 复用**身体数据**的目标设定做对比基准
- 复用**分享文案**功能，把营养结论带进文案

## 六、关键难点与应对（本功能是最难的一块）

| 难点 | 说明 | 应对 |
|------|------|------|
| **份量估计** ⭐最难 | 识别"米饭"容易，"200g"极难 | 参照物提示(筷子/手掌)、份量档位(小/中/大)、用户手调 |
| **混合菜品** | "青椒炒肉"是复合菜，库里没有 | 按标准配方拆解(青椒+猪肉+油)、或建复合菜库 |
| **食物名归一化** | "番茄/西红柿""土豆/马铃薯" | 别名映射表 |
| **长尾菜品** | 家常菜、店名菜库里没有 | 三级兜底：复合菜库→拆配料→LLM估算 |
| **数值可信度** | 生成值vs数据库值混淆 | **强制标注来源**，数据库值=可信，估算值=标黄提示 |
| **烹饪方式差异** | 同样的肉，蒸vs炸热量差几倍 | 库里按烹饪法分条目，或识别时问烹饪方式 |
| **成本** | 每餐都调模型+查库 | 常用食物结果缓存、批量查询 |
| **合规** | 营养数据不能当医疗建议 | 免责声明、明确"仅供参考、非诊断" |

---

## 七、三个关键设计原则

1. **数值去AI化**：营养数字**只从数据库来**，模型碰不得。这是整个功能可信度的生命线。
2. **份量是难点也是重点**：算法再准，份量错一倍，结果全错。把份量交互（档位/参照物/手调）做扎实，比换更贵的模型有用。
3. **数据可溯源**：每个数字都要能说"从哪来"（数据库值班/估算值）。用户问"凭什么"，你要答得上。

---

## 八、成本与工程建议

1. **成本控制**：识别结果+营养结果缓存；常用食物不动模型；只在识别环节用模型，计算环节零成本
2. **延迟控制**：识别（秒级）→ 匹配计算（毫秒级），前端分段展示
3. **准确率迭代**：收集用户修正的份量和食物名 → 建badcase → 补库/微调识别模型，这是准确率提升的飞轮
4. **MVP不贪全**：先做六大营养素 + 常见食物 + 份量档位，跑通"识别→匹配→计算"闭环，别一上来追求精确到克

## 九、一句话总结

**可行。核心不是选哪个模型，而是"把数值从模型里拿出去"——模型只负责识别食物和份量，营养数值由权威数据库+确定性公式算出，模型估算仅作长尾兜底且必须标注。份量估计是最大难点，把它的交互做扎实比换模型更重要。**

## 四个功能的技术一致性回顾

到这儿你已经问完四个功能，其实它们共享**同一条技术主线**，帮你拉通看：

| 功能 | 模型角色 | 数据/代码角色 |
|------|---------|--------------|
| 拍照识别食物 | 识别食物名 | 无/用户确认兜底 |
| 生成分享文案 | 生成文字 | 模板兜底 + 结构化数据输入 |
| **分析营养成分** | 识别食物名+份量 | **数据库供数值 + 代码算总量** |
| （前）输入/存储设计 | — | 数据结构底座 |

**主线思想**：**模型负责"理解语义/感知"，结构化数据与确定性代码负责"事实与计算"，两者边界清晰，永不越界。** 这条原则贯穿你四个功能，是整个产品技术可信度的根基。

## 第8轮（任务16）：自主设计两个新功能

这次不需要声明 exceed——这是个纯设计/可行性分析任务，在能力范围内，我直接答。

先明确一下前提：这是个以"识图识菜 + 文案 + 营养 + 搭配"为核心的饮食类小程序。我在不重复这四个功能的前提下，提两个新功能，并给出可行性、模型选型和实现路径。

## 新功能一：食材反查菜谱（"冰箱里有啥，能做什么"）

**功能描述**
用户上传一张食材照片，或手打/语音列出食材（如"鸡蛋、番茄、剩米饭"），系统反推能做的菜谱，输出菜名、用量、步骤、大致营养和所需时间。

**可行性：高**
- 识别食材这一环可以直接复用你已有的"识别食物"能力，边际成本低。
- 生成菜谱是纯文本生成，主流 LLM 都能做。
- 唯一要注意的是"幻觉菜谱"（步骤合理但不可行/有毒搭配），可通过检索增强缓解。

**模型选型**
- 食材识别：视觉多模态模型（如 Qwen-VL、DeepSeek-VL、GPT-4o 等）。
- 菜谱生成：文本 LLM（DeepSeek-V3/R1、Kimi、GPT-4o 均可）。
- 可选：接一个菜谱向量库做 RAG，提高步骤可信度。

**实现路径**
1. 前端上传图片 → 视觉模型输出结构化食材列表（JSON）。
2. 食材列表 + 用户偏好（口味、忌口、是否有灶具）拼成 prompt。
3. LLM 生成 2–3 个菜谱；命中菜谱库时用 RAG 补充真实步骤。
4. 输出带步骤和时间，可直接复用到"营养分析"模块算热量。

**风险点**：食材识别错误会连锁到菜谱，建议加"用户确认食材"一步。

## 新功能二：语音烹饪助手（"边做边问"）

**功能描述**
用户做菜时手上有油、不方便打字，直接语音提问："下一步是啥""这个要炖多久""盐放多了咋办"，系统语音/文字实时回答，并按当前菜谱进度给上下文。

**可行性：中高**
- 技术上成熟（ASR + LLM + TTS 三段式），不是难点。
- 难点在**上下文管理**（要知道用户做到哪一步）和**厨房噪音环境的识别准确率**。

**模型选型**
- 语音识别 ASR：Whisper 系列、或小程序自带语音识别接口。
- 对话/推理：文本 LLM（DeepSeek-V3、Kimi 等）。
- 语音合成 TTS：主流 TTS 引擎即可。

**实现路径**
1. 小程序内录音 → ASR 转文字。
2. 维护"当前菜谱 + 当前步骤"的会话状态，作为上下文喂给 LLM。
3. LLM 生成回答 → TTS 播报（或文字卡片展示）。
4. 用户说"下一步/完成"时，推进菜谱步骤状态。

**风险点**：噪音下误识别、多人同时说话；建议先做"文字版分步指引 + 可选语音输入"降级方案。

## 对比小结

| 功能 | 可行性 | 核心模型 | 主要难点 |
|---|---|---|---|
| 食材反查菜谱 | 高 | 视觉模型 + LLM | 幻觉菜谱、食材识别错误 |
| 语音烹饪助手 | 中高 | ASR + LLM + TTS | 上下文管理、噪音识别 |

**建议优先级**：先做"食材反查菜谱"，因为它最大化复用了你已有的识别和营养能力，开发成本最低；"语音助手"作为差异化亮点放第二阶段。
