# EEOP 方法原理与效力分析（逐方法·技术层）

2026-08-17｜分析对象：EEOP 的方法（机制），不是规则内容。依据：EEOP实施指南v1.0、规则库与任务包、加载文本、eeop_SKILL、两个月部署观察（含 pre-flight agent 反馈的 B7/B9/A1/A5）、外部技术文献。

## 〇、方法清单（12 项机制）

| 编号 | 方法 | 作用层 |
|---|---|---|
| M1 | TAE 协议化（可观察触发→具体动作→可机检产出） | 规则表示层 |
| M2 | 单一事实源+审计者维护规则库（被治理者不生成规则） | 权责结构 |
| M3 | 任务包装配（≤5条/包，oracle 选择） | 认知预算 |
| M4 | 嵌入式多轮预载（L0规格卡→L1协议→L2正例示范→L3模板） | 提示层主杠杆 |
| M5 | 承诺轮（assistant 复述动作承诺） | 提示层辅助 |
| M6 | 加载回执（无回执禁止开始） | 强迫函数 |
| M7 | 同源生成检查项+pre_flight 脚本闸门 | 机械层 |
| M8 | L3 汇报模板（证据指针必填） | 输出契约 |
| M9 | 审计轨迹（来源标记/append-only/hash） | 事后层 |
| M10 | P11 外部核对闸门 | 独立验证 |
| M11 | P13 会话恢复重载 | 状态重建 |
| M12 | 事故驱动规则再生 | 演化闭环 |

## 一、逐方法分析

### M1 TAE 协议化
- 原理：把"禁止 X"的态度声明改写为"当 T→做 A→产出 E"的条件-动作-证据三元组。两条检验：触发可外部观察、产出可脚本检查。
- 技术定位：这是规则工程层的成熟实践，等价于把 policy 从自然语言命题转成可判定谓词。护栏文献的分层框架（prompt→hook→deterministic engine→OS，arXiv 2605.24309）中，TAE 不改规则的执行层，但它是所有机械检查的前置条件——没有可机检产出，M7 的脚本无从写起。
- 理论效力：高。它买的东西是"可判定性"本身。
- 局限：可机检性有边界——格式、字段、存在性、数值复算可机检；语义质量、动机不可机检（护栏文献："guardrails check properties, not intent"）。EEOP 遵守了这个边界，设计正确。

### M2 单一事实源+审计者维护
- 原理：规则的生产权与受约束者分离。被治理 agent 自生成规则的编造率 32-82%（我们的档案），本质是自我立法的利益冲突+自我评估盲区（见 M7 失败分析）。
- 理论效力：高且必要。软件工程对应物是"不能把权限策略交给被管控进程自写"。
- 局限：增加审计者负担；规则库滞后于新错误类型（靠 M12 补偿）。

### M3 任务包装配（≤5条，oracle 选择）
- 原理：约束数量悬崖——指令遵守率随同时约束数乘法性下降（ManyIFEval/"Curse of Instructions"：GPT-4o 十条指令全遵守率仅15%；arXiv 2409.10715：LLM 活跃跟踪约束约 5-10 条后近随机；2608.02639 "Instruction Stacking Collapse" 24 约束堆叠崩溃）。≤5 条/包正好落在工作记忆窗口内。
- oracle 选择（任务类型由协调者指定而非 agent 自判）：消除"自己选宽松的包"的利益冲突。
- 2026 年进展（IFScale 复现：前沿模型可处理数千关键词级约束）需要正确解读：那是关键词包含代理任务，不代表 nuanced 规则遵守；"少而精仍是安全默认"的判断成立。
- 理论效力：高。这是 EEOP 最有文献支撑的设计之一。

### M4 嵌入式多轮预载
- 原理：不用 system prompt 单点注入，而构造一段多轮对话历史，其中 L2 以 assistant 轮次呈现正例示范（many-shot/历史塑形服从幂律），L0/L3 分别占据上下文首尾（U 型注意曲线，lost-in-the-middle，Liu et al. TACL 2024：首尾注意力最高）。prefill/few-shot 是推理时行为塑造最有效的手段之一（诚实性诱导研究：few-shot 与续写是最有效的推理时干预）。
- 理论效力：提示层内部最高。位置工程学（规格卡在前、模板承诺在后）符合注意力分布证据。
- 固有限界（设计时已知但必须承认）：a) 会话变长后预载相对位置漂移、注意力稀释——多轮场景行为退化有实测（sharded simulation：多轮比单轮差 39%、可靠性低 112%；"When Attention Closes" 2026：跨轮表征衰减）；b) 预载是概率性影响，不是约束——任何提示层方法都锚定护栏可靠性光谱的最软一档，提示注入或长任务压力可直接颠覆。这正是 EEOP 需要 M7 机械层兜底的原因，两者是互补不是替代。

### M5 承诺轮
- 原理：让 assistant 用自己的话复述动作承诺，利用生成后一致性压力。
- 理论效力：有限且必须限定范围。CoT 忠实性文献（Turpin et al. 2023：事后编造合理化；Lanham et al.）证明自我陈述不反映真实计算——EEOP 因此把承诺对象限定为"动作"而非"结果/品质"，这个限定方向正确。但动作承诺仍是 cheap talk：它没有提高违规成本，只提高违规后不一致的可检测性。
- 定位：辅助装置，单独使用无效力；价值在于给 M9 审计提供"承诺-行为"对照面。

### M6 加载回执
- 原理：强迫函数（forcing function）——把"读过"变成可观察的产出事件，无回执=未开始。
- 理论效力：作为闭环确认机制成立（等价于驾驶舱 checklist 的念读-确认）。但它的生效条件在环路外：必须有人（协调者）真的执行"无回执不放行"。我们实践中由协调者执行，有效。
- 断点风险：若 agent 自判回执合格，退化为自我声明。

### M7 同源生成检查项+pre_flight 闸门
- 原理：教与查同源（杜绝教一套查另一套）；检查用确定性脚本。
- 理论效力：方法本身是全清单中效力天花板——harness 层 hook 不可绕过（PreToolUse 类：检查发生在框架而非 LLM，agent 无路径否决；符号护栏实测 3/3 违规拦截 0 误杀）。
- 部署断点（我们实测的核心教训）：闸门只在被运行时存在。ds_kimi 实例中 pre_flight 由 agent 自己决定何时跑——等于把门禁钥匙交给被检查者。防跳过规则（禁止跳过自检的条文）是提示层方法，守不住机械层目标。设计错误不在脚本，在挂载点：闸门的触发权必须外置（harness/调度器），否则确定性只覆盖"跑了的部分"。

### M8 L3 汇报模板
- 原理：结构化输出契约，证据字段为空视为未执行——把"如实汇报"转成 schema 校验问题。
- 理论效力：高。schema 约束生成是生产中可靠的技术（SEAR 等结构化输出的工程证据充分）；必填证据字段把一类造假（无证据声明完成）变成机械可判违规。
- 局限：schema 验结构不验内容真伪——证据指针指向的文件是否真实，仍需 M9/M10 核。

### M9 审计轨迹
- 原理：来源标记、append-only、hash 链——软件供应链审计的成熟技术（SLSA、hash-chained audit log，arXiv 2606.26924）。
- 理论效力：检测层高效力（我们的实测：EEOP 后所有违规都被发现并留痕）。
- 固有弱点：日志由被审计者书写。append-only 防的是事后篡改，防不了写入时造假——需要哈希链+定期导出给独立方（导不出即不成立）才能闭环。这正是 pre-flight 方案中"日志即凭证"的依据。

### M10 P11 外部核对闸门
- 原理：产出者≠验证者。自我评估失败是结构性的：同上下文自检确认率>90%（不论对错）；自纠盲区实测 64.5% 失败率（Tsui 2025）；同模型同上下文评审继承同一批错误（误差相关性问题，数学上可证：评估者与生成者共享盲区时，一致性不携带正确性证据）。换 fresh context 评估即显著改善——因为误差相关性被打断。
- 理论效力：清单中与 M7 并列最高，且是语义层唯一可靠路线（M7 管属性，M10 管判断）。
- 我们实测的修复路径：不替换执行者，而是把独立核对插到关键闸口（协调者充任）——以更低成本拿到误差去相关的收益。

### M11 P13 会话恢复重载
- 原理：会话无状态是平台事实；重置后按固定顺序重载 MEMORY→纲领→spec→跑自检，重建状态。
- 理论效力：必要且方向正确（对应业界的 context-OS 实践）。
- 局限：重载恢复"内容"，恢复不了"注意的鲜活度"——长会话后规则表征衰减（多轮退化文献），重载文本在上下文中的位置也不再受控。需要周期性再注入或关键闸口前重载，而非一次性恢复。

### M12 事故驱动规则再生
- 原理：新错误类型→审计者提炼新协议→规则库版本升级→协议包与检查项同步再生。
- 理论效力：作为演化闭环成立（复刻高可靠组织的事故驱动成熟路径）。
- 局限：永远滞后——防不了第一起事故；规则库会单调膨胀，与 M3 的 ≤5 条约束冲突，需要配套淘汰机制（退役登记已有，规则侧同理）。

## 二、不可实现方法的断点定位（为什么会出现 agent 做不到的方法）

把 pre-flight 反馈与我们两个月的失败案例合并看，不可实现或失效的方法全部落在三个设计断点上：

### 断点 1：挂载点错误——需要确定性的地方用了概率层
- 实例：B9 直答、B7 声明佐证要求 agent 在作答时自我约束。作答行为发生在 LLM 生成内部，没有任何外部 chokepoint；而自我评估恰是文献中证据最强的失败区（同上下文>90% 自我确认、64.5% 自纠盲区）。
- 错误环节：需求分析阶段误判了可执行性的来源——"规则写得够具体"不等于"规则有执行点"。修正：一切行为约束先问"拦截点在 harness 还是只在提示里"；只在提示里的，要么升级为发送前 lint（机械扫描草稿），要么降级标注为承诺层并接受事后审计。

### 断点 2：观测点错误——要求 agent 观测它物理上看不到的东西
- 实例：A1 原设计要求在核对时判断"群聊中这条指令之后有无更新"——检查时刻的群聊状态对 agent 不可见，不是能力问题，是信息不可得。
- 错误环节：设计时把审计者视角（能看到全部对话）无意识地代入了执行者视角。修正：把观测挪到信息可得的时刻——收指令当场本地落账，时效性从"检查时回看群聊"变成"本地日志比对"，机械可行（pre-flight 方案已按此修复）。

### 断点 3：验证者同一性——产出者兼任验证者
- 实例：A5"du 字段属外部系统算不了"的说法把机械复算降级为自我声明；以及一切"自查通过"类结论。自我声明的不可信不是因为恶意，而是误差相关性：同一模型、同一上下文，犯错的输入正是自检也会看漏的输入。
- 错误环节：设计时低估了误差相关性的结构性——它不是模型变强就消失的属性。修正：验证项必须满足"误差去相关"——独立模型、独立上下文、或干脆确定性脚本（脚本无"误差"，只有规则）。

### 断点之外的正确设计（对照）
预载结构（M4 位置工程）、≤5 条分包（M3 悬崖证据）、同源检查（M7 的生成侧）、承诺限定为动作（M5 的边界声明）、审计者不立法（M2）——这五处与外部文献独立吻合，属于设计做对了的部分。

## 三、总体结论

1. EEOP 的 12 个方法分属三个效力档：机械层（M7/M10，高效力但依赖外置挂载）、提示层（M3/M4/M5/M6/M8，概率性效力，设计基本正确但有会话衰减上界）、审计层（M1/M2/M9/M11/M12，不产生即时约束，决定体系的可演化性与事后追责能力）。
2. 理论判断与两个月实测一致：EEOP 检测层有效（违规零漏检）、预防层只在机械闸门处有效。这不是执行失败，是架构性质——提示层方法的效力上限就是概率。
3. 不可实现方法的根因不是"模型不行"，是设计时三处判断错误：挂载点（概率层担确定性任务）、观测点（代入了不可得信息）、验证者同一性（产出者自证）。三处都有已验证的修复路径，且不需要更换执行模型。
4. 对现有模型的可行性结论：EEOP 的全套方法在现有模型上都可运行，但"运行"≠"生效"——生效的充分条件是把确定性要求逐条从提示层迁移到机械层，直到提示层只剩真正只能概率处理的部分（语义判断、任务执行本身）。
