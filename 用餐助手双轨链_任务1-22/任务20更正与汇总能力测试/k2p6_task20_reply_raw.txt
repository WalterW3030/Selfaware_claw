# 饮食知识助手小程序 · 完整设计文档

> 本文档汇总了从产品定位到具体功能、数据模型、技术选型的完整设计，核心贯穿一条主线：**模型负责"理解语义/感知"，结构化数据与确定性代码负责"事实与计算"，两者边界清晰、永不越界。**

---

## 一、产品概述

### 1.1 一句话定位
一款"边吃边懂"的用餐知识助手——把每一次吃饭变成获取饮食知识、记录饮食习惯的入口。

### 1.2 核心价值主张
解决用户"吃的时候有疑问、吃完想记录、但信息分散"的痛点，通过 **拍照/文字/图文混合** 的多模态输入，实时提供用餐知识，并把零散的饮食行为沉淀为个人数据。

### 1.3 差异化三抓手
1. **场景聚焦"用餐时"**——精准卡在"吃饭这一刻"的即时需求，而非通用营养查询工具。
2. **多模态输入**——拍照识食物、打字提问、图文结合。
3. **数据闭环**——身体数据 + 饮食记录互相反哺，让建议越来越个性化（长久留存的护城河）。

---

## 二、目标用户

按需求强度分层：

| 层级 | 用户画像 | 核心诉求 |
|------|---------|---------|
| **核心** | 体重/健康管理者（减脂、控糖、健身） | 吃前想知道热量、能不能吃、怎么吃更健康 |
| **核心** | 饮食限制者（过敏、糖尿病、三高、孕期） | 快速判断"这口能不能进嘴"，规避风险 |
| **次核心** | 家庭主厨/家长 | 配餐、食材搭配、营养均衡 |
| **次核心** | 外食党/外卖族 | 看菜单、看配料、点餐决策辅助 |
| **泛用户** | 美食爱好者、养生人群 | 食物科普、饮食文化、养生知识 |

**起步聚焦建议**：核心用户中的"减脂/控糖 + 过敏人群"——需求最高频、最刚需、最易形成高留存。

---

## 三、使用场景

围绕"用餐全流程"拆解为事前—事中—事后—长期：

**① 点餐前/备餐前（决策场景）**
- 拍菜单 → 识别菜品、给热量和营养提示
- 拍食材/包装 → 看配料表、识别添加剂、过敏原
- 拍冰箱剩菜 → "这些能一起做吗""怎么搭配"

**② 用餐中（即时问答场景）**
- 拍盘中菜 → "这是什么""大概多少卡"
- 文字提问 → "螃蟹和柿子能一起吃吗""痛风能吃这个吗"
- 图文结合 → 拍照 + "我在哺乳期"

**③ 用餐后（记录场景）**
- 一键把刚才拍的食物存进饮食记录
- 自动累计当日热量/营养/糖分
- 结合身体数据给反馈（"今天钠摄入偏高"）

**④ 长期（数据沉淀场景）**
- 身体数据（体重、血糖、身高、目标）→ 个性化推荐
- 饮食记录趋势 → 周报/月报，看到习惯变化

## 五、核心：统一输入模型

不管用户发什么，先归一到统一数据结构，再进入处理管线，避免为三种情况各写一套逻辑。

```
InputObject {
  text:      string | null   // 用户文字
  image:     image[] | null  // 用户照片（支持多张）
  context: {                 // 系统附带的上下文
    userProfile,             // 身体数据、过敏史、目标
    history,                 // 近期饮食记录
    timestamp, location      // 用餐时间/地点（可选）
  }
}
```

三种输入只是同一对象的三种填充方式：
- 只发照片 → `text = null, image = [...]`
- 只发文字 → `text = "...", image = null`
- 图文一起 → `text = "...", image = [...]`

**核心原则：入口统一，分流处理。**

### 5.1 三种输入的处理差异

| 维度 | 只发照片 | 只发文字 | 图文结合 |
|------|---------|---------|---------|
| **主要难点** | 识别准确率 | 意图分类 | 图文语义对齐 |
| **意图来源** | 靠图像类型推断 | 靠语义分析 | 文字直接给 + 图像补实体 |
| **默认行为** | 识别+科普+记录 | 按分类路由 | 以文字问题为主，图像为实体 |
| **出错风险** | 识别错→答非所问 | 分类错→走错流程 | 图文冲突→答偏 |
| **必要交互** | 低置信度时反问确认 | 意图模糊时澄清 | 冲突时以用户文字为准 |

### 5.2 统一处理管线

```
[输入接收层]
   ↓ 归一化为 InputObject
[预处理]
   图片→压缩/OCR/识别    文字→意图分类/实体抽取
   ↓
[融合层]  ← 只有情况C真正触发，A/B是单模态直通
   对齐图文语义，消解冲突
   ↓
[决策路由]
   知识问答 → 知识库检索
   饮食记录 → 数据库写入
   决策推荐 → 推荐引擎
   ↓
[个性化层]
   叠加用户画像（过敏/目标/历史）
   ↓
[生成层]
   输出答案 + 记录动作 + 置信度声明
```

**图文融合的语义对齐（最关键一步）**：把文字当作对图片的"注解/指令"——
- 补充约束："我在哺乳期" → 叠加哺乳期规则
- 修正识别："这不是红烧肉，是糖醋排骨" → 用文字覆盖识别结果
- 具体问题："这个我能吃几口" → 回答针对该问题

## 六、功能详细设计

### 6.1 拍照识别食物

**可行性**：可行，但认清四个难点——

| 难点 | 问题 | 难度 |
|------|------|------|
| 细粒度分类 | 区分"红烧肉 vs 糖醋排骨 vs 东坡肉" | 高 |
| 混合菜品 | 中餐一盘常含多种食材 | 高 |
| 份量估计 | 识别"米饭"易，"多少克"极难 | 极高 |
| 非标菜品 | 家常菜、地方菜训练集没有 | 中高 |

**正确心态**：不是"识别即正确"，而是"识别出候选 + 用户确认/修正"。

**技术路线**（三条对比）：

| 路线 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 专用食物分类模型 | Food-101 训练的 CNN/ResNet | 快、便宜、可控 | 只能识别固定类别，中餐抓瞎 |
| **B. 多模态大模型(VLM)直接识别** ⭐ | 图片丢给 VLM 输出食物名 | 开放类别、理解场景、结构化输出 | 有幻觉、有成本、延迟高 |
| C. 混合级联 | 小模型筛 → 大模型精修 → 营养库匹配 | 成本准确率平衡 | 架构复杂 |

**建议：MVP 走路线B，跑通后演进到路线C。**

**Prompt 设计要求结构化输出**：

```json
{
  "foods": [
    {
      "name": "食物名称",
      "confidence": 0.0-1.0,
      "estimated_quantity": "估算份量(如1碗/200g)",
      "ingredients": ["可能含的食材"],
      "is_mixed_dish": true
    }
  ],
  "scene": "用餐场景描述",
  "need_confirm": true
}
```

**关键约束**：强制输出 confidence（低于阈值如 0.7 让用户确认）、输出 ingredients（应对混合菜）、明确告知"不确定就说不确定"。

**分步流程**：拍照 → 前端压缩到 1024px → 上传对象存储拿 URL → 调 VLM → 解析 JSON → 用户确认/修正 → 入库。

**难点应对**：

| 难点 | 应对方案 |
|------|---------|
| 细粒度分不清 | 给"红烧肉类"上位概念 + 用户修正 |
| 混合菜品 | Prompt 要求输出 ingredients |
| 份量估不准 | 参照物提示（筷子/手掌）、份量档位、用户手调 |
| 模型幻觉 | Prompt 约束 + 后处理校验（不在营养库标"待确认"） |
| 中餐长尾 | 自建常见菜库优先匹配 |
| 成本延迟 | 图片压缩、相同图哈希缓存、级联小模型 |

### 6.2 营养成分分析

**核心原则：营养数据不能靠模型"生成"。**

> 食物识别可以靠多模态大模型（开放类别，容错高）；营养数值绝对不能靠大模型生成——它会一本正经地胡说八道。

**正确架构**：

```
大模型负责"识别是什么" → 营养数据库负责"含多少营养" → 计算逻辑负责"这顿多少"
```

**数学内核**：

```
某营养素摄入量 = Σ（食物营养密度 × 实际份量 ÷ 100g）
```

**营养素指标**：起步只做基础六大项（热量、蛋白质、碳水、脂肪、钠、糖），可扩展膳食纤维、胆固醇、饱和脂肪、钙铁锌、维生素等。

**三条数据来源路线**：

| 路线 | 做法 | 结论 |
|------|------|------|
| A. 全靠大模型生成 | LLM 直接说"红烧肉500大卡" | ❌ 不可靠、会幻觉、无法溯源 |
| B. 营养数据库 + 匹配 | 识别名→查标准营养库 | ✅ 数值权威、可溯源 |
| **C. 混合（识别用模型，数值用库）** | LLM 识别+匹配库，库未命中才让模型估 | ✅✅ **最佳** |

**营养数据库选型**：

| 数据库 | 特点 | 用途 |
|--------|------|------|
| 中国食物成分表 | 中式食物权威、中文菜名全 | **主库** |
| USDA FoodData Central | 全球最全、开放免费 | 补充西式 |
| 自建菜品库 | 家常菜、店名菜补充 | 长尾兜底 |
| 商业营养API | 接入省事、有中文菜 | 快速上线可选 |

**完整架构**：

```
[输入] 文字/照片
    ↓
[① 识别层]  ← LLM/VLM：输出食物标准名+估算份量+置信度（不输出数值）
    ↓
[② 匹配层]  ← 关键：食物名去营养库检索（模糊匹配+别名映射）
    ├─ 命中 → 取每100g营养密度
    └─ 未命中 → 兜底（LLM估算 or 上位概念替代）
    ↓
[③ 计算层]  ← 纯代码，确定性：Σ(营养密度 × 份量/100)
    ↓
[④ 个性化层] 对比用户目标 → 超标/不足 + 过敏原/禁忌
    ↓
[⑤ 输出层] 拆解 + 汇总 + 评价 + 数据来源标注
```

**示例输出**：

```
这餐分析：
  米饭 200g    →  232 kcal
  红烧肉 150g  →  480 kcal
  ───────────────────────
  合计         →  712 kcal
  蛋白质 22g | 碳水 68g | 脂肪 38g | 钠 980mg
  评价：热量适中，但脂肪和钠偏高，晚餐建议清淡些。
  ⚠️ 红烧肉为估算值，仅供参考
```

**难点应对**：

| 难点 | 应对 |
|------|------|
| 份量估计（最难） | 参照物、份量档位、用户手调 |
| 混合菜品 | 按标准配方拆解 / 建复合菜库 |
| 食物名归一化 | 别名映射表（番茄=西红柿、土豆=马铃薯） |
| 长尾菜品 | 三级兜底：复合菜库→拆配料→LLM估算 |
| 数值可信度 | **强制标注来源**：数据库值=可信，估算值=标黄 |
| 烹饪方式差异 | 库里按烹饪法分条目，或识别时问烹饪方式 |
| 合规 | 免责声明、"仅供参考、非诊断" |

### 6.3 生成分享文案

**定位**：分享裂变型功能，价值在传播（拉新），不在解决痛点。设计原则——**轻、有趣、可玩，别做重。**

**本质**：不是"生成文字"，而是"生成符合社交语境的文字"。

**两组核心变量**：

| 变量组 | 具体维度 |
|--------|---------|
| 内容维度 | 吃了什么、热量、营养、是否健康、几点吃、和谁吃 |
| 风格维度 | 朋友圈晒图风、搞笑自嘲风、养生打卡风、种草安利风、凡尔赛风、夜宵罪恶风…… |

**关键洞察**：同一个"炸鸡+啤酒"，配"晒美食"和"破功自嘲"文案天差地别——**风格选择权交给用户**。

**技术路线**：MVP 用 LLM 生成（路线B），A/B 结合（LLM 超时或失败降级模板保底）。

**核心：控风格三件事**：

1. **结构化输入**：

```json
{
  "foods": ["炸鸡", "啤酒"],
  "calories": 850,
  "meal_type": "夜宵",
  "time": "23:30",
  "health_tag": "高热量",
  "user_mood": "罪恶但快乐",
  "platform": "朋友圈",
  "style": "自嘲搞笑",
  "length": "短"
}
```

2. **风格提示词库**（每风格一段 system prompt，举例）：

**「自嘲搞笑风」**：
```
你是个幽默的干饭人。根据下面这顿饭，写一段发朋友圈的短文案。
要求：口语化、有梗、自嘲但不油腻，2-3句，可带1-2个emoji。
不要出现"健康""营养均衡"这类说教词。
```

3. **输出约束**：明确字数、是否 emoji、禁止说教、一次给 2-3 个候选。

**难点应对**：AI味重→多风格模板+禁说教词+多候选；内容跑偏→只允许用输入数据；成本→相同食物+风格缓存。

---

### 6.4 搭配推荐

**可行性**：高，纯知识推理（口味互补、浓淡平衡、酒水与菜系搭配）。

**唯一外部依赖**：如果"这餐已有东西"需从订单系统/库存读取，那部分属于 B4（外部系统），需接接口；推荐逻辑本身不依赖外部。

**模型选型**：

| 场景 | 推荐模型 | 理由 |
|------|---------|------|
| 轻量、低成本、高频 | Qwen2.5-7B/14B、GLM-4-Flash、DeepSeek-V3(小档) | 任务不难，小模型够用 |
| 细腻口味/文化/营养推理 | DeepSeek-V3、Qwen-Max、GPT-4o 级 | 推理更细 |
| 要求结构化输出 | 支持 JSON mode / function calling 的模型 | 便于前端渲染 |

**实现要点**：把已有菜品整理成结构化列表作为输入，输出搭配建议（可直接归一到 InputObject 的 context）。

---

### 6.5 食材反查菜谱（二期）

**功能描述**：用户上传食材照片或手打/语音列出食材（如"鸡蛋、番茄、剩米饭"），系统反推能做的菜谱——菜名、用量、步骤、大致营养、所需时间。

**可行性**：高。识别食材复用已有"识别食物"能力，边际成本低；生成菜谱是纯文本生成。

**模型选型**：
- 食材识别：视觉多模态模型（Qwen-VL、DeepSeek-VL、GPT-4o 等）
- 菜谱生成：文本 LLM（DeepSeek-V3/R1、Kimi、GPT-4o）
- 可选：菜谱向量库做 RAG，提高步骤可信度

**实现路径**：
1. 上传图片 → 视觉模型输出结构化食材列表（JSON）
2. 食材列表 + 用户偏好（口味、忌口、灶具）拼 prompt
3. LLM 生成 2-3 个菜谱；命中菜谱库时用 RAG 补真实步骤
4. 输出带步骤和时间，可复用营养分析模块算热量

**风险点**：食材识别错误会连锁到菜谱，建议加"用户确认食材"一步（防幻觉菜谱、有毒搭配）。

---

### 6.6 语音烹饪助手（二期）

**功能描述**：做菜时手上不方便打字，直接语音提问（"下一步是啥""盐放多了咋办"），系统语音/文字实时回答，并按菜谱进度给上下文。

**可行性**：中高。技术成熟（ASR + LLM + TTS），难点在**上下文管理**和**厨房噪音环境识别准确率**。

**模型选型**：
- ASR：Whisper 系列、或小程序自带语音识别接口
- 对话/推理：文本 LLM（DeepSeek-V3、Kimi）
- TTS：主流 TTS 引擎

**实现路径**：
1. 小程序内录音 → ASR 转文字
2. 维护"当前菜谱 + 当前步骤"会话状态作为上下文
3. LLM 生成回答 → TTS 播报（或文字卡片）
4. 用户说"下一步/完成"时推进步骤状态

**风险点**：噪音误识别、多人同时说话；建议先做"文字版分步指引 + 可选语音输入"降级方案。

## 七、数据模型设计

### 7.1 两类数据的本质差异（决定必须分开建模）

| 维度 | 身体数据 | 饮食记录 |
|------|---------|---------|
| 变化频率 | 低（几天/几周变一次） | 高（每天多次） |
| 数据性质 | 状态快照（时间序列） | 事件流水 |
| 主观性 | 客观测量值 | 主观输入，有误差 |
| 关联对象 | 人 | 具体食物+时间 |
| 敏感度 | 极高（健康隐私） | 高（行为隐私） |

**核心结论：不能混在一张表里，必须分开建模。**

### 7.2 身体数据（状态快照表）

```
BodyMetric {
  id
  user_id
  date             // 记录日期
  height           // 身高（相对稳定）
  weight           // 体重
  body_fat_rate    // 体脂率（可选）
  blood_sugar      // 血糖（可选）
  blood_pressure   // 血压（可选）
  waist            // 腰围（可选）
  target           // 目标：减脂/增肌/控糖/维持
  note             // 备注
  source           // 手动录入 / 体脂秤同步 / 医疗设备
  created_at
}
```

**设计要点**：身高单独放用户档案（基本不变）；可选字段可扩展；source 字段区分来源便于判断数据质量。

### 7.3 饮食记录（事件流水表，主从分表）

```
DietRecord {              // 主表：一次用餐事件
  id
  user_id
  meal_type          // 早餐/午餐/晚餐/加餐
  time               // 用餐时间
  location           // 在家/外食/外卖（可选）
  input_type         // photo / text / photo+text
  raw_text           // 用户原始文字
  raw_image_url      // 原图存对象存储，表里只存URL
  note
  created_at
}

DietItem {               // 从表：这餐包含的每样食物
  id
  record_id          // 外键关联主表
  food_name
  quantity
  unit               // 克/份/碗
  calories
  protein/carb/fat   // 营养成分
  sodium/sugar       // 钠/糖
  confidence         // 识别置信度
  is_confirmed       // 用户是否确认了识别结果
}
```

**为什么主从分表**：一餐可能多样食物（一餐=多个 DietItem），分开才能做营养累加和单品查询。

### 7.4 两类数据的关联管理（产品核心价值）

```
身体数据 ──提供个性化基准──→ 饮食建议
   ↑                              │
   │                              ↓
   └────饮食记录累积趋势────── 影响身体变化
```

**具体机制**：
1. **身体数据 → 饮食建议**：算出日需热量/营养目标，饮食记录实时对照。
   > 例：基础代谢算日需1800kcal → 今日已摄入1200 → 剩余600
2. **饮食记录 → 趋势反馈**：按日/周/月聚合生成报告。
   > 例："本周平均钠摄入偏高""连续5天蛋白质不足"
3. **联动触发**：身体指标变化时提示关联。
   > 例："体重连续两周未变，是否调整饮食结构？"

### 7.5 存储策略

| 数据类型 | 存储位置 | 理由 |
|---------|---------|------|
| 结构化数据（数值、字段） | 关系型数据库 | 便于查询、聚合、统计 |
| 原始照片 | 对象存储（OSS/S3） | 图片大，不进库，表里存URL |
| 聚合统计结果 | 缓存/物化视图 | 周报月报不用实时算 |
| 敏感健康数据 | 加密存储 | 合规要求 |

**关键策略**：读写分离（饮食记录写多读少、身体数据读多写少）；冷热分离；照片生命周期（可设保留期如90天）；聚合表预计算。

## 八、技术架构与选型

### 8.1 模型选型总原则

- **国内手机小程序**：优先**国产多模态/文本模型**（通义千问、豆包、文心、Kimi、GLM、DeepSeek），合规友好、接入方便、**中文菜名识别明显更准**。
- **开源自部署**（量大了省钱、数据可控）：Qwen-VL、InternVL、MiniCPM-V、LLaVA 等。
- **注意**：模型版本号、定价、接口能力会持续更新，落地前需以厂商最新文档为准。

### 8.2 选型决策阶梯

```
MVP阶段（<1万用户）  → 国产多模态API，快速验证
增长阶段             → API + 专用小模型级联，控成本
成熟阶段             → 自部署开源VLM + 微调，控数据+成本
```

### 8.3 端到端主架构

```
[小程序端]
  拍照/选图/文字/语音
    ↓ 压缩、旋转校正、转Base64或上传URL
[上传层]
  图片上传至对象存储，拿到URL
    ↓
[识别服务]
  组装Prompt + 图片 → 调用VLM/LLM
    ↓ 输出结构化JSON（食物名+置信度+份量+食材）
[结构化解析]
  解析校验字段
    ↓
[营养匹配层]
  食物名查营养数据库 → 补热量/蛋白/脂肪/钠/糖（数值去AI化）
    ↓
[计算层]
  Σ(营养密度 × 份量/100) → 确定性算出这餐总量
    ↓
[个性化层]
  叠加用户画像、过敏原、目标
    ↓
[返回端]
  展示结果 + 用户确认/修正
    ↓ 用户确认
[入库]
  写入 DietItem（带 is_confirmed、confidence）
```

### 8.4 全链路数据流（含新功能）

用户输入 → InputObject 归一 → 识别 → 营养匹配计算 → 个性化 → 输出/记录 → 数据飞轮（用户修正 → badcase库 → 迭代）。

## 九、成本、延迟与准确率工程

### 9.1 成本控制
- 图片压缩后再传（token 大头在图片）
- 相同图片哈希缓存，相同食物+风格不重复生成
- 高并发时"小模型筛 + 大模型兜底"
- **只在识别环节用模型，计算环节零成本**

### 9.2 延迟控制
- VLM 调用秒级，前端要有 loading 和进度反馈
- 识别（秒级）→ 匹配计算（毫秒级），前端分段展示

### 9.3 准确率飞轮（核心）
- 收集用户修正的食物名和份量 → 建 badcase 集 → 优化 Prompt 或微调模型 → 补库
- 这是产品准确率提升的**核心飞轮**

### 9.4 份量交互（比换模型更重要）
- 参照物提示（"请和筷子/手掌一起拍"）
- 份量档位（小/中/大）
- 用户手调

## 十、合规与隐私

1. **健康措辞红线**：规避"诊断/治疗"措辞，所有健康建议附免责声明（"仅供参考、非诊断"）。
2. **食物相克谨慎**：大量流传的相克说法是伪科学，知识库需科学审核，避免损害专业可信度。
3. **隐私保护**：
   - 传输加密（HTTPS）+ 存储加密（敏感字段）
   - 权限隔离：用户只能访问自己的数据
   - 用户控制权：可导出、可删除全部数据（合规硬要求）
   - 照片上传要加密、要告知；原始照片可设保留期降风险
4. **内容安全**：生成的分享文案要过审核（避免低俗、虚假宣传、医疗宣称），可追溯。
5. **授权边界**：若未来接入医疗/健康服务，需明确授权边界。
6. **数据出境**：若用境外模型，注意数据出境合规。

---

## 十一、关键落地建议（三个"从第一天就做对"）

1. **MVP 先存最小集**：身体数据先做身高、体重、目标；饮食记录先做食物名、份量、热量。别一上来铺满字段。
2. **主从分表从第一天就做对**：饮食主表+明细从表的结构后期很难改。
3. **隐私合规前置**：加密、导出、删除能力在 MVP 就具备，不要等上线后补。
4. **识别置信度安全网**：所有识别结果带置信度，低置信度统一走"反问确认"，绝不静默入库。
5. **保留原始输入+中间结果**：便于 debug、纠错和模型迭代。

---

## 十二、贯穿全产品的技术主线

**模型负责"理解语义/感知"，结构化数据与确定性代码负责"事实与计算"，两者边界清晰、永不越界。**

具体落地为四条铁律：
- 识别靠模型，**数值靠数据库**（营养数值去AI化）
- 计算靠代码，**可溯源、可复现、可审计**
- 长尾靠兜底，**估算值必须标注"仅供参考"**
- 每步带置信度，**低置信度走用户确认**

这条原则贯穿拍照识别、文案生成、营养分析、搭配推荐、菜谱反查、语音助手全部功能，是整个产品技术可信度的根基。

---

**优先级建议**：MVP 先做【拍照识别 + 营养分析 + 数据管理】跑通闭环；一期加【分享文案 + 搭配推荐】；二期做【食材反查菜谱 + 语音烹饪助手】。

如需继续细化，可针对任一模块展开：如**数据库表结构详细 DDL**、**各风格完整 Prompt 模板**、**营养匹配的模糊算法与别名映射机制**、**份量估计的交互设计**、或**日/周报告指标设计**。
