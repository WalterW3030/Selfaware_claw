# 部署台账结构定义（v1，2026-10-13 定稿）

> 依据：Walter 2026-10-13 指令（直接从结构定稿开始）；群规则"错误复犯即修复无效"配套格式、"记录事实分层制"、"更正不覆盖"、"第三方可读标准"、"最新优先审查制"。
> 设计方法依据见文末"检索记录"（设计类工作规程要求）。

## 一、台账是什么

唯一进度基准文件（single source of truth）。位置：原仓库 三期/结论/部署台账.md，Good2Eat 仓库同名同步。只回答三件事：哪些修复真的生效了（以云端实测为准）、哪些还没生效、每件事的卡点和人。

## 二、每条记录的字段（全部必填，缺一不入账）

| 字段 | 定义 | 取值规则 |
|---|---|---|
| 编号 | 条目唯一号 | LD-YYYYMMDD-NNN，当日顺序号 |
| 日期 | 本条目落盘日期 | YYYY-MM-DD |
| 改动内容 | 谁对什么做了什么改动 | 完整主语+对象全称+一句话；禁止缩写首开 |
| 证据锚 | 可独立核验的锚点 | commit 号 / 命令输出原文摘录 / 文件路径+行号 / 对方原话原文，至少一项 |
| 云端实测结果 | 改完在云端真跑的结果 | 实测通过 / 实测未过 / 未实测，三选一；实测的附实测日期 |
| 状态 | 本条是否仍为当前有效结论 | 有效 / 已被更正 |
| 更正指针 | 被更正时指向更正条目编号 | 有效条目留空 |

## 三、铁律

1. append-only：正文只追加，不删不改旧行。发现旧条目失实：新起一条更正条目，写明"更正 LD-xxx"并把旧条目标"已被更正"（更正指针双向可追），旧行原文保留。
2. 未实测禁写"完成"：云端实测结果=未实测的条目，改动内容里禁止出现"完成/修复成功"字样，只能写"已改动，未实测"。
3. 事实/推断分层：正文只写带证据锚的事实；推断集中放文末"推断区"，每条显式标注"推断"，未证实前不得作为派发、验收依据。
4. 第三方可读：每条独立可读——完整主语、全称、日期、依据，四缺一则该条退回重写。
5. 例外登记：未结事项单独一节登记，每条含【现象/卡点/待办人/下一步动作】；例外清零前台账不算"当前健康"。

## 四、更新时机（只在三个时刻更新，当日落盘）

1. 修复类任务交付并核验后（写入新条目）；
2. 云端实测结果到达（写入实测结果；改变既有结论时走更正条目）；
3. Walter 指令要求登记或更正。

## 五、审查机制（最新优先，禁止空筛）

- 每次审查只先验头部：台账最新条目 ↔ git HEAD / 最近一次云端实测，对得上即停。
- 头部对不上：逐条向前回溯，找到最后一个可靠锚点为止；从该锚点之后以追加更正条目方式修复，不批量重抄。
- 禁止无触发点的全量重读；触发点只有三个：最新记录失效、新事实到达、Walter 指令。

## 检索记录（设计依据）

1. 关键词 "event sourcing correction events compensating entries audit trail" → Microsoft Azure Architecture Center《Event Sourcing Pattern》（learn.microsoft.com，2026-10-13 访问）：append-only 事件存储即审计轨迹，更正以补偿事件追加、不修改旧事件——支撑铁律 1。
2. 关键词 "bitemporal data valid time record corrections without deleting history" → loglune.com《Bitemporal Data: Correct the Past, Keep the Record》（2026-10-11 发布，2026-10-13 访问）：更正=关闭旧记录期+新增记录，历史不删——支撑状态/更正指针字段。
3. 关键词 "reconciliation process verify records against source of truth exception handling" → montecarlo.ai《The Comprehensive Guide To Data Reconciliation》（2026-10-13 访问）：对账例外逐条登记+处置+复核——支撑铁律 5 例外登记。
4. 关键词 "single source of truth ledger design best practices" → airbyte.com SSOT 指南（2026-10-13 访问）：单一事实源+逐字段溯源——支撑"一、台账是什么"。
