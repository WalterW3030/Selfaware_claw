# 流水线对商业调研（黑板方案）的适用性判断与三通道对比

日期：2026-09-16 | 编制：kimi | 对象：黑板方案 v3.2 商业调研版（Kimi Research多会话+GitHub黑板）
数据口径：流水线实测记录（任务20-22）+ 黑板方案文档 + 通道结构性事实；未杜撰价格数字。

## 一、判断：deepseek_kimi自检流水线不适用于这个任务

流水线的设计目的是能力边界测试：DeepSeek（deepseek-v4-flash，无联网）先答，超界声明后转交k2p6执行。商业调研的核心活动是大规模实时检索、多源交叉、引用链留存——全是B1/B3类（数据检索/网页访问）。后果：
1. 退化：DeepSeek侧对检索类问题只能几乎逐题声明EXCEED::转交，流水线退化为"每题都走一遍声明再全部甩给k2p6"，DeepSeek阶段变成纯过路成本。
2. 转交执行形态不符：流水线的k2p6转交是脚本化单次调用，不是迭代式研究者；调研要的是"检索→发现→再检索"多轮探索，流水线没有回路。
3. 黑板协议接不上：黑板要求产物是原子化findings（L1/L2分级、原始来源链接、supersedes链），流水线输出是问答日志+jsonl，中间缺一整套改写与提交机制。
4. 它的强项用不上：边界自律、成本门闸是测试指标，不是调研产能。

## 二、三通道对比（性能/表现/效率/成本）

| 维度 | 自检流水线 | 直接对话 | Kimi Research（黑板方案指定通道） |
|---|---|---|---|
| 性能（能不能干） | 不能主干：无检索能力侧在前置位，检索全靠转交，链路无迭代回路 | 轻量可干：单点查证、改写digest、核事实可以；系统调研不行（检索靠手、来源靠记忆） | 能主干：自主多步检索+引用+长报告，原生匹配黑板协议 |
| 表现（产出质量） | 调研场景无实测；类比已知：无上下文注入就跑题（任务18），注入后汇总能力成立（任务20-22）——但汇总≠调研 | 事实时效与出处不可靠（记忆型回答，商业数据幻觉风险高）；表达质量好 | 来源新鲜、引用链可追、覆盖面广；风险在回声室与来源质量（方案§9已列控制项） |
| 效率 | 实测：单周期12-26秒，但那是压缩任务；调研要N轮检索，链路每轮双模型往返+overload中断风险（实测多次） | 小问题分钟级；系统调研人工作业量大、天级 | 深度任务单次分钟级出稿，多会话经黑板并行，人工只需出题与抽查 |
| 成本 | 双模型链式重复计费（DeepSeek API tokens + k2p6额度），调研场景下DeepSeek段纯浪费 | 单模型订阅内，货币成本最低，人工时间成本最高 | 单次运行算力成本最高（会员额度制），人工时间最少；无链式重复 |

## 三、结论与建议

- 主干通道：Kimi Research + GitHub黑板，按方案v3.2部署（多agent 3-5个）。
- 辅助通道：直接对话用于轻量查证、digest改写、decision-brief整理（方案§7同款分工）。
- 流水线：不进入调研链路。它的保留价值在别处——边界行为回归测试、以及若未来要做"调研子任务的边界分流"（把可离线分析的子任务留给便宜模型、检索子任务上交）时可复用其EXCEED::协议与context-file机制，但那是改造项，不是现状适用。
- 若Walter要实测验证而非结构判断，可出一道小型真实调研题三通道各跑一次计时计费对比——需要的话我来设计对照任务。
