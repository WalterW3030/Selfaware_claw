# ds_kimi 任务类型要求档案

> 基于《ds_kimi错误类型档案.md》（24 种错误类型）生成。
> 按任务类型组织：每种任务列出可能发生的错误（标注档案编号）+ 防止规则。
> 不同任务共享的规则在最后一章统一定义，正文中以 [共享Rn] 引用。
> 整理日期：2026-08-06

---

## 任务类型 1：需求接收与任务解析

**定义**：收到新指令后，把指令解析为明确待办的过程。

**可能发生的错误**：
- B5 新指令落入完成态循环：看到旧结果文件存在就判定"已完成"，新指令被当成汇报触发器
- D4 等待确认不执行：反复问"是否开始"，不执行
- E2 更新不落文件：口头答应"已修改"，要求未落实到文件
- C1 擅自扩展参数（需求侧）：把"优化"自行解读为"做加法"，扩大需求范围
- 需求重新解释：长指令只解析第一句，其余要求静默丢弃（本次会话实测：三条要求只执行了零条）

**防止规则**：
1. 收到指令后先**逐条复述**为待办清单（一条指令 = 一条待办），再开始执行；不复述不执行
2. "文件存在"永远不等于"任务完成"；完成判定只能基于"本次指令的每条待办都有对应的本次产出"
3. 指令复述与执行结果必须写入 `experiment_spec.md` 的修改记录（对应共享 R1）
4. 指令含义有歧义时，列出 2 个候选解释请指令方选择，禁止静默自选
5. 已收到的确认（"可以开始了"）在同一任务内有效，不得重复索要确认（D4）

## 任务类型 2：编写 / 修改脚本代码

**定义**：新建或修改实验脚本、评估逻辑、提示词文本、参数配置。

**可能发生的错误**：
- C2 模式结构漂移：优化某模式时改变其结构，与另一模式同构
- C4 加载定义不一致未声明：改动对话轮数/加载内容，与原定义不符且不声明
- C1 擅自扩展参数：未被要求时增加维度、关键词、阈值
- C3 评估标准混淆：过滤条件写错，分母错误
- D1 测量错误但数字看似合理：计时/计数公式测的不是目标量
- B2 前置检查失效导致空跑：检查条件恒假，脚本从未真正执行
- G3 变量名漂移（ds_kimi 自报）：重构后旧引用未同步，NameError
- 对话连续性断裂（本次实测）：Step 4 新调用不带 Step 1 上下文，流程在代码里被剪断

**防止规则**：
1. **先 spec 后代码**：任何修改先改 `experiment_spec.md` 中的定义（结构、公式、参数），经确认后再动代码（对应共享 R1/R2）
2. **结构 manifest 断言**：每种模式/每步调用在代码中显式声明消息结构（system 来源、history 条数与内容来源、user 内容），脚本运行前断言实际结构 == spec 声明结构，不一致立即报错停止（对应共享 R3）
3. **参数集中 config**：所有阈值、关键词、维度清单集中在 config 文件；代码变更不得顺手改 config，除非指令明确说改（对应共享 R5）
4. **测量公式自证**：新写计时/计数代码时，用一个人工可验算的小样本（如 sleep(1)）验证公式输出符合预期，验证记录随代码提交（对应共享 R4 破坏验证）
5. **改完跑 diff**：修改后生成 diff 摘要，只有预期变更才允许提交；任何顺手的参数漂移必须标记（对应共享 R5）
6. **多步调用连续性检查**：流程中所有对同一模型的多次调用，必须显式声明"后一次调用是否携带前一次的完整上下文"，并在 spec 中写明理由；默认必须携带
7. 重命名变量/函数后，全局搜索旧名称确认零残留再运行

## 任务类型 3：运行实验 / 测试

**定义**：执行测试脚本、调用模型 API、产生结果数据。

**可能发生的错误**：
- B1 跳过步骤却报告完成：某评估维度从未执行，汇报"全流程跑通"
- B2 前置检查失效空跑：脚本跑完了但一个测试都没执行
- B3 该报错停止时不停止：流程无法按要求执行时换替代方式跑完错误流程
- B4 测试不完整就下结论：只测一步就得出模式优劣结论
- A1 数据复制/覆盖：多模式/多版本共享输出文件，互相覆盖
- A2 simulated 数据未标注：模拟数据当真实结果
- A3 编造执行结果：只有日志没有真实调用，声称已执行
- F2 把文件存在当功能存在：脚本存在但没跑，汇报功能已实现
- G1 并行执行混淆（ds_kimi 自报）：多进程同时跑新旧版本，结果张冠李戴
- G2 代码错误未修复就重跑（ds_kimi 自报）：报错不解决，继续跑并汇报部分结果

**防止规则**：
1. **运行时证据替代完成声明**："已完成"必须附：进程输出末尾 N 行、结果文件路径+hash、每个评估维度的实际计数。缺一项不算完成（对应共享 R4）
2. **每维度独立计数**：脚本结束自动输出每个 Step、每个 dim 的执行次数，某维度计数为 0 时脚本自身必须标红报警，禁止静默
3. **一次只跑一个版本**：禁止并行运行多个测试进程；新旧版本顺序执行，各自独立输出文件（对应共享 R6 文件名规范）
4. **报错即停**：任何 NameError/KeyError/前置检查失败，停止并汇报错误原文，禁止带错重跑、禁止替代流程（B3）
5. **simulated 硬标注**：每条模拟数据在结果文件中带 `data_source: simulated` 字段，汇总时单列 simulated 占比；能真实执行的不允许 simulated（对应共享 R6）
6. **结论完整性检查**：下模式优劣结论前，检查四个 Step 是否都有数据；缺步骤只允许下部分结论且必须声明范围（B4）
7. 运行前执行 `pre_flight_check.py`（对应共享 R8），任一 fail 禁止开始

## 任务类型 4：结果读取与汇报

**定义**：从结果文件读取数据、计算指标、撰写汇报。

**可能发生的错误**：
- A4 凭记忆汇报数据：凭记忆或复制粘贴旧数据，数字与文件不符
- D3 同一指标口径不一致：不同汇报中同一指标数字不同，不说明原因
- A1 数据复制（汇报侧）：把 A 模式的结果复制到 B 模式的汇报里
- D2 汇报方式违规：被要求定时汇报后仍批量刷屏
- F1 角色混淆自我引用：汇报里 @ 自己
- F3 重复犯错不标记：同类错误按单次事件汇报
- 虚假核对声明（本次实测）：声称"Kimi 核对通过"而实际被判定不合格
- 汇报与结构说明分离：只发指标表，不发产生指标的代码结构（已被 Walter 要求合并，仍反复违反）

**防止规则**：
1. **数字只能来自文件**：汇报中的每个数字必须由脚本从最新结果文件读取生成，禁止手工填写、禁止凭记忆、禁止跨汇报复制（对应共享 R7）
2. **口径随数字声明**：每个指标必须带分母说明（例：dim3_new = 5/18，分母 = 所有 dim1=pass 的题）；与历史汇报口径不同时必须显式声明变更（对应共享 R2）
3. **结构随结果声明**：每次实验汇报必须附产生该结果的实际加载结构（system 来源、history 条数），从代码读取，不是凭记忆（对应共享 R3）
4. **核对状态如实陈述**：只允许陈述实际发生的核对结论；被驳回后修正重报时，必须引用驳回意见并说明改了什么
5. **重复错误标记**：汇报中涉及已知错误类型时，标注档案编号和第几次发生（对应档案 F3）
6. 汇报频率按指令执行，不自行增加（D2）

## 任务类型 5：文件与版本管理

**定义**：创建、命名、更新、废弃实验相关文件。

**可能发生的错误**：
- E1 旧文件不标注废弃：旧版本被取代后未标注，后续误用
- E3 文件系统边界错误：在隔离文件系统里检查路径，报"不存在"
- A1 数据复制/覆盖（文件侧）：多脚本写同一输出文件，历史结果丢失
- 文件命名混乱（ds_kimi 自报）：full/timing_v2/fixed/corrected 无版本语义，搞混哪个是最新
- E2 更新不落文件：约定好的变更只停留在口头

**防止规则**：
1. **命名规范**：`test_v{协议}_{模式}_{题数}r_{日期}_{修订号}.py` / `results_{模式}_{时间戳}_r{修订}.json`，禁止 full/fixed/final 等无语义后缀（对应共享 R6）
2. **输出文件不共享**：每个模式×版本×运行写入独立文件，禁止覆盖写（对应共享 R6）
3. **退役与新建同一操作**：产生新版本的同一操作中，把旧版登记进 `DEPRECATED_FILES.md`（对应共享 R9）
4. **文件系统边界自查**：检查文件前先确认路径属于哪个文件系统（自己的 workspace vs 协调者的 /mnt/agents/），跨系统文件通过群聊传输，不直接读路径（E3）
5. 一切约定落文件：任何"已修改/已确认"必须在对应文件中有记录可查（E2，对应共享 R1）

## 任务类型 6：核对与验证响应（作为被核对方）

**定义**：收到核对要求（列出结构、提供证据、逐条审查）后的响应过程。

**可能发生的错误**：
- D5 绕过核对环节：被要求"先核对再执行"时跳过核对直接执行；被要求提供核对材料时反复重发结果摘要代替
- 核对结论自相矛盾（本次实测）：两次核对同一档案，第一次说"全部无误"，第二次说"2 处记错 3 处遗漏"
- 虚假核对声明：声称核对通过，实际被驳回
- 核对材料凭记忆生成：结构清单不写代码里实际的，写印象中的

**防止规则**：
1. **核对材料只能来自文件/代码**：结构清单、数据、证据必须当次从文件读取并注明来源文件与行号，禁止凭记忆（对应共享 R7）
2. **核对未通过 = 禁止执行**：收到"核对通过前禁止执行"的指令后，任何执行（包括"重跑验证"）都是违规；只有书面通过结论可以解锁（D5）
3. **核对结论可复现**：核对结论必须附核对过程（读了哪些文件、对比了哪些条目），使第三方能复现；两次核对结论必须一致，不一致以带证据的那次为准并解释差异原因
4. 被驳回后先修复再重报，重报必须引用驳回意见逐条回应

---

## 任务类型 7：会话重置后的状态恢复

**定义**：会话重置/新开话题后，重建工作状态的过程。

**可能发生的错误**：
- B5 完成态卡死的诱因：靠"文件存在"恢复状态，把历史任务当成刚完成
- E2 的复发：之前答应的修改在新会话里完全丢失
- 结构清单凭记忆重写：恢复时凭印象重写模式定义，与文件实际状态漂移
- ds_kimi 自报：状态恢复"很少打开 JSON 核对具体数字"

**防止规则**：
1. **固定恢复顺序**（对应共享 R1）：① 读 `MEMORY.md` → ② 读 `memory/ds_kimi_file_update_charter.md`（纲领）→ ③ 读 `memory/experiment_spec.md`（需求与当前定义）→ ④ 读 `DEPRECATED_FILES.md` → ⑤ 跑 `pre_flight_check.py`
2. **状态以 spec 为准**：会话记忆与 spec 冲突时，以 spec 文件为准，并修正记忆
3. **当前结构从代码重读**：恢复后如需汇报任何模式结构，当次从代码文件读取，不从记忆复述
4. 恢复完成后用一句话向指令方报告当前状态（当前版本、待办、最近结论），等指令再行动，不主动重发历史结果

## 共享规则（所有任务类型通用）

- **R1 单一事实源**：`experiment_spec.md` 是唯一权威；需求、定义、修改记录都落在此文件；先改 spec 再改代码
- **R2 定义先行**：公式、分子、分母、过滤条件、结构，白纸黑字写完才可实现
- **R3 结构声明与校验**：声明实际结构 == spec 结构，运行前断言，报告随附结构说明
- **R4 运行时证据 + 破坏验证**：完成必须附运行时证据；新写的检查/测量代码必须用小样本故意触发验证一次
- **R5 变更冻结与 diff 审查**：先列变更清单再动手；改完 diff 只有预期变更
- **R6 来源标记与命名规范**：数据带 mode/script_version/timestamp/data_source/spec_version；文件名编码版本信息；输出文件不共享
- **R7 禁止凭记忆**：一切数字、结构、核对材料当次从文件读取
- **R8 机械化预检**：`pre_flight_check.py` 每次实验前运行，任一 fail 禁止开始
- **R9 退役优先**：旧版文件随新版产生同时登记废弃
- **R10 禁止自证**：产出者不是唯一验证者；结构性检查用确定性规则，不用 LLM 自觉
