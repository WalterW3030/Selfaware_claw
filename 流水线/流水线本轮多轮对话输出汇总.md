- **能做**：食饮搭配是通用知识推理，模型靠常识就能输出（口味互补、浓淡平衡、酒水与菜系搭配等）。

| 场景 | 推荐模型 | 理由 |

| 需要细腻口味/文化/营养推理 | DeepSeek-V3、Qwen-Max、GPT-4o 级 | 推理更细，适合复杂菜系搭配 |
| 要求结构化输出 | 任意支持 JSON mode / function calling 的模型 | 便于前端直接渲染 |

## 实现方案

**1. 输入层**
把已有菜品整理成结构化列表，例如：
```json
{"dishes": ["麻婆豆腐", "宫保鸡丁"], "spicy_level": "高", "meal_type": "晚餐"}
```

**2. Prompt 设计**（关键）
- 角色设定：餐饮搭配顾问
- 搭配原则约束：口味互补（重辣→清甜解辣）、浓淡平衡、干湿搭配、营养均衡
- 输出格式强制：JSON 或固定结构

**3. 输出示例**
```json
{
  "recommend_drink": ["酸梅汤", "冰镇柠檬水"],
  "recommend_food": ["清炒时蔬", "凉拌黄瓜"],
  "reason": "已有菜品偏辣偏重口，搭配清甜/清淡项可解腻平衡"
}
```

**4. 可选增强**
- **RAG**：挂一个搭配知识库（酒水搭配表、营养表），提升专业性和一致性
- **Few-shot**：给几个示例，稳定输出风格
- **缓存**：常见菜品组合缓存结果，省成本

**总结**：选 DeepSeek-V3 或 Qwen 系列即可，核心成本在 Prompt 工程和输出结构化，不在模型规模。

## 新功能一：食材反查菜谱（"冰箱里有啥，能做什么"）

**功能描述**
用户上传一张食材照片，或手打/语音列出食材（如"鸡蛋、番茄、剩米饭"），系统反推能做的菜谱，输出菜名、用量、步骤、大致营养和所需时间。

**可行性：高**
- 识别食材这一环可以直接复用你已有的"识别食物"能力，边际成本低。
- 生成菜谱是纯文本生成，主流 LLM 都能做。
- 唯一要注意的是"幻觉菜谱"（步骤合理但不可行/有毒搭配），可通过检索增强缓解。

**模型选型**
- 食材识别：视觉多模态模型（如 Qwen-VL、DeepSeek-VL、GPT-4o 等）。
- 菜谱生成：文本 LLM（DeepSeek-V3/R1、Kimi、GPT-4o 均可）。
- 可选：接一个菜谱向量库做 RAG，提高步骤可信度。

**实现路径**
1. 前端上传图片 → 视觉模型输出结构化食材列表（JSON）。
2. 食材列表 + 用户偏好（口味、忌口、是否有灶具）拼成 prompt。
3. LLM 生成 2–3 个菜谱；命中菜谱库时用 RAG 补充真实步骤。
4. 输出带步骤和时间，可直接复用到"营养分析"模块算热量。

**风险点**：食材识别错误会连锁到菜谱，建议加"用户确认食材"一步。

## 新功能二：语音烹饪助手（"边做边问"）

**功能描述**
用户做菜时手上有油、不方便打字，直接语音提问："下一步是啥""这个要炖多久""盐放多了咋办"，系统语音/文字实时回答，并按当前菜谱进度给上下文。

**可行性：中高**
- 技术上成熟（ASR + LLM + TTS 三段式），不是难点。
- 难点在**上下文管理**（要知道用户做到哪一步）和**厨房噪音环境的识别准确率**。

**模型选型**
- 语音识别 ASR：Whisper 系列、或小程序自带语音识别接口。
- 对话/推理：文本 LLM（DeepSeek-V3、Kimi 等）。
- 语音合成 TTS：主流 TTS 引擎即可。

**实现路径**
1. 小程序内录音 → ASR 转文字。
2. 维护"当前菜谱 + 当前步骤"的会话状态，作为上下文喂给 LLM。
3. LLM 生成回答 → TTS 播报（或文字卡片展示）。
4. 用户说"下一步/完成"时，推进菜谱步骤状态。

**风险点**：噪音下误识别、多人同时说话；建议先做"文字版分步指引 + 可选语音输入"降级方案。

# 多智能体能力边界协作助手 · 小程序设计文档

> 说明：我们这轮对话的核心内容是「能力边界识别与声明协议（exceed protocol）」以及「两阶段行为规则」。本设计文档以此为基础，把该协议产品化为一个微信小程序。以下内容为纯方案设计，不含实时数据或外部系统调用。

---

## 一、产品定位

| 项目 | 内容 |
|---|---|
| 产品名称 | 边界助手（BoundaryHelper） |
| 一句话定位 | 帮助用户判断「当前任务是否超出 AI 能力边界」，并在超界时自动生成可供下游智能体直接执行的「需求描述」。 |
| 目标用户 | 多智能体协作系统的使用者、AI 工作流开发者、需要路由任务给不同模型的团队 |
| 核心价值 | 把对话中隐含的「能力边界判断」变成结构化、可存储、可路由的产品能力，减少无效调用 |
| 形态 | 微信小程序（轻前端 + 云端规则/模型服务） |

**核心概念（来自对话）**
- 能力维度：B1 数据检索 / B2 代码执行 / B3 网页访问 / B4 外部系统 / B5 其他
- 阶段一（无数据）：超界 → 声明 exceed + 提取需求；在界内 → 直接回答
- 阶段二（有数据）：强制基于数据作答，禁止拒绝性回答，强制引用数值与来源

## 三、存储设计

小程序本地 + 云端分离：

| 层级 | 存储内容 | 技术方案 | 说明 |
|---|---|---|---|
| 本地 | 会话栈、阶段状态、草稿 | `wx.setStorageSync` | 离线可用，隐私数据优先本地 |
| 云端 | 会话日志、需求模板、路由记录 | 云开发数据库 / 自建 DB | 用于审计与路由统计 |
| 模板库 | exceed 声明模板、需求提取模板 | 配置文件 | 可运营更新 |

**存储对象模型**
- `Session`：session_id、phase、created_at
- `TaskRecord`：task_text、是否超界、维度、提取需求
- `Handoff`：源智能体、目标智能体、需求文本、状态（待处理/已回填）

⚠️ 隐私：provided_data 若含敏感数据，仅本地留存，不同步云端。

## 四、功能列表与可行性 / 实现方案

### 功能 1：能力边界判定
（对应对话「判断原则」）
- **可行性**：高。规则引擎即可，无需联网。
- **实现**：关键词 + 规则匹配（实时数据→B1、代码→B2、网页→B3、外部系统→B4、其余→B5）。边界模糊时输出「需人工确认」。
- **依赖**：无外部依赖。

### 功能 2：exceed 声明生成
（对应对话「声明格式」）
- **可行性**：高。模板拼接。
- **实现**：
  ```
  [exceed my capability] 维度：B?（类别）。原因说明。
  需要协助的具体需求：{一句话描述}
  ```
- **关键点**：把原始任务压缩成「Kimi 可直接执行的一句话」。

### 功能 3：需求提取（Handoff 生成）
- **可行性**：中高。规则 + 轻量模型。
- **实现**：从 task_text 抽取动作+对象，回填 `Handoff.需求文本`。
- **示例**：输入「查询道琼斯指数」→ 输出「查询纽约股市道琼斯指数实时行情」。

### 功能 4：阶段二数据作答
（对应「两阶段行为规则·阶段二」）
- **可行性**：高，但需接入模型生成。
- **实现**：接收 provided_data → 强制生成含数值引用的答案 → 拒绝性词库过滤（拦截「无法/没有/建议你/我不能」）。
- **风险**：模型可能生成幻觉数值 → 需加「引用来源标注」校验。

### 功能 5：会话阶段管理
- **可行性**：高。
- **实现**：根据是否收到 provided_data 自动在 phase1/phase2 间切换。

### 功能 6：拒绝性回答拦截
- **可行性**：中高（正则兜底 + 语义检测）。
- **实现**：黑名单词过滤，命中则重新生成。
