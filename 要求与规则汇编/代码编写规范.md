# 代码编写规范

适用：analysis group 全部代码工作（脚本 / 云函数 / harness / 流水线装配 / 实验配套件）。
定位：本规范管**"写什么、怎么写、怎么验"**；任务51《执行规范》管**"怎么改、怎么测、怎么交付"**。两份配套使用。
生效：2026-10-10（任务52，Walter 指令①②的直接落地）。此前任务的历史问题按本规范追溯登记，不追罚。

---

## 第一章 总则

**R0 外部世界不可信，默认值是敌人。**
任何来自外部的输入——模型响应结构、文件存在性、环境变量、依赖脚本路径、文件名——都必须经过"探测→校验→显式消费"三步，禁止假设其符合预期。
依据：防御式编程核心原则（Wikipedia: Defensive programming，"Design by contract 的互补：即使在外部输入不守约时模块也能运作，且失败必须显式"）；fail-fast 原则（Martin Fowler, Fail Fast, 2004）；12-factor 之 Config（"若代码在环境与配置之间不做严格区分，则它不具备可伸缩性"）。

---

## 第二章 硬编码禁令细则（Walter 指令①的细则化）

**R1 禁止硬编码标识符。**
模型 ID、文件名（含 prompt 卡文件名）、目录路径、环境名、URL 域名，一律不得作为字面量出现在脚本里。它们必须来自：单一配置清单（如 `shared/assets.config.js`）、环境变量注入、或运行期探测结果。
依据：12-factor Config（"向环境中存储配置"是独立于代码的正确做法）；配置外置实践（configuration externalization，见 Cognition-Partner-Workshops workshop-content: configuration-management-feature-flags）。
- 反例（本仓库真实案例）：任务43 recommend.js 卡 id 硬编码 `AGT-0924-w8n-096`——换卡必须改脚本，属静默失配的温床；任务37 aiGateway `MODEL_MAP` 六位模型名内嵌。
- 正例：任务52 配置外置——`requirePromptRole('PROMPT_RECOGNIZE')` 从清单 `PROMPT_BINDINGS` 读卡 id，换卡=改清单一行，脚本零字面量。

**R2 禁止硬编码行为匹配。**
不得用硬编码字符串匹配来判定"某个特定动作/某条特定消息完成了没有"。动作完成判定必须基于**通用结构信号**（如终版载荷的恒定指纹），而非碰巧出现在载荷里的字面量。
依据：Defensive programming（对外部行为做弱假设）；《Patterns for Building Fault Tolerant Software》（InfoQ, 2026）——故障点要显式化而非被巧合覆盖。
- 反例（本仓库真实案例）：任务20-35 全程用 `modeB_m1m4` 字面量当完成信号——模型改口换词即静默断裂，35 轮未暴露；任务40 工程模式验收以"终版载荷内容 SHA 相等"为通过定义，终被实测击穿。
- 正例：任务40/41 以稳定轨迹特征（十项指纹）与证据文件验收对齐，指纹与内容去相关。

**R3 匹配/解析模式必须可读、可解释。**
脚本中的每个匹配模式（正则、字符串比较、前缀/后缀判断）必须：可一行说清意图；命名或使用具名常量说明语义；禁止无法朗读的长正则字面量直接埋在逻辑里。模式升级（如防误报收紧）必须留注释说明防的是哪类误报。
依据：Code Review Checklist for AI-Generated Code（Packt, 2026）——可读性与意图明确是 review 底线；Atlassian《5 code review best practices》——checklist 化与可解释反馈。
- 反例：`payload?.choices?.[0]?.message?.content ?? reply?.result ?? reply?.data ?? reply?.reply ?? ''` 这类裸链拼接，无任何注释说明各分支对应的实际模型行为。
- 正例：任务52 extract 的 dropBinding 正则带注释"容忍行尾注释；不匹配 MODEL_MAP（冒号后是 `{`）；不匹配数组项（引号逗号非冒号）"。

## 第三章 先探测后消费

**R4 消费外部对象前先探测类型/结构。**
用 `typeof`/`Array.isArray`/`hasOwnProperty` 探测后再消费字段；禁止裸深层链式访问假定结构存在。
依据：MDN 特性探测（feature detection）实践——按能力而非假设消费；Defensive programming 输入校验条款。
- 反例：脚本假定 `reply.choices[0].message.content` 存在，模型方一改结构即 TypeError 或拿到 undefined 静默走空值分支。
- 正例：aiGateway `normalizeDeepseekModel` 在消费 event.model 前先探类型；extract 四分支解析前先用 try/可选链+存在性检查。
- 注：v2.1 修后版已按官方端点行为固定载荷结构（multi_turn+thinking disabled），但脚本层探测仍保留——结构固定减的是解析分支数量，不减探测义务。

## 第四章 取不到如实报缺

**R5 探测失败必须显式报缺，禁止静默兜底。**
取不到预期的结构/值/文件时，必须走显式失败路径：报错（stop_reason）或显式报缺并列出缺项。禁止"猜一个默认值继续跑"。
依据：Fail-fast（Fowler 2004："故障迅速可见、便于诊断，且远胜于让系统带着错误状态继续"）；silent failure 反模式文献——《The Nightmare of Silent Failures》（opsbros.com）与《Prevention of Silent Failures》（Logdy, 2025）共同结论：静默失败是生产事故首要来源之一，显式失败成本远低于事后追溯。
- 反例：`result = data || defaults` 后在日志里什么都不说；模型请求 401 被 catch 后返回空串当"正常无输出"。
- 正例：aiGateway 清单元件缺失——加载即 throw 点名缺项；importRefTables 文件名精确不匹配→数字段模糊→再不中显式报缺列表；pre_flight 检查不过——停止成立登记，不猜"应该没问题"。

**R6 允许兜底，但兜底必须带显式告警。**
确需模糊兜底（如文件名数字段匹配）时，匹配成功也必须输出告警说明"用了兜底、精确名未命中"，使下游知道精度已降级。
依据：Defensive programming（容忍降级但要可观测）；《Patterns for Building Fault Tolerant Software》 graceful degradation 条目（Netflix 实践："系统需跨故障组合优雅降级，但降级本身要被看见"）。
- 正例：importRefTables 模糊匹配命中时，导入结果带标记，校验可见"该表经数字段模糊命中"。

**R7 外部假设必须清单化、集中化、自检化。**
脚本依赖的所有外部项（模型、文件、卡 id、环境变量、依赖脚本路径）集中登记在一份假设清单里；脚本启动时先跑清单自检（checkConfig），缺项显式拒绝并列出；假设变化只改清单，不动脚本。
依据：12-factor Config；本仓库任务52 先例（assets.config.js + checkConfig）。
- 反例：同一模型名散落三个脚本文件，换模型要改三处且必漏一处。
- 正例：任务52——EXPECTED_TABLES/EXPECTED_PROMPTS/PROMPT_BINDINGS 单点登记，三脚本共享。

## 第五章 错误显式化

**R8 禁止吞错。**
catch 之后必须：再 throw、或显式记录并改变控制流（报缺/停止）。禁止空 catch 和"catch 后当无事发生"。
依据：异常处理反模式研究（de Sousa et al., JABS 2020, "Exception handling anti-patterns in a long-lived large-scale project"——嵌套 try 与吞噬异常是最常见且危害最大的反模式）；《The Nightmare of Silent Failures》。
- 反例：`try { ... } catch (e) { console.log('ok') }`。
- 正例：extend 调用失败透传 errMsg 与 status 给前端（任务37 行为保留核验项）；checkConfig 自检失败即 throw 点名缺项。

**R9 错误信息必须含定位要素。**
报错必须让读者知道：哪个变量/哪份文件、期望什么、实际拿到什么、建议查哪里。禁止只有"failed""error"字样的无效报错。
依据：Code Review Checklist（Packt, 2026）——诊断性是错误处理评审项；Atlassian checklist 实践。
- 反例：`throw new Error('load failed')`。
- 正例：`清单自检不通过：assets.config.js 缺项：PROMPT_BINDINGS.PROMPT_RECOGNIZE`；`文件不存在：/tmp/pre_flight_check.py（/tmp 非持久，需重生成）`。

**R10 失败状态要可机检。**
设计错误回执时，考虑下游能否 grep/断言判定"失败了"。stop_reason、退出码、报缺列表等机检友好的失败面，优于只有人类可读的自然语言段落。
依据：Contract testing 实践（InfoQ: The Value of Contract Testing, 2025——测试应锚定系统行为的稳定契约，而非可塑的临时形状）；本仓库实验 Harness 先例（问题/载荷/回复三分离+NDJSON，使机器可复算）。
- 正例：两级模式 stop_reason 枚举稳定；负向单测断言"抛出且消息含'缺'+点名项"。

## 第六章 负向用例与 harness 独立假设

**R11 每个防御点至少配一个负向用例。**
清单缺项报缺、改名不命中不误配、模糊兜底优先级、错误透传、探测失败路径——每个"防御行为"都要有对应的负向测试，且负向测试断言的是"失败得对"（报缺点名/不误配），不是"没崩"。
依据：Negative testing 方法学（Functionize, 2026：负向测试专门构造意外输入以检验错误显式性；BrowserStack: Negative Testing Guide——"应用需给出合适错误消息并妥善处理"）；Wikipedia: Negative testing 词条。
- 正例：任务52 tests/assets_config_negative_tests.js 十项负向全断言异常消息内容（含'缺'+点名）。
- 判定：只断言"抛异常"而不看点名的用例算半条，按 R9 补齐。

**R12 harness 的假设必须独立于被测对象的假设。**
实验 harness/验收工具不许与被测脚本共享同一批环境假设。被测对象假设"某文件在盘"，harness 必须独立核验该文件真在盘，不能从被测对象的自我报告推断。提交证据时必须诚实声明"跑没跑机检、跑的是哪套"。
依据：Chaos engineering 独立验证思想（Netflix Chaos Monkey 以独立注入验证系统假设而非信任系统自述）；AgentChaos（arXiv:2608.06790, 2026——以故障注入实证检验 agent 系统韧性，而非采信其自我声明）；本仓库任务48 先例（以真实落盘证据驱动打回）。
- 反例：/tmp 清理后 pre_flight_check.py 不在盘，汇报却按"检查通过"口径写——harness 与被测共享"/tmp 文件永在"这一假设，双双失效。
- 正例：任务51/52 先例——机检缺席时，按文档化规则备齐汇报要素，并在证据中诚实声明"未跑机检"一节。

**R13 环境差异显式化。**
代码不得假定"开发环境=运行环境"。工作区、cron、群会话、临时目录的生命周期与工具集（解释器可用性、命令护栏）都可能不同；跨环境文件必须走持久路径并登记，命令必须符合目标环境的执行约束。
依据：12-factor（环境等价性需显式维护）；《Nightmare of Silent Failures》（环境假设失效是静默失败高发源）；本仓库 2026-10-10 exec 护栏实测（复合命令混合解释器链被拒，须直连单命令）。
- 正例：实验脚本统一持久路径（过程目录）+ 相对引用清单；提交证据注明"本环境执行约束下用 python3 直连单命令完成，与文档 python 调用等价的读数一致性已核对"。
