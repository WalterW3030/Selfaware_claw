# 食知特化参考指南与实际开发方案执行计划

日期：2026-09-18 | 编制：kimi
依据：《AI小程序低人力开发方案》（Walter提供，下称开发指南）+《食知小程序设计方案v3》+ v2各任务设计文档
用途：从开发指南提取与食知相关的要求，特化成本项目的参考指南，并给出编写实际开发方案的逐步执行计划。

## 一、从开发指南提取的与本任务相关的要求

1. **主体红线（第一个决策点）**：食知含AI生成文案与AI识别——属AI生成/深度合成相关功能，个人主体不能备案"深度合成"类目。按指南：核心涉AI对话/生成→需个体工商户或企业主体（约300元/年）。**这条无法技术绕过，立项第一天必须由Walter拍板**。
2. **AI接入用 wx.cloud.extend.AI**：多模型接入=配置问题（3行代码换模型），Key平台托管、原生流式。与食知v3的"识图强VL、文案营养用轻量模型"的分级路由完全同构。
3. **框架 uni-app（Vue3）**：AI语料最熟、一套代码多端、性能足够。
4. **后端 CloudBase 云开发**：免服务器免运维；v2的本地优先+授权云同步，云层落到CloudBase。
5. **三标准优先级**：减少人力 > 开发难度 > 性能/曝光。开发方案的人力形态=1技术负责人+AI结对，禁止AI无人审查直发生产。
6. **安全与合规**：AI生成代码约45%含安全缺陷→上线前必跑安全清单；类目/隐私/资质合规前置。
7. **验证路径**：以真实小功能全流程走一遍记录人时，AI接入或审核人时超40%则方案需修订。

## 二、食知特化参考指南

### 2.1 架构定型（四层）

```
平台主体：微信首发；主体类型=待Walter决策（见红线）
框架：uni-app (Vue3)
AI接入：wx.cloud.extend.AI（配置化多模型）
后端：CloudBase 云开发（数据库/云函数/存储/支付如需）
工具链：CodeBuddy + miniprogram-ci
```

### 2.2 模型路由（承接任务25选型结论）

| 功能 | 模型档位 | 接入方式 |
|---|---|---|
| 识图/含图自由提问 | 强多模态模型（不降配） | extend.AI配置VL端点（**待验证**：extend.AI是否支持图像输入；不支持则走OpenAI兼容端点如硅基流动挂Qwen3-VL） |
| 文案生成 | 轻量模型（deepseek-v4-flash级） | extend.AI直配 |
| 营养建议翻译 | 轻量模型 | 同上 |
| 自由提问（纯文本） | 强文本模型 | 同上 |
| 营养计算/搭配过滤 | 不用模型，规则引擎+数据库 | 云函数 |

### 2.3 数据层落地映射（承接任务24五表）

dish_profile / diet_record / daily_nutrition_summary / nutrition_audit_log / user_profile → CloudBase五个集合；本地Storage做离线缓存与未授权态，授权后同步云端；敏感字段（身体数据）加密存储，安全规则禁止未登录读写。

### 2.4 合规清单（食知特化）

- 主体类型决策（红线）；类目申报：工具/生活服务，文案避开"资讯/教程/医疗"字样
- 全量"非医疗建议，以医嘱为准"标注
- 敏感个人信息：分层授权弹窗（身体数据/饮食记录/微信运动分别触发，不打包）
- 隐私政策先行；可导出可删除入口
- 不碰虚拟支付；若未来变现（如高级营养报告），iOS端不露头
- extend.AI调用的用户数据出域问题需在隐私政策中声明

### 2.5 安全红线（写进项目AGENTS.md）

用户输入校验转义；云函数权限最小化；密钥只在云函数环境变量/extend.AI托管，禁止前端硬编码；数据库安全规则禁未登录读写；AI生成代码上线前逐项过OWASP清单。

### 2.6 人力形态

Walter（产品负责人：架构决策、合规判断、AI产出审查、审美上限）+ AI结对（编码/测试初筛/文档）。禁止AI直连生产环境。
